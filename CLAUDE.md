# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Laminar Python SDK - tracing and evaluation framework for LLM applications. Provides automatic instrumentation for LLM providers (OpenAI, Anthropic, Groq, etc.), manual tracing via decorators, and an evaluation framework for testing LLM outputs.

## Commands

```bash
# Install dependencies with all extras
uv sync --all-extras --dev

# Run all tests
uv run pytest

# Run specific test file
uv run pytest tests/test_initialize.py

# Run specific test
uv run pytest tests/test_initialize.py::test_laminar_initialize_url_parsing -v

# Lint
uv run flake8 src/

# Format
uv run autopep8 --in-place --aggressive src/lmnr/**/*.py

# CLI commands
lmnr eval <file.py>           # Run evaluations
lmnr datasets pull <id>       # Pull dataset
```

## Architecture

### Core SDK (`src/lmnr/sdk/`)
- `laminar.py` - Main `Laminar` class with `initialize()` entry point and span management
- `decorators.py` - `@observe()` decorator for manual instrumentation
- `evaluations.py` - `evaluate()` function and `Evaluation` class for running tests
- `client/` - HTTP clients (`LaminarClient`, `AsyncLaminarClient`) for API interactions

### OpenTelemetry Layer (`src/lmnr/opentelemetry_lib/`)
- `tracing/instruments.py` - `Instruments` enum listing all auto-instrumentable providers
- `tracing/__init__.py` - `TracerWrapper` singleton managing OTEL setup
- `opentelemetry/instrumentation/` - Provider-specific instrumentors (anthropic/, openai/, groq/, etc.)
- Each provider instrumentor has: `__init__.py` (instrumentor class), `utils.py` (parsing), `span_utils.py` (span creation)

### CLI (`src/lmnr/cli/`)
- `evals.py` - `lmnr eval` command

### Debug mode / replay (`src/lmnr/sdk/debug/`)
- A "debug run" is a normal process started with `LMNR_DEBUG*` env vars; there is no cache server, SSE, orchestrator, or `lmnr dev` command. **v2 has NO in-process cache**: every live LLM call hashes its input messages and asks the **app-server** replay-cache endpoint (`POST /v1/rollouts/{session_id}/cache`) what to do (HIT / MISS / LIVE — shared spec §7). The v1 machinery (`ReplayCache`, `spine.py`, `source_trace.py`, per-path occurrence counters, synchronous cache build, SQL source-trace fetch, span-path matching) is **deleted** — do not look for it.
- This is a **cross-language parity surface** with the TS SDK `lmnr-ts/packages/lmnr/src/debug/`. Keep `config.py`, `hash.py`, `pointer.py`, `replay.py`, `__init__.py` line-comparable. The shared vector `tests/data/debug/input_hash_cases.json` (and `config_truth_table.json`) must stay byte-identical with `lmnr-ts/packages/lmnr/test/data/debug/`; change them in lockstep across both repos.
- Parity invariants that MUST match the TS SDK: truthy set `["true","1","yes","on"]`; `replay_enabled = replay_trace_id is not None and cache_until_span_id is not None`; `CONSOLE_PREFIX = "LMNR_DEBUG_RUN "`. **The persisted file is `.lmnr/debug-session.json` (was `.lmnr/last-run.json`).** Its shape (`DebugSessionFile`) + filename consts (`DEBUG_SESSION_DIR`/`DEBUG_SESSION_FILE`) and the best-effort `read_debug_session_file` / `write_debug_session_file` fs helpers live in `debug_session_file.py` (in TS the contract lives in `@lmnr-ai/types` and the fs helpers in `src/debug/debug-session-file.ts` + the CLI; Python has one package so both halves are in one module). `DebugSessionFile` field order is `[session_id, trace_id, replay_trace_id, cache_until, debugger_url, started_at]` — `session_id` is now FIRST AND primary (the field read at startup), and `trace_id` is `str | None` (a freshly-minted session has no trace yet).
- **Input hash (`hash.py`, shared spec §5):** each cached LLM call is addressed by `hex(blake3(canonical_json(messages_without_system)))`. `_canonical_json` reproduces app-server's `input_dedup.rs::canonical_json` byte-for-byte (object keys sorted lexicographically + recursively, array order preserved, scalars via `json.dumps(..., ensure_ascii=False)`); system-message exclusion mirrors `prompt_hash.rs::extract_system_message` (first `role=="system"`, text pulled from string / content-array / `parts` shapes, dropped only when non-empty). **`blake3` (`>=1.0.0,<2.0.0`) is a new runtime dependency** (added to `pyproject.toml`). Number canonicalization is deferred (`1.0` ≠ `1`); revisit only in the shared spec on both sides. Pinned by `input_hash_cases.json` (`tests/test_debug_replay.py::test_input_hash_matches_shared_vector`).
- **The hash is computed off the live span's `gen_ai.input.messages` attribute** (a JSON STRING every provider stamps before the rollout wrapper runs), read via `input_messages_from_span` in `replay.py`. That attribute is exactly what becomes `spans.input` server-side, so hashing it gives the SAME hash app-server computes from the stored span — parity without re-deriving messages per provider. A missing / unparseable / non-list attribute → `None` → run live (never hash a partial input).
- **Three cache outcomes (`outcome.py` `CacheOutcome(kind, cached)`):** HIT (`{"outcome":"hit","response":{...}}`) → serve the cached span; MISS (`{"outcome":"miss"}`) → latch the process-wide run-live flag so every later call skips the endpoint and runs live; LIVE (`{"outcome":"live"}`, warmup-timeout / transport degrade) → run THIS call live WITHOUT latching. COLD is never seen by the SDK. The HIT `response` is **CachedSpan-shaped** (`attributes`, `output`, `start_time` ns, `end_time` ns) — the provider `cached_response_to_*` reconstructors read `start_time`/`end_time` (ns) plus `attributes["gen_ai.output.messages"]` / `attributes["lmnr.sdk.raw.response"]` and reset usage to 0 tokens.
- **The cache HTTP never raises:** `RolloutSessions.cache(session_id, replay_trace_id, cache_until, input_hash)` (sync `rollout_sessions.py` + async mirror) POSTs `{replayTraceId, cacheUntil, inputHash}` and maps the discriminated `{outcome}` body via `_parse_cache_outcome`; any non-2xx or transport exception degrades to `kind="live"`. Only a real MISS latches run-live — that's the **caller's** job (`cache_outcome_for`), not the resource's.
- **A HIT MUST carry a non-null `response` to be servable** — `_parse_cache_outcome` degrades a HIT whose body omits/nulls `response` to `kind="live"` (run this call live, no latch). Without this guard `CacheOutcome(kind="hit", cached=None)` reaches the provider wrappers, which call `cached_response_to_*(None)` → `None.get("type")` → `AttributeError`, and since the chat wrapper re-raises (it is NOT `@dont_throw`) the whole debug run aborts. Fixed once at the shared parse boundary, not in each of the four `cached_response_to_*` methods. Pinned by `test_parse_outcome_hit_without_response_degrades_to_live`.
- **The run-live latch is a process-wide `Laminar.__debug_run_live` flag** (`is_debug_run_live` / `set_debug_run_live`), shared by the sync and async paths. `cache_outcome_for` / `acache_outcome_for` (`replay.py`) short-circuit to `CacheOutcome(kind="live")` WITHOUT hitting the endpoint once it's latched. `Laminar.shutdown()` resets it to `False` so a later `initialize()` starts clean. Tested in `tests/test_debug_replay.py` (`test_cache_outcome_miss_latches_run_live`, `..._live_does_not_latch`, `..._short_circuits_when_already_live`) and `tests/test_debug_runtime.py` (`test_shutdown_resets_run_live_latch`).
- **`replay_enabled()` gates on `get_runtime().replay_configured`, NOT on `get_runtime() is not None`.** A debug-no-replay run (`LMNR_DEBUG` set but no `LMNR_DEBUG_REPLAY_TRACE_ID` / `LMNR_DEBUG_CACHE_UNTIL`) still creates a runtime — needed to stamp `rollout.session_id` and emit the run pointer — but replay must stay off there, or the provider wrappers hit the cache endpoint for a run with no source trace. In v2 `DebugRuntime.replay_configured` collapses to `config.replay_enabled` (there is no synchronous build and no async load window, so no "configured but not ready" state to model). Tested in `tests/test_debug_replay.py` (`test_replay_enabled_false_for_debug_no_replay_runtime`) and `tests/test_debug_runtime.py` (`test_replay_configured_reflects_config`).
- **`LMNR_DEBUG_CACHE_UNTIL` is a span id ONLY — v2 dropped the v1 integer count form.** `config.py` `_parse_cache_until_span_id` → `_normalize_span_id` produces the hyphen-stripped lowercase hex needle `cache_until_span_id` (≤32 chars; `None` when unset or not span-id-shaped, with a warning). All four user forms suffix-match the same span server-side: full UUID `00000000-0000-0000-0123-456789abcdef`, last-two-groups `0123-456789abcdef`, raw 16-hex `0123456789abcdef`, short suffix `abcdef`. The needle is sent **verbatim** as `cacheUntil` in the cache request — app-server does the suffix match against the source trace; the SDK never resolves it (no spine, no occurrence count). There is no `config.cache_until` field anymore. Tested in `tests/test_debug_config.py` + `tests/data/debug/config_truth_table.json`.
- **Two retained clients, closed at shutdown (NOT at init).** `DebugRuntime(config, client, async_client, debugger_url)` holds BOTH a sync `LaminarClient` and an async `AsyncLaminarClient` for the whole run — sync providers look up through `runtime.client`, async providers through `runtime.async_client`. This is the key v1→v2 change: v1 closed the client at the end of init; v2 `Laminar._init_debug_runtime` constructs and **retains** both, and `Laminar.shutdown()` closes them (`runtime.client.close()` + `_close_debug_async_client(runtime.async_client)`, the latter `asyncio.run(async_client.close())`). The bail-out path inside init still closes both. Tested in `tests/test_debug_runtime.py` (`test_runtime_retains_both_clients`, `test_init_registers_session_with_backend` asserts `spy.closed is False` + `runtime.client is spy`, `test_shutdown_closes_retained_clients`).
- **Per-provider async dispatch differs — know which helper each wrapper calls.** The wrapper files are still named `rollout.py` (`instrumentation/{openai,anthropic,google_genai,litellm}/rollout.py`) and import from `lmnr.sdk.debug.replay`. **openai** and **google_genai**: the instrumentation checks `inspect.iscoroutine(result)` and the wrapper returns the coroutine on the async path (`_awrap_*` awaits `acache_outcome_for`), else `cache_outcome_for` sync. **anthropic**: the async call site ALWAYS awaits, so `wrap_create(is_async=True)` returns the `_awrap_create` coroutine directly. **litellm**: sync-only — its instrumentation routes both sync and async calls through the same sync wrapper and only `inspect.iscoroutine`s the result, so the cache lookup is a **blocking** HTTP call even on the async path (a documented v1 limitation carried forward; the lookup is small and one-shot). `get_*_rollout_wrapper()` returns `None` when `replay_enabled()` is false, so the wrappers are inert on non-replay (and non-debug) runs.
- **`mark_span_cached(span)`** stamps the CACHED boundary attributes the frontend renders: `{"lmnr.span.type":"CACHED","lmnr.span.original_type":"LLM"}` — only when the span `is_recording()`, no-op otherwise / on `None`. Called by each provider wrapper right before serving a HIT.
- The record's **`started_at` is captured at `DebugRuntime` construction (SDK init), NOT inside `build_debug_session_file`/`emit_pointer`** (the record is emitted at shutdown, so reading the clock then would stamp process-exit time). `__init__` records `self._started_at` and passes it to `build_debug_session_file(..., started_at=...)`. `emit_pointer` persists `cache_until=self._config.cache_until_span_id` (the needle as-is — a later replay re-sends the same needle). TS mirrors via `DebugRuntime._startedAt` → `buildDebugSessionFile({ startedAt })`. Tested in `tests/test_debug_runtime.py` (`test_emit_pointer_persists_cache_until_span_id`).
- `init_debug_runtime(client, async_client, debugger_url=None)` is one-shot (the `_initialized` global makes it idempotent), but `Laminar.shutdown()` supports a later `initialize()`, so it MUST call `reset_debug_runtime()` to clear `_runtime`/`_initialized` — otherwise a second `initialize()` resurrects the first run's stale session metadata / spent pointer and never re-reads `LMNR_DEBUG*`. When `build_debug_config()` returns `None` (debug off), init does NOT latch `_initialized`, so a later env-flip-on still works. `reset_debug_runtime` is the public reset (tests use it too); TS mirrors `resetDebugRuntime`.
- **The debug `atexit` pointer hook must be unregistered on `shutdown()` or it leaks the retired runtime across init/shutdown cycles.** `_init_debug_runtime` does `atexit.register(runtime.emit_pointer)` so the pointer is emitted at process teardown. `atexit` holds a *strong* reference, so even though `emit_pointer` is one-shot (`_emitted`), an `initialize()`/`shutdown()` loop (test suites, notebooks) keeps every retired `DebugRuntime` — and its retained clients — alive and accumulates dead handlers. Fix: keep the bound method by reference in `Laminar.__debug_exit_hook`, `atexit.unregister` any prior hook before registering a new one, and `atexit.unregister` + null it in `shutdown()`. The synchronous `runtime.emit_pointer()` call at the TOP of `shutdown()` MUST be wrapped in its own `try/except`: `pointer.py` does an UNGUARDED `print(..., flush=True)` (only the `write_debug_session_file` file write is best-effort), and a closed stdout (daemons, broken pipes, notebook restarts) raises `BrokenPipeError`/`OSError` that would otherwise skip `TracerManager.shutdown()` + `reset_debug_runtime()` + the atexit unregister + client close. The guard lives at the `shutdown()` call site (not in `pointer.py`) so `pointer.py`/`pointer.ts` stay line-comparable. `laminar.py` is NOT part of the line-parity surface, but TS has the same fix in `laminar.ts` (`Laminar.debugExitHook` + `process.removeListener`).
- **A debug run registers its SDK-minted session id with the backend** via `client.rollout_sessions.register(session_id)` (`POST /v1/rollouts/{session_id}`, body `{"name": null}`, project-API-key auth). Without it a bare `LMNR_DEBUG=true` run mints a session id the backend never learns about, so the run is invisible in the UI. The register call lives in `Laminar._init_debug_runtime` and is **best-effort** (own inner `try/except` inside the method's outer try/except) — a backend error only warns, never crashes `initialize()`. Python's `initialize()` has no event loop, so this is a direct blocking call (TS does fire-and-forget `void ...catch`). The endpoint is an idempotent upsert keyed on the SDK id; a null `name` never clobbers a name set elsewhere. `register` returns the backend-resolved `projectId` (`response.json().get("projectId")`, `None` on parse failure) so the SDK can build the human-facing URL. The full-URL construction is **one shared code path** `DebugRuntime.debugger_session_url()` — used by BOTH the `cls.__logger.info` console line AND the pointer's `debugger_url` field; after `register`, `_init_debug_runtime` calls `runtime.record_project_id(project_id)` (first-wins) so it returns `<base>/project/<project_id>/debugger-sessions/<session_id>`, else the bare base, else `None`. `debugger_url = os.getenv("LMNR_FRONTEND_URL") or get_frontend_url(base_url)`. For INFO to emit, `_initialize_logger` sets `cls.__logger.setLevel(get_level_from_env())`. The `RolloutSessions` resource carries `register` + `delete` + **`cache`** + `add_block` / `list_blocks` on BOTH the sync and async clients; debug init uses the sync `register`, and the cache lookups use whichever client matches the provider's sync/async path. TS mirrors `debuggerSessionUrl()` / `recordProjectId`. Tested in `tests/test_debug_runtime.py` (`test_init_registers_session_with_backend` / `test_init_survives_registration_failure` / `test_init_logs_debugger_url_when_project_id_returned`).
- **`.lmnr/debug-session.json` is now DEFAULT-ON — both the `LMNR_DEBUG_FROM_LAST_RUN` and `LMNR_DEBUG_WRITE_LAST_RUN_TO_FILE` env gates are DELETED.** `build_debug_config` always calls `read_debug_session_file()` (from `debug_session_file.py`) and `emit_pointer`/shutdown always writes via `write_debug_session_file`. The kept debug env vars are `LMNR_DEBUG`, `LMNR_DEBUG_SESSION_ID`, `LMNR_DEBUG_REPLAY_TRACE_ID`, `LMNR_DEBUG_CACHE_UNTIL`. The startup state machine: session id precedence `LMNR_DEBUG_SESSION_ID` → `existing["session_id"]` (file) → freshly-minted UUID; `session_minted` is True ONLY when we minted (so a **file-present run is a CONTINUATION — it rejoins the same session silently, no browser**, which is the core UX change). `replay_trace_id` = `LMNR_DEBUG_REPLAY_TRACE_ID` → `existing["replay_trace_id"]` → None; `cache_until_span_id` = `_parse_cache_until_span_id(LMNR_DEBUG_CACHE_UNTIL ?? existing["cache_until"])`. **Continuation ≠ replay**: unlike the old `FROM_LAST_RUN` path, the prior run's `trace_id` is NOT promoted into `replay_trace_id` — replay is armed explicitly by the agent via the env var or the file's `replay_trace_id`. `config.py` imports `read_debug_session_file` from `debug_session_file.py` (config→debug_session_file; no cycle — `debug_session_file.py` imports neither). The TS CLI's `lmnr-cli debug session new` is what mints a fresh session + resets the file; the SDK only mints when NO file exists. Keep line-comparable with TS `buildDebugConfig`. Tested in `tests/test_debug_config.py` (`test_session_file_*`, `test_env_overrides_the_file_per_field`, `test_mints_fresh_session_*`).
- **The debug-session file location is resolved by walking UP from cwd to the nearest ancestor with a usable `.lmnr/debug-session.json`** (`find_debug_session_dir` / `resolve_debug_session_dir` in `debug_session_file.py`; `read_debug_session_file(dir)` itself stays an exact-dir read). Startup (`config.py`) resolves the anchor ONCE and pins it on the config as `DebugConfig.session_dir`, alongside `file_session_id` (the on-disk `session_id` read at init); `DebugRuntime.emit_pointer` passes both to `pointer.emit_pointer`, so the shutdown write targets the SAME file startup read even if the process chdir'd in between — re-resolving at emit would retarget after a chdir, and reading from an ancestor but writing to cwd would strand the ancestor's copy stale and shadow it with a nested one. The clobber guard asks "did the file change since init?": it skips the write only when the on-disk `session_id` differs from BOTH ours and `file_session_id` (a fresher `lmnr-cli debug session new` owns the file; the console marker still prints). Comparing against ours alone would also block an explicit `LMNR_DEBUG_SESSION_ID` override from persisting to an unchanged file (Bugbot findings on PR #303). Falls back to cwd when no ancestor has a file. Mirrors TS `findDebugSessionDir` / `resolveDebugSessionDir` (de02c48); **the anchor-pinning + changed-since-init guard are Python-first — TS still re-resolves at emit and compares against its own session id, parity follow-up pending.** Tested in `tests/test_debug_pointer.py` (`test_find_*`, `test_resolve_*`, `test_emit_from_subdirectory_*`, `test_emit_persists_env_session_override_*`, `test_emit_skips_when_file_changed_*`, `test_emit_writes_to_the_pinned_directory_*`) and `tests/test_debug_config.py` (`test_session_file_found_in_ancestor_joins_its_session`, `test_config_pins_session_dir_and_file_session_id`).
- **A debug run forces batching OFF.** `Laminar.initialize()` flips `disable_batch=True` whenever `_is_truthy(os.environ["LMNR_DEBUG"])`, BEFORE `TracerManager.init` (the only consumer of `disable_batch` → `SimpleSpanProcessor` vs `BatchSpanProcessor`), so the agent sees spans in the UI instantly instead of after the batch schedule delay. The gate matches the env-origin `LMNR_DEBUG` check already used in `_init_debug_runtime`; a downstream context-armed run is not the origin and configures its own transport. Cross-language parity with TS `disableBatchForDebug` in `laminar.ts`.
- **Debug-session notes are session BLOCKS, not env vars — the `LMNR_DEBUG_RUN_NOTES` / `LMNR_DEBUG_RUN_NOTES_FILE` vars and `config.py::resolve_debug_run_note` / `ROLLOUT_NOTE_KEY` are DELETED.** A debug session renders as an ordered list of blocks (`trace` / `evaluation` / `text`); a note is a standalone `text` block attached post-factum via `RolloutSessions.add_block` (`POST /v1/rollouts/{session_id}/blocks`, e.g. from `lmnr-cli debug session add-note`), keyed by session id rather than stamped onto trace metadata at init. `add_block` treats a 404 as best-effort (warn + return None) unless `fail_on_not_found=True` (CLI callers pass it so exit 0 means the block landed); `list_blocks` (`GET .../blocks`) returns the blocks in creation order. The block shapes live in `sdk/types.py` (`SessionBlock`, `SessionBlockType`, `TraceBlockContent` / `EvaluationBlockContent` / `TextBlockContent`) — kept parity with the TS SDK's `@lmnr-ai/types` `session-block.ts`. Evaluations link to the session via `evaluations.py::_with_debugger_session_metadata`, which auto-stamps `rollout.session_id` (`SESSION_METADATA_KEY`) into the eval-init metadata when a debug runtime exists, so a plain `LMNR_DEBUG=1 <run-your-eval>` groups the eval under the current session; the backend writes the `evaluation` block from that key at eval creation.
- Debug tests (`tests/test_debug_*.py`) are isolated unit tests that do NOT need VCR cassettes — they use `monkeypatch` for env vars and `_FakeSpan`/`_FakeRuntime`/`_RecordingCache`/`_SpyDebugClient` doubles. `replay.py` does a function-local `from lmnr.sdk.laminar import Laminar` inside `cache_outcome_for`/`acache_outcome_for` to avoid the `laminar` ↔ `debug` import cycle.
- **The replay cache keys off `gen_ai.input.messages`, which app-server PREFERS over the legacy `gen_ai.prompt.{N}.*` reconstruction.** In `app-server/src/traces/spans.rs::parse_and_enrich_attributes`, the `gen_ai.input.messages` branch (and `gen_ai.output.messages`) OVERWRITES whatever the `gen_ai.prompt.{N}.*` / `ai.prompt.messages` handlers put on `self.input`/`self.output`. So a provider that emits ONLY the legacy per-index attrs has no hashable input for the cache. Both the chat-completions and LiteLLM-responses paths already stamp `gen_ai.input.messages`; the OpenAI **Responses-API** wrapper historically stamped only `gen_ai.prompt.{N}.*`, so it was invisible to replay until we added `build_genai_input_messages` / `build_genai_output_messages` in `instrumentation/openai/v1/responses_wrappers.py` (stamped from `set_data_attributes`, alongside — not replacing — the legacy attrs that the existing `test_responses.py` asserts on).
- **OpenAI Responses-API replay is wired differently from chat/litellm because its instrumentation calls `wrapped()` BEFORE any span exists** (it accumulates a module-level `responses[response_id]` `TracedData` and only mints the span post-hoc when `status=="completed"`). The chat path opens the span in `safe_start_span` and hands it to the rollout wrapper; the responses path can't. So `responses_wrappers.py` keeps its OWN replay orchestration (`_replay_response_sync` / `_replay_response_async`, gated on `_replay_enabled() and not kwargs.get("stream")`) that: opens the span up front, stamps `gen_ai.input.messages` via `build_genai_input_messages(process_input(kwargs["input"]))`, probes `cache_outcome_for`/`acache_outcome_for`, and on HIT calls `OpenAIRolloutWrapper.cached_response_to_responses(outcome.cached)` (in `instrumentation/openai/rollout.py`) to rebuild an `openai.types.responses.Response`, then `set_data_attributes` + `mark_span_cached` + `span.end()`. On MISS/LIVE it runs `wrapped()` live on that same span and records `lmnr.sdk.raw.response`. **Hash parity is guaranteed BY CONSTRUCTION** because the recording run (`set_data_attributes`) and the replay pre-stamp (`_open_replay_span`) build `gen_ai.input.messages` through the identical `build_genai_input_messages(process_input(...))` chain, and app-server stores that string verbatim and re-hashes it. `Responses.retrieve` shares the same wrapper but carries no `input`, so the cache probe returns None and it falls through to live. **Streaming responses are intentionally NOT replayed** (`responses_wrappers.py` still has no streaming span support at all). Only `OpenAIRolloutWrapper.cached_response_to_responses` lives in `rollout.py`; there is no `wrap_responses` there because the responses instrumentation owns its orchestration. Tested in `tests/test_debug_replay_openai_responses.py`.
- **A debug run propagates its coordinates downstream as ONE nested `debug` block of the serialized `LaminarSpanContext`** (`DebugContext` in `sdk/types.py`: `enabled`, `session_id`, `replay_trace_id`, `cache_until`). `LaminarSpanInterfaceMixin.get_laminar_span_context()` stamps it via the module-local `_current_debug_context()` (reads `get_runtime()`, best-effort → `None` when debug is off; only `enabled=True` blocks are ever produced — we are the sole producer). `LaminarSpanContext.deserialize` parses it (accepting camelCase + snake_case; `session_id`/`replay_trace_id` normalized to hyphenated UUID via `_normalize_uuid_like`, `cache_until` kept VERBATIM as the needle; a malformed id drops to `None` rather than raising). Backward-compatible: old SDKs never send it, the block is usually absent in production. This is a **cross-language parity surface** — keep `DebugContext` / `build_debug_config_from_context` line-comparable with TS `deserializeDebugContext` / `buildDebugConfigFromContext`.
- **A downstream service arms — and then REFRESHES — its debug runtime from that propagated block**, so it joins the upstream run regardless of how its spans originate. `Laminar._arm_debug_runtime_from_context(debug)` is called from BOTH `start_span` and `start_as_current_span` right after `_parse_parent_span_context` — i.e. deep in span creation, BEFORE any caching instrumentation consults the runtime, but AFTER the context is parsed. **The coordinates carried in the block (`session_id` / `replay_trace_id` / `cache_until`) are DYNAMIC, not first-wins**: a long-lived downstream service handling many requests must follow each request's context, not freeze on the very first one it ever saw. So the **stable transport (the two retained clients) is separated from the dynamic coordinates** — the clients are built once on first arm and reused; only the coordinates move per request. The arming logic: (a) no runtime yet → build one from the context (latch `_initialized`); (b) a `local_origin=True` (env) runtime exists → env config wins, leave it untouched (the local process owns the run; a propagated context must NOT hijack it) — `_arm_debug_runtime_from_context` bails before any allocation when `existing.local_origin`; (c) a `local_origin=False` (context-armed) runtime exists → REUSE its `client`/`async_client` and `DebugRuntime.update_context_config(config)` refreshes only the dynamic coordinates in place (`local_origin` / `session_minted` are run IDENTITY and never change; `DebugConfig` is frozen so the whole config is rebuilt and the reference swapped under the GIL). `init_debug_runtime_from_context` returns a `(runtime, session_changed)` tuple — `session_changed` is True when the refresh moved to a different session id (or a fresh runtime was just built). The caller (re-)registers the session + re-stamps `rollout.session_id` (onto `__global_metadata` AND `CONTEXT_METADATA_KEY`) ONLY when `session_changed` — a steady stream of requests on the SAME session must not spam the backend or rewrite metadata on every span. `init_debug_runtime_from_context` does NOT latch `_initialized` when the block is absent/unarmed, so a later valid context can still arm. The from-context config is `local_origin=False`: a downstream run reuses the upstream session and may consult the cache, but does NOT open the browser, log the session URL, or register an exit-time pointer hook (the origin owns those). Because the from-context path has no access to `initialize()`'s args, `initialize()` captures `base_url`/`http_port` into `Laminar.__base_url_for_debug` / `__http_port_for_debug` (set unconditionally, even when local debug is off) so it can build its own clients on first arm. The `_init_lock` still serializes the build/refresh so concurrent worker threads don't both build a runtime (loser's clients would leak) or interleave a refresh. **Cross-language parity** — mirrors TS `_armDebugRuntimeFromContext` / `initDebugRuntimeFromContext` / `DebugRuntime.updateContextConfig` (TS holds ONE `rolloutSessions` handle reused via the `rolloutSessions` getter; Python holds the two clients). Tested in `tests/test_debug_runtime.py` (`test_update_context_config_*`, `test_init_from_context_refreshes_context_runtime_reusing_clients`, `test_init_from_context_never_overrides_env_origin_runtime`, `test_arm_from_context_refreshes_session_on_new_context`, `test_arm_from_context_reuses_clients_on_same_session`).
- **A context runtime that races ahead of `_init_debug_runtime` is preempted when `LMNR_DEBUG` is set.** `initialize()` flips `__initialized = True` BEFORE calling `_init_debug_runtime`, and the span funnels gate only on `is_initialized()` — so in that window a span carrying a propagated `debug` block can arm a `local_origin=False` context runtime. `init_debug_runtime` is idempotent, so it would then return THAT runtime; its clients differ from the env-built ones, the `runtime.client is not client` guard fires, and `_init_debug_runtime` bails — leaving the local `LMNR_DEBUG` run with NO session registration, browser open, or pointer hook. Per the PR's "env-origin config owns the process" rule, `_init_debug_runtime` checks `get_runtime()` right after the `LMNR_DEBUG` gate: if a non-`local_origin` runtime exists, it closes that runtime's orphaned clients and calls `reset_debug_runtime()` so the env path below builds a fresh `local_origin=True` runtime. The `runtime.client is not client` guard remains as a defensive fallback for the residual race between the discard and the rebuild. This guard is Python-only on this surface — TS `_initDebugRuntime` instead *rebinds* a pre-armed runtime's rollout-sessions handle (`rebindRolloutSessions`) because a TS from-context runtime can be armed even BEFORE `initialize()` (TS span funnels have no init guard). Maintainer endorsed the guard on the PR ("super unlikely? But we can guard against that, yes"). Tested in `tests/test_debug_runtime.py` (`test_init_preempts_context_runtime_when_env_debug_set`).
- **The one-time browser open is gated on the resolved config, not env vars.** `DebugConfig` gained `local_origin` (origin vs inherited) and `session_minted` (fresh vs reused/provided session id); `DebugRuntime.should_open_browser` is `local_origin and session_minted`. `_init_debug_runtime` now opens the browser on `if runtime.should_open_browser:` (was `if not os.getenv("LMNR_DEBUG_SESSION_ID"):`) — a reused session id (continuation/replay) or a context-armed downstream run no longer reopens the browser. Tested in `tests/test_debug_config.py` (DebugContext parse, from-context builder, local_origin/session_minted, nested-debug `LaminarSpanContext` parse).
- **Reconstructed cached Responses MUST get a UNIQUE id** (`cached_response_to_responses` builds `id=f"cached_{uuid4().hex}"`, NOT a constant `"cached"`). The Responses instrumentation keys its module-level `responses[response_id]` accumulator by id, and `_build_traced_data` prefers the *stashed* `existing_data["input"]` over the live `kwargs["input"]`. With a constant id, the FIRST cached HIT's (shortest) input is stashed under `"cached"`, then every later cached HIT collides on that key and `set_data_attributes` RE-STAMPS `gen_ai.input.messages` with that stale input — overwriting the correct value `_open_replay_span` already set. Symptom: cached Responses spans 2..N all show only span 1's input history (missing tool calls / function_call_output). Note this is the `gen_ai.input.messages` attribute being clobbered, NOT the legacy `gen_ai.prompt.N.*` path — dropping the legacy path does NOT fix it. The chat-completions path is unaffected (it serves the cached response directly and never re-stamps from the accumulator). Pinned by `test_cached_genai_responses_have_unique_ids`.

## Span payload size limit

- `MAX_MANUAL_SPAN_PAYLOAD_SIZE` (10MB, `opentelemetry_lib/tracing/span.py`) caps manual `set_input` / `set_output`. An oversized payload is **truncated to the limit with a trailing `TRUNCATION_SUFFIX` (`...[Laminar: truncated]`)**, NOT replaced — the old behavior swapped the whole value for `"Laminar: input too large to record"`, which discarded everything (LAM-2050). The recorded value is deliberately no longer valid JSON; the frontend renders it as a string. Keep `_truncate_payload` line-comparable with TS `truncateSpanPayload` in `packages/lmnr/src/utils.ts` (same constant, same suffix).
- The limit only guards the MANUAL API. Auto-instrumentation attributes (`gen_ai.input.messages`, the daytona/langfuse `SPAN_INPUT` writers) are not truncated — they set the attribute directly rather than going through the mixin.
- **The SDK limit (10MB) is larger than app-server's default `HTTP_PAYLOAD_LIMIT` (5MB)**, so a payload can pass truncation and still 413 on export. Truncating is not a guarantee of ingestion; it only stops one span from being unboundedly large.

## Logging (`sdk/log.py`)

- **`get_default_logger` attaches AT MOST ONE handler per logger name.** `logging.getLogger(name)` returns the same logger object on every call, so the previous unconditional `addHandler` stacked a handler per call and emitted each message once per handler. Callers legitimately call it repeatedly — most importantly `LaminarSpan.__init__`, so the duplicate count grew with the number of spans a run created (a 5-span run logged one warning 5×). The guard marks its own handler with the `_lmnr_default_handler` attribute and skips if one is already present; a user's own handler is never touched or removed. Pinned by `tests/test_logger_handlers.py`.
- **Never hand-roll `logging.getLogger(...) + addHandler` — route through `get_default_logger`.** Both `Laminar._initialize_logger` and `TracerWrapper._initialize_logger` did, which duplicated every log line across `initialize()`/`shutdown()` cycles.
- **Keep `propagate=False` (the helper's default) everywhere.** Because we attach our OWN handler, propagating makes every record emit twice once the host app has a root handler (`logging.basicConfig()`) — the same duplication this section exists to prevent. Do NOT pass `propagate=True` to make a `caplog` assertion work: `caplog` only sees records that reach the root, so the test should `monkeypatch.setattr(logger, "propagate", True)` for its own scope instead (see `tests/test_debug_runtime.py::test_init_logs_debugger_url_when_project_id_returned`). An earlier pass did the opposite and Bugbot caught the reintroduced double-emit on PR #317; `tests/test_logger_handlers.py::test_our_loggers_do_not_propagate` now pins it.
- **The TS SDK does NOT have this bug and needs no equivalent guard**: `initializeLogger()` returns a fresh independent pino instance per call rather than mutating a shared registry, so per-instance/per-call construction (`processor.ts`, `v7-integration`, temporal interceptors) is harmless there.

## HTTP error reporting

- **Never assume an error body is JSON.** app-server returns PLAIN TEXT for payload-limit (413) rejections and its own `ResponseError` bodies, and proxies can return HTML — so `response.json()` raises on the error path. Route every non-2xx body through `describe_response` (`sdk/utils.py`), which renders `[<status>] <body>`, handles `None`, labels an empty body, and truncates at `MAX_ERROR_BODY_CHARS` so a large body can't flood logs.
- `client/synchronous/resources/evals.py` and its async mirror must stay in lockstep — every error-message change needs the same edit in both files. This drifts easily (Bugbot caught an async-only raw `{response.text}` on PR #317 after the sync twin was converted), so `tests/test_413_error_reporting.py::TestSyncAsyncLockstep` compares the two modules' sources via `inspect.getsource`: one test fails on ANY raw `{response.text}` interpolation, the other asserts both mirrors raise an identical set of error messages. Prefer extending those guards over hand-diffing the files.
- `Evals._retry_save_datapoints` halves `max_data_length` on each 413. Its `length == 0` branch can be reached BEFORE any request is made (with a small `initial_length`), so `response` must be initialized to `None` and reported via `describe_response` — dereferencing it there is an `UnboundLocalError`. Pinned by `tests/test_413_error_reporting.py`.
- A 413 on the OTLP span-export path is logged by **opentelemetry-sdk's own exporter**, not Laminar (`LaminarSpanExporter` just delegates). The only lever on that message is the server's response body, so improving it is an app-server change — see the payload-too-large section in `/repos/lmnr/CLAUDE.md`.

## Span batching / export

- **`LaminarSpanProcessor` is a `SpanProcessor` wrapper, not a batcher.** It owns the path bookkeeping + attribute stamping and delegates the actual buffering to `self.instance`: `SimpleSpanProcessor` when `disable_batch=True`, `SizeLimitedBatchSpanProcessor` when `flush_by_size=True`, and the plain upstream `BatchSpanProcessor` otherwise. `disable_batch` wins over `flush_by_size`. Both construction sites (`__init__` and `force_reinit`) go through `_new_batch_processor()` so the two must never drift — `force_reinit` silently dropping a limit *or switching transports* is the failure mode this centralization prevents.
- **`SizeLimitedBatchSpanProcessor` adds a THIRD flush trigger to OTel's two, and it is OPT-IN** via `Laminar.initialize(flush_by_size=True)`. Upstream `BatchSpanProcessor` flushes on `max_export_batch_size` items OR `schedule_delay_millis` elapsed; neither bounds the payload, so a few large GenAI spans (whole prompts + completions as string attributes) can build an export the backend rejects. `max_export_batch_size_bytes` (default `DEFAULT_MAX_EXPORT_BATCH_SIZE_BYTES` = 32 MiB) flushes the buffer when the span being ended *would* push it over, then enqueues that span as the start of a fresh batch. **The default is restated in prose in three places — this file, the `Laminar.initialize` docstring, and the overshoot arithmetic in `on_end`'s comment — so changing the constant means updating all three** (a stale 16 MiB in those spots is what Bugbot flagged on PR #318). `max_export_batch_size_bytes` is **ignored without the flag** — passing it alone must not silently switch transports (pinned by `test_size_limit_is_ignored_without_the_flag`). The full option chain is `Laminar.initialize(...)` → `TracerManager.init` → `TracerWrapper.__new__` → `LaminarSpanProcessor` → the batch processor; a new export knob must be threaded through all five or it is silently ignored.
- **The size flush normally runs on this processor's OWN background thread (`LmnrSizeLimitedSpanFlush`), not on the thread that ended the span.** Upstream's worker cannot be reused for it: `BatchProcessor._should_export_batch` returns False for a queue shorter than `max_export_batch_size` under `EXPORT_WHILE_BATCH_EXCEEDS_THRESHOLD`, the strategy an `emit`-interrupted sleep selects, so merely waking it does nothing. An earlier revision called `force_flush()` inline from `on_end` and load testing measured a p99 of ~664ms — every thread tripping the limit serialized on OTel's `BatchProcessor._export_lock`.
- **Two cases still export INLINE, and both are load-bearing** (`on_end`): (a) a previous flush request has not been picked up yet — the producer is outrunning the network and this backpressure is the only thing bounding the buffer, without which the export size is governed by `max_export_batch_size` instead; (b) the span is at least half the limit by itself, since an async flush **cannot exclude the span that triggered it** (`on_end` enqueues before the flush thread wakes), so a large span would ride along and materially overshoot. The half threshold bounds any export at 1.5x the limit.
- **`_at_fork_reinit` must replace EVERY lock and Event, not just some.** `fork` clones only the calling thread, so any lock another thread held at fork time is inherited permanently locked with nobody left to release it. `on_end` acquires `_pending_size_lock` before it could ever notice the pid changed, so a lazy "respawn if pid differs" check in `on_end` **deadlocks instead of recovering** — verified: the child hangs forever on its first span. Registered via `os.register_at_fork(after_in_child=...)` (same mechanism upstream uses) with a `weakref.WeakMethod`, because fork handlers cannot be unregistered and must not keep a dead processor alive. Pinned by `test_forked_child_can_still_flush_with_locks_held_at_fork`, which hangs if the handler is removed.
- **The running byte total is an estimate that resyncs on an observed-empty queue** (`if not self._batch_processor._queue: self._pending_size_bytes = 0`). The worker drains the buffer on its own schedule without notifying us, so any counter we keep drifts: over-counting after a partial drain, under-counting when a concurrent emitter resyncs mid-`on_end`. Both self-correct at the next resync and only shift *when* a flush happens, never *whether* spans are exported — do not try to make this exact by tracking per-span sizes through the deque, which would mean reimplementing `BatchProcessor`.
- **String sizes go through `utf8_size`, NOT `len()` — `len()` counts code points and undercounts CJK ~3x, Cyrillic/Arabic ~2x, emoji ~1.4x.** `utf8_size` takes an O(1) `str.isascii()` fast path (CPython caches the flag on the string object, so it does NOT scale with length — verified flat at 10.4ns from 100 to 1M chars) and returns `len()` there, exact and free for the common case.
- **Above `_UTF8_SAMPLE_BUDGET` (1024 chars) `utf8_size` encodes a STRIDED sample (`value[::step]`), never a prefix.** Prefix sampling is wrong for this data specifically: `gen_ai.input.messages` opens with ASCII JSON scaffolding (`[{"role":"system","content":"`) before reaching non-ASCII content, so a prefix probe reports near-ASCII sizes for a CJK payload (measured −64.5%, i.e. no better than the bug being fixed). Striding lands within ~2% worst case at ~5us on an 80 KB value, versus 40–80us to encode it outright, and never reallocates the whole string. Pinned by `test_utf8_size_is_within_five_percent_of_the_real_encoding` (parametrized across scripts, including both prefix-adversarial layouts).
- **`utf8_size` MUST encode with `errors="replace"`.** Attribute values can contain lone surrogates (upstream JSON decoding produces them) and a strict `.encode("utf-8")` raises `UnicodeEncodeError` on those. This runs inside `on_end`, so raising would break span export for the whole batch. Verified that such a string does reach span attributes intact. Pinned by `test_utf8_size_survives_lone_surrogates`, which fails with `errors="strict"`.
- **`approximate_span_size` is still deliberately an underestimate** in the other dimensions: non-string values counted a flat 8 bytes, no protobuf framing / ids / timestamps. That is safe by design — if most spans are small the item-count or schedule-delay trigger fires first; the size trigger only needs to be accurate for spans dominated by big string attributes, which is what `utf8_size` delivers.
- **When `on_end` latency regresses, the cause is the export, never the size bookkeeping lock.** Measured under an 8-thread stress test with a 20ms export against the old inline implementation: `on_end` p99 ~170ms, of which `force_flush` was 99.9% and the `_pending_size_lock` wait was ~0.2us (0.00%). The contention is OTel's own `BatchProcessor._export_lock` (p50 wait ~148ms), which serializes every concurrent `force_flush`, so N threads queue behind N sequential exports. That is what the background flush thread exists to avoid. Do NOT "optimize" the size-aggregation lock — it has never been the bottleneck.
- **`LaminarSpanProcessor(max_export_batch_size=...)` was previously typed `int = 64`, but the 64 never applied.** Every caller in the chain defaults to `None` and passed it straight through, so `BatchSpanProcessor` fell back to OTel's own env-var default of **512** — i.e. the "we lowered 512 to 64" claim in the `initialize` docstring was not true in practice. The default now lives in `DEFAULT_MAX_EXPORT_BATCH_SIZE` and is applied via `or` inside `LaminarSpanProcessor.__init__`, where a `None` from any upstream layer actually resolves. Pinned by `test_default_is_the_plain_upstream_batch_processor`, which asserts the 64 on the DEFAULT (non-`flush_by_size`) path — that is the path the bug lived on. `sdk/evaluations.py` keeps its own `MAX_EXPORT_BATCH_SIZE = 64` as an explicit non-None default for eval runs.
- **`tests/test_batch_processor.py` builds its own `TracerProvider` + recording exporter instead of using the session-scoped `span_exporter` fixture.** Isolating the byte trigger requires setting `max_export_batch_size` high (1000) and `schedule_delay_millis` to 10 minutes so the other two triggers cannot fire; the shared fixture initializes with `disable_batch=True` (`SimpleSpanProcessor`) and has no batching to test. An autouse fixture shuts down every processor the module builds — each starts a daemon worker thread that would otherwise survive the whole session and keep exporting on its own schedule.
- **`test_litellm.py::test_litellm_completion_activates_span_for_otel_callbacks` is flaky at roughly 3-in-6, independent of any batching change** (verified by running the full suite six times on a clean tree and six times with the batch-processor work applied — identical rates). It fails with `KeyError: 'span_id'`, i.e. litellm's success callback never fired. Do not chase it as a regression from an export/batching change; a small sample will mislead you into thinking your branch caused it.

## Span attribute serialization (`json_dumps` / bytes)

- **`json_dumps` (`sdk/utils.py`) is the single serialization boundary for span attributes, and it OWNS bytes encoding.** `default_json` encodes `bytes`/`bytearray` as **STANDARD** base64 (`+`/`/`). Do NOT switch it to `base64.urlsafe_b64encode`: consumers (our frontend, customer tooling) decode with `base64.b64decode`, which defaults to `validate=False` and **silently DROPS** out-of-alphabet characters instead of raising — every following byte shifts, so a PNG still parses its header and reports correct dimensions while the pixels are garbage. That silent-corruption property is why the bug (LAM-2052) cost a customer a day of debugging; it never surfaces as an exception. Without the bytes branch, bytes fall through to `str(o)` and land in the span as the useless repr `"b'\xfb\xef'"`.
- **Therefore: never serialize a pydantic model for a span attribute with `model_dump(mode="json")` or `model_dump_json()` when the model can carry bytes.** Dump `mode="python"` and let `json_dumps` do the encoding. `mode="json"` applies the model's own `ser_json_bytes` setting — and **google-genai sets `ser_json_bytes="base64"`, which is pydantic's URL-SAFE alphabet**, so json mode emits `-`/`_` and bypasses our encoder entirely. In `google_genai/utils.py` this is what `model_to_json_safe_dict` exists for; the affected attributes were `gen_ai.input.messages`, `gen_ai.output.messages`, and `lmnr.sdk.raw.response`, and the bytes fields are `Blob.data` and `Part.thought_signature`. openai / anthropic base models set no `ser_json_bytes`, so they were never affected.
- **Keeping `mode="json"` was investigated and is not possible** — don't re-try these: pydantic exposes no standard-base64 setting (`ser_json_bytes` accepts only `"base64"`, which IS the URL-safe one, plus `"hex"` and `"utf8"`, and `utf8` raises `UnicodeDecodeError` on real binary); a per-call `context=` does not reach `ser_json_bytes`; `TypeAdapter(config=...)` is rejected outright for BaseModel types (`PydanticUserError`); `model_dump(fallback=...)` only fires for types pydantic can't serialize, so it never sees `Blob.data`; and repairing the alphabet after the dump would have to guess which strings came from bytes — a blind `-`→`+` / `_`→`/` swap corrupts ordinary text (`"well-known B-tree"` → `"well+known B+tree"`) and even JSON keys.
- **`mode="python"` is also strictly MORE robust than `mode="json"` here, not a tradeoff.** For the `Any`-typed `function_call.args` / `function_response.response` fields, json mode RAISES `PydanticSerializationError` on any value it doesn't recognise (a `Mapping` that isn't a `dict`, a custom object, `range`, a lambda) — and because the callers are `@dont_throw`, that silently dropped the ENTIRE `gen_ai.input.messages` attribute, every message in the conversation, not just the offending value. Python mode passes the value to `json_dumps`, which degrades that one leaf. Pinned by `test_an_unserializable_tool_value_does_not_drop_the_conversation`.
- **The one real hazard of python mode is `str(o)` on a dict-like/list-like**, which yields a Python repr with SINGLE quotes (`"{'a': 1}"`) — not JSON, unparseable by any consumer. `default_json` therefore has `collections.abc.Mapping` → `dict(o)` and `collections.abc.Sequence` → `list(o)` branches BEFORE the `str(o)` fallback (excluding `str`/`bytes`/`bytearray`, which are Sequences and must not explode into char lists). Pinned by `test_json_dumps_dict_like_objects_do_not_stringify_to_python_reprs`.
- Pydantic's base64 **validator** (`val_json_bytes="base64"`) accepts BOTH alphabets, so the debug-replay path (`GenerateContentResponse.model_validate_json` on `lmnr.sdk.raw.response`) round-trips old URL-safe spans and new standard ones alike — the fix needed no migration. The frontend's `toStandardBase64` (`frontend/lib/utils.ts`) is a no-op on standard base64, so it stays harmless.
- **orjson aborts the ENTIRE document on an unencodable mapping key**, so one bad key used to collapse a whole attribute to `"{}"`, losing every sibling message. `OPT_NON_STR_KEYS` only covers a fixed set of scalar key types; tuples/bytes/arbitrary objects raise. `json_dumps` retries once through `_stringify_dict_keys` for this. It's reachable from user data: `FunctionResponse.response` is typed `dict[str, Any]`, so nested keys are unvalidated (and google-genai itself will happily send a tuple key, stringified). **The retry must only coerce keys orjson CAN'T encode** (`_ORJSON_NATIVE_KEY_TYPES`): orjson renders the ones it handles differently from `str()` (`None` → `"null"`, `True` → `"true"`, datetimes → RFC 3339, enums → their value), so coercing them would make a key's name depend on whether some unrelated sibling key happened to force the retry. Pinned by `test_json_dumps_key_names_do_not_depend_on_the_retry_path`. **`default_json` and `_stringify_dict_keys` MUST agree on what counts as a container, so both route through `_unwrap_container` — add a new container type there, once, never to one of them.** A bad key nested inside something `default_json` opens but the retry walker skips survives the retry, fails the second dump too, and takes every sibling field down with it. This diverged three times during LAM-2052 review (builtins only → missing `Mapping` → missing `pydantic.BaseModel`), each time silently collapsing a whole span attribute to `"{}"`; the `BaseModel` case is reachable because `part_to_dict`'s dict branch deliberately leaves a nested model un-dumped. `str`/`bytes`/`bytearray` are `Sequence`s and must NOT be opened (they'd explode into per-character lists), so both callers check them first. Pinned by `test_unwrap_container_is_the_single_source_of_truth_for_containers` plus the two `test_json_dumps_recovers_bad_keys_nested_in_*` tests.
- **`json_dumps` NEVER raises — it returns `"{}"`.** So a `try/except` around it is dead code; check the returned value instead. This matters for `lmnr.sdk.raw.response` specifically: app-server's replay cache PREFERS a non-empty raw response over reconstructing from `gen_ai.output.messages` (`app-server/src/debugger/mod.rs`), so stamping `"{}"` would shadow the usable fallback and make every cache HIT rebuild an empty response. `_set_raw_response_attribute` skips the attribute instead.

## Claude Agent instrumentation — settings.json outranks process env

- **Claude Code's settings `env` block wins over the subprocess environment.** Rewriting `options.env["ANTHROPIC_BASE_URL"]` is NOT sufficient to route the CLI through our proxy: a user with `ANTHROPIC_BASE_URL` in `~/.claude/settings.json` talks straight to their upstream and the proxy sees zero traffic, so the trace has only DEFAULT spans and no `anthropic.messages` LLM span (lmnr-ai/lmnr#2167). Verified empirically against the bundled CLI (2.1.81 and 2.1.220): with the base URL in user settings, 2/2 requests went to the settings URL and 0 to the process-env URL. The same precedence applies to `ANTHROPIC_API_KEY`.
- **The fix is the flag-settings layer (`--settings`), which outranks user, project, AND local settings.** `build_proxy_flag_settings` (utils.py) builds the JSON that `apply_settings_proxy_override` (wrappers.py) assigns to `options.settings`; the Claude Agent SDK maps that to `--settings`. Verified: with `--settings` injected, 0 requests hit the settings URL and 2 hit the proxy, for all three lower layers. The user's files on disk are NEVER modified.
- **Settings layers merge PER KEY, they do not replace wholesale.** So keys we omit from the flag layer keep their lower-layer value — which means a redirecting key (`HTTP_PROXY` / `HTTPS_PROXY` / `ANTHROPIC_FOUNDRY_RESOURCE`) must be **blanked to `""`**, not popped. Blank them when present in the settings layers, the flag layer, **or `os.environ`** — the flag layer is the only place we can override a value for the subprocess, so a key that exists only in the real env still needs blanking there.
- **`ANTHROPIC_FOUNDRY_RESOURCE` must be blanked whenever the Foundry base URL is pinned, regardless of where the resource lives.** The CLI treats base URL and resource as mutually exclusive and **hard-fails** (`API Error: baseURL and resource are mutually exclusive`) when both are live — it does NOT silently prefer one. Verified against the real bundled CLI. Python already pops the resource from `os.environ` and `options.env`, but the flag layer needed the same blanking for the case where Foundry is enabled via settings and the resource sits in the process env. That blanking happens in the SINGLE `PROXY_NEUTRALIZED_ENV_KEYS` loop, whose `key in os.environ` check is exactly what covers the process-env-only resource — do NOT add a second clear inside the `PROVIDER_BASE_URL_ENV_KEYS` pass. An earlier iteration had both; the in-loop one only differed by emitting `ANTHROPIC_FOUNDRY_RESOURCE: ""` when Foundry was enabled and the resource existed NOWHERE, and the CLI behaves identically whether that empty key is present or absent (verified: same Azure-credential error either way), so it was pure redundancy. Verified: a corporate `HTTPS_PROXY` in user settings captured all 3 connections until it was blanked in the flag layer. The merge behavior is also what lets the user's own `ANTHROPIC_API_KEY` / `ANTHROPIC_MODEL` survive while we rewrite only base URLs — do NOT copy the whole settings env into the flag layer.
- **`HTTP_PROXY` / `HTTPS_PROXY` must be handled in BOTH cases (`PROXY_ENV_KEYS`).** Claude Code reads the lowercase `http_proxy` / `https_proxy` too and PREFERS them. Verified against the bundled CLI: with a lowercase `https_proxy` in settings and only the uppercase key blanked in the flag layer, all 3 connections went to the corporate proxy and 0 to ours; blanking the lowercase key too flipped it to 2/0. The tuple covers the neutralized list, the upstream-settings exclusion list, the `resolve_target_url_from_env` steps 1–2 lookups, and the three loops that strip proxy vars from the subprocess env — keep all of them keyed off `PROXY_ENV_KEYS` rather than re-listing the uppercase pair.
- **Every key the proxy-var pops touch MUST also be snapshotted.** `setup_proxy_env` (os.environ) and `snapshot_options_env_for_proxy` (options.env) both build their snapshot from `PROXY_ENV_KEYS`, because the pop loops use that same tuple — listing only the uppercase pair while popping all four silently destroys a user's lowercase `http_proxy` / `https_proxy` for the rest of the process (or, on a failed connect that restores `options.env`, for the retry). Keep the snapshot key list and the pop list keyed off the SAME constant.
- **`build_proxy_flag_settings` normalizes the caller's `options.settings` env through `_settings_env_block`, NOT a raw `dict(...)`.** A caller can pass JSON booleans / numbers (`{"env": {"CLAUDE_CODE_USE_FOUNDRY": true}}`), and those flow into `is_truthy_env` — which lowercases the value — so an uncoerced `bool` raised `AttributeError: 'bool' object has no attribute 'strip'` and aborted proxy setup. `is_truthy_env` is ALSO defensively type-checked (non-`str` → only literal `True` counts) so no future caller can crash the proxy on a stray type.
- **`is_truthy_env` accepts `1` / `true` / `yes` / `on`, case-insensitively — NOT just `"1"`.** Verified by probing the bundled CLI with `CLAUDE_CODE_USE_FOUNDRY` set to each value: `1`/`true`/`True`/`yes`/`on` all produce a Foundry-specific error (provider enabled), while `0`/`false`/`""` make a plain Anthropic call (disabled). This matters because the provider flag is what decides whether we pin a provider base URL: under the old `value == "1"` check, `CLAUDE_CODE_USE_FOUNDRY=true` + `ANTHROPIC_FOUNDRY_RESOURCE` blanked the resource (it is in `PROXY_NEUTRALIZED_ENV_KEYS`) without pinning `ANTHROPIC_FOUNDRY_BASE_URL`, stripping the only routing key and hard-failing the run. Note the debug-mode truthy set in `sdk/debug/config.py` is a SEPARATE list that happens to match — do not consolidate them; they track different upstreams.
- **An empty string is NOT treated as unset for `ANTHROPIC_BASE_URL`** — setting it to `""` in the flag layer does not fall back to the lower layer, it breaks auth ("Invalid API key"). Only blank the redirecting keys listed above; always write a real proxy URL for the base URL.
- **Only pin provider base URLs that are actually in play — but key off the provider's ENABLING FLAG, not just its base-URL key.** `build_proxy_flag_settings` pins `ANTHROPIC_{BEDROCK,VERTEX,FOUNDRY}_BASE_URL` when `CLAUDE_CODE_USE_{BEDROCK,VERTEX,FOUNDRY}` is truthy **or** the base-URL key is already set (see `PROVIDER_BASE_URL_ENV_KEYS`, which pairs each base URL with its flag). Keying only off the base-URL key is a bug: Foundry is commonly configured via `ANTHROPIC_FOUNDRY_RESOURCE` with **no** base-URL key, so the resource would get blanked (it's in `PROXY_NEUTRALIZED_ENV_KEYS`) while no proxy base URL was written — stripping its only routing key and breaking the call instead of intercepting it. Writing all provider URLs unconditionally is the opposite error (hands a Bedrock URL to someone who never enabled Bedrock). Pinned by `test_flag_settings_pin_foundry_base_url_for_resource_only_setup` / `..._from_enabling_flag`.
- **`read_claude_settings_env` MUST honor `options.setting_sources`**, which gates which on-disk layers the CLI loads: `None` = all, a list = only those, `[]` = no filesystem settings at all. Verified against the real bundled CLI — a gateway in project settings got 2 requests with all layers loaded and 0 under `--setting-sources=user`. So reading a layer the CLI was told to ignore resolves an upstream the CLI never uses and points the proxy at an unintended host. The param threads through `resolve_target_url_from_env(setting_sources=...)`, `build_proxy_flag_settings(setting_sources=...)`, and `update_options_env_for_proxy`.
- **Read `options.setting_sources` DIRECTLY; do not try to mirror the SDK's private defaulting.** The field is documented public API ("When `None`, all sources are loaded"). The SDK ALSO narrows the CLI to `--setting-sources=user,project` whenever `options.skills` is set, but it does so inside the private `_apply_skills_defaults`, so replicating that would couple us to an internal that can change with no notice. We deliberately accept the looser assumption: with `skills` set we may over-read the `local` layer and resolve an upstream the CLI ignores. **That over-read is safe** — the flag layer (`--settings`) still pins every base URL to the proxy, so the CLI cannot reach a local-only gateway regardless. Verified against bundled CLI 2.1.220: with a gateway only in `.claude/settings.local.json` and `--setting-sources=user,project`, all requests went to the proxy and 0 direct. A previous iteration of this PR had an `effective_setting_sources()` helper for this; it was removed on review — do not reintroduce it.
- **Upstream resolution MUST also read the caller's own `options.settings` (the flag layer), via `flag_settings_env`.** That layer outranks every on-disk layer inside the CLI, and `build_proxy_flag_settings` overwrites its base URLs with the proxy moments later — so a gateway or `CLAUDE_CODE_USE_*` provider config that lives ONLY in `options.settings` was silently dropped and the proxy forwarded to `api.anthropic.com`. Precedence in `resolve_target_url_from_env` is `options.env` → `os.environ` → **flag settings** → on-disk settings. `flag_settings_env` handles both shapes (inline JSON / file path) and returns `{}` for anything unreadable, leaving the bail-out to `build_proxy_flag_settings`.
- **`resolve_target_url_from_env` reads settings LAST (after `options.env` and `os.environ`) as the proxy's upstream.** That ordering is deliberate and differs from the CLI's own precedence: we want the most specific caller-supplied upstream for forwarding, but the CLI itself will honor settings over process env — hence the separate flag-settings override. Pass `cwd=options.cwd` so project/local settings resolve against the session root, not the process cwd.
- **`HTTP_PROXY` / `HTTPS_PROXY` are deliberately EXCLUDED from the settings fallback** (`UPSTREAM_SETTINGS_EXCLUDED_ENV_KEYS`). They are transport-level forward proxies, not Anthropic API bases, and they sit at the TOP of the resolution order (steps 1–2, above every base URL) precisely so our proxy forwards through a corporate proxy when the process env demands it. Reading them from settings too would mean a user with BOTH a gateway and a corporate proxy in `~/.claude/settings.json` resolves the upstream to the *proxy*, so intercepted API calls get forwarded to a CONNECT proxy as if it were an API host and fail. The `options.env` / `os.environ` handling for these keys is unchanged (pre-existing behavior: a proxy var in the real env IS the target) — settings simply do not contribute them. Pinned by `test_settings_proxy_var_does_not_shadow_the_gateway` / `..._alone_falls_back_to_default` / `test_process_env_proxy_var_is_still_the_upstream`.
- **`options.settings` may be a JSON string OR a file path.** Anything we cannot FULLY read must be left untouched (return `None`) so the CLI can still resolve it with its own cwd — replacing it with a proxy-only JSON blob would silently drop all of the user's real settings for that run. "Cannot read" covers more than a missing path: an unreadable file (`OSError`), malformed JSON (a trailing comma the CLI may tolerate), and valid JSON that isn't an object all count. This is why `_load_settings_file` returns `dict | None` rather than defaulting to `{}`: the flag-settings builder must NOT confuse a failed read with a valid-but-empty `{}` file (the latter still gets the proxy). The on-disk settings LAYERS want the opposite ("absent → `{}`", carry on), so `read_claude_settings_env` applies `or {}` at its single call site — do NOT reintroduce a wrapper function for that, and do NOT make `None` the same as `{}` inside the loader. `apply_settings_proxy_override` returns a plain **`bool`** ("did I rewrite `options.settings`?") and the CALLER snapshots the previous value itself. An earlier iteration returned a one-tuple so restoration could tell "the original was `None`" from "we never touched it"; that distinction is real but the caller already holds the original, so the tuple was pure obfuscation — do not reintroduce it.
- **The SDK's `--setting-sources` default changed between versions and affects whether the bug reproduces.** claude-agent-sdk `0.1.50` always passes `--setting-sources ""` when `setting_sources is None`, which disables on-disk settings entirely and masks the bug. `0.2.128+` OMITS the flag unless `skills`/`setting_sources` is set (then defaults to `["user","project"]`), so the CLI loads all layers and the bug is live. The `--settings` fix works under both, so do not gate it on a version check.
- **`setup_proxy_env` (custom-transport path) must read the settings layers too, not just `os.environ`.** It decides which provider base URLs to pin from `CLAUDE_CODE_USE_{BEDROCK,VERTEX,FOUNDRY}`, and a user who keeps that flag — plus its credentials, e.g. `AWS_BEARER_TOKEN_BEDROCK` — in `~/.claude/settings.json` has NOTHING in the process env. Gating on `os.environ` alone therefore left `ANTHROPIC_BEDROCK_BASE_URL` unpinned and the CLI talked to Bedrock directly while the proxy saw zero traffic. This is the same class of bug as lmnr-ai/lmnr#2167, one layer down. The subprocess path was already correct (`build_proxy_flag_settings` / `resolve_target_url_from_env` consult `read_claude_settings_env`); only this function was missing it, which is why the fix threads `cwd` through from `wrap_transport_connect`. Pinned by `test_setup_proxy_env_pins_a_provider_enabled_only_in_settings`.
- **Do NOT copy credentials (`AWS_BEARER_TOKEN_BEDROCK`, `AWS_*`, `GOOGLE_APPLICATION_CREDENTIALS`, …) out of settings into the env or the flag layer.** It is never necessary: the CLI reads them from its own settings layer, and the only thing we must control is the base URL. Verified end-to-end against bundled CLI 2.1.220 with the token only in `~/.claude/settings.json` — the proxy saw `Authorization: Bearer <token>` on all requests and forwarded it upstream. Copying secrets into a `--settings` blob or the process env would widen their exposure (argv/env are readable by other processes) for zero benefit. Pinned by `test_setup_proxy_env_never_copies_credentials`.
- **A provider configured ONLY in a settings layer that `setting_sources` excludes is correctly invisible to us.** With `--setting-sources=` the CLI ignores `settings.json` entirely, so its credentials reach nothing and the run fails to authenticate — that is the CLI's own behavior under the caller's explicit isolation choice, NOT something the instrumentation should paper over by resurrecting those files. Do not "fix" this by reading layers the CLI was told to ignore.
- The TS SDK needed **no** equivalent change: it wraps only `query` (the subprocess path) and has no `setup_proxy_env`/global-env path, and its `buildProxyFlagSettings` already ORs `settingsEnv[useKey]` into the provider check. Verified with the exact settings-only Bedrock setup — base URL pinned to the proxy, token not copied, upstream resolved to `bedrock-runtime.us-east-1`.
- Note when linting Python here: the configured formatter is **ruff** (`[tool.ruff]`, 88 cols), so bare `flake8` (79 cols) reports ~150 pre-existing E501s across this instrumentation that are NOT regressions. Compare against the stashed baseline before believing a lint delta.
- The 6 pre-existing failures in `tests/test_instrumentations/test_claude_agent/test_proxy_{env,unit}.py` + `test_update_options_env.py` are **sandbox artifacts, not regressions** — this environment sets `CLAUDE_CODE_USE_BEDROCK=1` and `ANTHROPIC_BASE_URL`, which the tests read through `os.environ`. They fail identically on a clean checkout.
- **When mocking the proxy lifecycle, patch `wrappers.create_proxy_for_transport` / `wrappers.start_proxy` — NOT `proxy.*`.** `wrappers.py` does `from .proxy import create_proxy_for_transport, start_proxy`, binding those names into its own namespace at import time, so `patch.object(claude_proxy, ...)` is a silent no-op for anything the wrapper calls and a REAL proxy server starts. `run_server` then spawns a daemon `proxy-monitor-<port>` thread that GETs `/lmnr-internal/health` **every second for the rest of the session**; the conftest's `_cleanup_proxy` only stops the module-level singleton (default port 45667) and cannot see a per-transport instance, and the test's own `finally` never fires because its `mock_create`/`mock_start` assertions fail first. The autouse `no_leaked_proxy_monitor_threads` fixture in the claude_agent conftest now fails the leaking test by name — do not delete it, and do not "fix" a failure by stopping the assert instead of the proxy.
- **That leaked thread is what made `test_openai/traces/test_chat.py::test_chat_context_propagation` flake in `scheduled-tests.yml`** (~1 run in 8; it passes on re-run, which is why it read as a transient). The context-propagation tests patch `httpx.Client.send` GLOBALLY, so the stray health GET landed inside their spy and blew `assert_called_once` ("Called 2 times"), then hit VCR under `record_mode=none` and surfaced as a confusing `CannotOverwriteExistingCassetteException` for a request no test made. Failure depends only on whether a 1s tick falls inside a few-millisecond window, so a small local sample will NOT reproduce it — reproduce by asserting no `proxy-monitor-*` thread survives the claude_agent module instead. The 6 spy tests (chat / completions / embeddings, sync + async) now select their request via `single_request_to_path(spy.mock, "/v1/...")` rather than asserting on all global httpx traffic; **keep that pattern for any new spy test** — a global `assert_called_once` is a latent flake, and `call_args` (the LAST call) can silently be someone else's request.

## Anthropic instrumentor

- `messages.parse` (the structured-output helper introduced in `anthropic>=0.59`) is wrapped with the same `_wrap` / `_awrap` that wrap `messages.create` — the resulting span name is `anthropic.chat` and the attribute set is identical, plus `gen_ai.request.structured_output_schema`.
- Schema extraction lives in `span_utils._extract_structured_output_schema`. It handles: (1) `output_format=PydanticModel` via `model_json_schema()`, (2) `output_format=<any TypeAdapter-compatible type>` via `pydantic.TypeAdapter(...).json_schema()`, (3) raw-dict `output_format` (bare schema or `JSONOutputFormatParam`), and (4) `output_config={"format": {"type": "json_schema", "schema": {...}}}` on `messages.create`.
- `anthropic.lib.bedrock._beta_messages.Messages` does **not** expose `parse` (only regular + `beta.messages.messages` do). `_instrument` already swallows `ModuleNotFoundError` / `AttributeError` so the missing bedrock.parse attempt is a silent no-op.

## OpenAI Agents instrumentor

- **`set_status(StatusCode.ERROR)` alone does NOT mark a span as failed in Laminar.** app-server's `from_otel_span` (`app-server/src/traces/spans.rs`) never reads `otel_span.status`; the ONLY thing that sets `status = "error"` is the presence of an event named `exception` (`app-server/src/traces/utils.rs::prepare_span_for_recording`). So any instrumentation that reports failure must emit an `exception` event — `apply_span_error` (`openai_agents/span_data.py`) does both, and the event is the load-bearing half. The frontend error card reads `exception.type` (headline) and `exception.message` (body) off that event, so both attributes must be set. This applies to every instrumentor, not just this one.
- **`SpanError` is a `TypedDict`, so at runtime it is a plain dict** — `getattr(error, "message")` silently returns `None`. `apply_span_error` handles the dict and object shapes both. Its `message` is a short label ("Error running tool (non-fatal)", "Max turns exceeded"); the specifics live in `data`.
- **Cached input tokens are unavailable on `openai-agents` <= 0.0.x.** `_apply_usage` (`openai_agents/messages.py`) correctly reads `input_tokens_details` / `prompt_tokens_details` → `cached_tokens` and emits `gen_ai.usage.cache_read_input_tokens`, but early SDK versions have a 4-field `Usage` dataclass with no details objects, AND `models/openai_chatcompletions.py` hand-builds the generation span's usage as a 2-key `{"input_tokens", "output_tokens"}` dict. The data is destroyed before any `TracingProcessor` sees it — this is not an instrumentation bug, and the only fix at those versions is to read the raw provider response yourself.
- `OpenAIAgentsInstrumentor` declares `_instruments = ("openai-agents >= 0.7.0",)`, but the `TracingProcessor` ABC and the `set_trace_processors` / `GLOBAL_TRACE_PROVIDER` API are compatible far below that. To instrument a pinned older version, skip the version-gated instrumentor and register the processor directly: `set_trace_processors([LaminarAgentsTraceProcessor()])`. Replace rather than append — the SDK's default processor uploads to OpenAI's own tracing backend.

## google_genai emits the NATIVE Gemini shape (no OpenAI conversion)

- Messages are built by `content_union_to_dict` + `part_to_dict` into the native Gemini `{role, parts}` shape, and that is what the frontend parses (`frontend/lib/spans/types/gemini.ts`, wired into `process-messages.ts` — `GeminiContentSchema` requires `parts`). **Don't add an OpenAI-format conversion layer here.** An older pipeline that converted parts to OpenAI's `{type: "image_url", ...}` shape (`get_content` / `process_content_union` / `_process_part*` / `_process_image_item` plus the `ProcessedContentPart` / `ToolCall` / `ImageUrl` / `ImageUrlInner` / `ToolResult` models) was orphaned when the native shape landed in `5b43e75`, and is now DELETED — along with the two `Config` fields that gated it (`convert_image_to_openai_format`, `upload_base64_image`) and their `GoogleGenAiSdkInstrumentor.__init__` kwargs. `Config.exception_logger` is the only remaining field.
- It was deleted rather than re-enabled because it was **lossy**. `ProcessedContentPart` models only text / function_call / image_url / function_response, so `executable_code`, `code_execution_result` and `file_data` each fell through `_process_part`'s final `else` into `json.dumps(part_dict)` — becoming a text part holding a JSON blob of the entire part with every null field spelled out. It also dropped `thought` / `thought_signature` (which would break Gemini 3 thinking-signature round-trips) and `role`, and returned a bare part array with no `{role, parts}` wrapper, so the frontend's Gemini parser would not have matched it and every span would have fallen through to the generic renderer. Since `convert_image_to_openai_format` defaulted to `True`, enabling it would have changed span shape for every Gemini user, not just opt-ins.
- If a consumer ever needs image data URLs, transform the current `{role, parts}` output (map `inline_data` → a data-URL part, leave every other part type structured) rather than reviving that pipeline.

## Evaluation trace type propagation

- `_evaluate_datapoint` in `evaluations.py` must set `trace_type=TraceType.EVALUATION` on the isolated context (via `set_association_prop_context`) **before** starting the root evaluation span. Without it, the `LaminarSpanProcessor.on_start()` handler has no `CONTEXT_TRACE_TYPE_KEY` in `parent_context` for child spans (executor, evaluator), so they export without `lmnr.association.properties.trace_type` and the app-server classifies the trace as `DEFAULT`.

## deepagents instrument

- `Instruments.DEEPAGENTS` is auto-enabled when `deepagents` is installed. When auto-enabled, `LANGCHAIN` and `LANGGRAPH` are auto-removed from the default instrument set (see `_DEEPAGENTS_NOISE_CONFLICTS` in `tracing/instruments.py`) — the LangSmith-style node-level spans they emit add no signal on top of what `LaminarMiddleware` already captures, and clutter the transcript view.
- **Deepagents wins over pydantic_ai when both are installed**: `init_instrumentations` normally strips the raw LLM-provider instrumentors (`OPENAI`, `ANTHROPIC`, …) when `pydantic_ai` is auto-enabled (`_PYDANTIC_AI_PROVIDER_CONFLICTS`), but the deepagents instrumentation relies on those raw instrumentors to emit LLM spans underneath each `TOOL` span — without them the `deep_agent` trace shows only root + tool spans and no LLM children. When `_deepagents_installed()` is true, `init_instrumentations` skips the pydantic_ai conflict-removal so the providers stay enabled. Users with both libraries who want pydantic_ai's de-dup back can either block deepagents (`block_instruments={Instruments.DEEPAGENTS}`) or pass an explicit `instruments` set.
- Root span (`deep_agent`, type DEFAULT) is opened by wrapping the compiled graph's `invoke`/`ainvoke`/`stream`/`astream` at the instance level in `DeepagentsInstrumentor._wrap_graph_methods`, NOT from `AgentMiddleware.before_agent`/`after_agent`. LangGraph runs each middleware hook as its own graph node (a separate task), so OTel context attached in `before_agent` is popped before downstream tool nodes execute and the root span fails to parent subsequent tool spans (symptom: tool spans emit with `parent_span_id=0` on a new trace_id). Wrapping the graph entrypoint keeps the context active for the whole execution.
- `Pregel.invoke` internally calls `self.stream`, so wrapping both without a guard produces two root spans per top-level call. A `contextvars.ContextVar` sentinel (`_root_active` in `deepagents/instrumentor.py`) collapses that to one.
- Subagent cards in the frontend transcript are derived from `lmnr.span.prompt_hash` fingerprinting (see `computeSubagentBoundaries` in `frontend/components/traces/trace-view/store/utils.ts`) — no dedicated subagent span type is needed. A TOOL span named `task` nesting the subagent's LLM/tool spans is enough; the frontend groups them automatically.
- `deepagents` depends on `langchain>=1.0`. `DeepagentsInstrumentorInitializer` returns `None` unless both `deepagents` and `langchain` are installed, so the instrumentor is a silent no-op in environments where only one is present.
- Span-lifetime split: the `invoke`/`ainvoke` and tool-call wrappers use `Laminar.start_as_current_span(...)` as a context manager — the span lives for exactly the `with` block. `stream`/`astream` cannot — the wrapper returns before the caller iterates, so a `with start_as_current_span(...)` around the wrapper body would end the span before any chunk is yielded. Use `Laminar.start_span(...)` to mint the span imperatively *inside* the generator, then re-activate it with `Laminar.use_span(span, end_on_exit=True)`; that handles the 3-way context attach (OTel global context, Laminar isolated context, TracerWrapper span stack), lets `@contextmanager`'s built-in `GeneratorExit` handling leave the span status as UNSET on `break`, and ends the span when the generator closes. Do NOT hand-roll a `_SpanHandle`-style wrapper for this — `use_span(..., end_on_exit=True)` is the public API and is what every other lmnr-python instrumentor uses.
- Stream wrappers (`_wrap_graph_stream` / `_awrap_graph_stream`) must open the span inside the returned generator, not eagerly in the outer function: if the caller never iterates, an eagerly-opened span would never be ended. Additionally, the `_root_active` sentinel must NOT be mutated inside a sync generator body — Python leaks ContextVar changes from sync generators to the caller's context on `yield`, which would make a second concurrent `graph.stream()` call short-circuit and skip instrumentation. The sentinel only needs to be set by `_wrap_graph_invoke` (in its plain-function frame) to collapse `Pregel.invoke → self.stream` into one root span.

## Langfuse bridge

- **The Langfuse bridge is OPT-IN and is NEVER in the default instrument set, even when `langfuse` is installed.** `init_instrumentations` builds the default set as `set(Instruments) - {Instruments.LANGFUSE}` (then the pydantic_ai / deepagents auto-removal logic), so a bare langfuse install changes nothing — Laminar's own instrumentors keep running. This is deliberate: the prior "auto-enable whenever `langfuse >= 3.0` is importable" behavior was a development-environment footgun where a transitive/unrelated `langfuse` install would silently disable ALL of Laminar's own tracing for a user who only instrumented with Laminar. There is no `bridge_from_langfuse` flag and no auto-enable branch — an earlier iteration added one and it was removed in favor of the two opt-in paths below.
- **Two ways to opt in:** (1) pass an explicit `instruments` set containing `Instruments.LANGFUSE` to `Laminar.initialize` — when `instruments` is explicit it is honored verbatim (no pydantic_ai/deepagents auto-removal, no auto-add of LANGFUSE), so the caller gets exactly what they listed and accepts any double-coverage; (2) call `Laminar.connect_to_langfuse()` after initialization (e.g. when init happens in code you don't control). Note that opting in does NOT disable Laminar's other instrumentors — if you enable LANGFUSE alongside the raw-provider/framework instrumentors, the same call may be traced twice. To avoid that, pass an `instruments` set with only LANGFUSE (+ whatever else you want).
- `_langfuse_installed()` in `tracing/instruments.py` gates on **both** `is_package_installed("langfuse")` and `get_package_version("langfuse") >= 3.0.0`. It is used ONLY by `Laminar.connect_to_langfuse()` (and the bridge initializer's own version guard), to refuse installing a useless translator on langfuse 2.x. It no longer participates in any default-set computation.
- The bridge lives in `src/lmnr/opentelemetry_lib/opentelemetry/instrumentation/langfuse/__init__.py` and has two parts:
  1. `LangfuseInstrumentor.instrument(lmnr_tracer_provider, lmnr_span_processor)` attaches Laminar's `SpanProcessor` to every Langfuse-owned `TracerProvider` by iterating `LangfuseResourceManager._instances` and monkey-patching `_initialize_instance` so Langfuse clients created AFTER the bridge installs also get dual-attached. `_handled_providers: set[int]` (keyed by `id()`) prevents double-attach; the Laminar provider itself is skipped.
  2. `LangfuseAttributeTranslator` is a `SpanProcessor` that mutates Langfuse-scoped spans on `on_end` — rewriting `langfuse.observation.model.name` → `gen_ai.request.model`/`gen_ai.response.model`, `langfuse.observation.usage_details` → `gen_ai.usage.{input,output}_tokens`/`llm.usage.total_tokens`, `langfuse.observation.cost_details` → `gen_ai.usage.{input,output,}_cost`, and observation-type mapping (`generation|completion|embedding` → `SPAN_TYPE=LLM`, `tool` → `SPAN_TYPE=TOOL`). Trace-level attrs `session.id` / `user.id` / `langfuse.trace.tags` / `langfuse.trace.metadata.*` map into `lmnr.association.properties.{session_id,user_id,tags,metadata.*}`. Input/output handling is **observation-type aware** (see the input-split bullet below).
- `LangfuseInstrumentor` does NOT extend `BaseInstrumentor` because `BaseInstrumentor.instrument()` ignores kwargs other than `tracer_provider`/`logger_provider`, and the bridge needs the caller-supplied Laminar `SpanProcessor`. `init_instrumentations` has a special-case branch (`if instrument == Instruments.LANGFUSE: instrumentor.instrument(lmnr_tracer_provider=..., lmnr_span_processor=...)`).
- `LangfuseInstrumentor` idempotency state (`_installed`, `_translator`, `_original_initialize_instance`, `_lmnr_span_processor`) is stored **on the class, not the instance** — both `Laminar.connect_to_langfuse()` and `init_instrumentations` construct a fresh `LangfuseInstrumentor()` each call, so `self.X = v` would create an instance attribute that shadows the class default and every new instance would read the unshadowed `_installed = False`, duplicating the translator processor and layering monkey-patches. Always assign via `type(self).X = v` (or `LangfuseInstrumentor.X = v`) in `instrument`/`uninstrument`/`_patch_resource_manager`/`_unpatch_resource_manager`. Reads via `self._X` are fine because attribute lookup falls through to the class.
- `LangfuseAttributeTranslator.on_end` cannot use `span.set_attribute(...)` to inject the translated attrs: (a) `on_end` is called with an OTel `ReadableSpan`, which has no `set_attribute` method, and (b) even when the object happens to be the recording `Span`, its `end()` has already run so `set_attribute` is a silent no-op. The translator writes directly to `span._attributes[k] = v` — safe because `ReadableSpan._attributes` is the *same dict object* as the recording `Span._attributes`, so the exporter sees the mutation when it serializes the span.
- Processor **order** on the shared `TracerProvider` matters. `SynchronousMultiSpanProcessor` runs `on_end` in insertion order, and when `disable_batch=True` the Laminar exporter is backed by `SimpleSpanProcessor`, which `export()`s synchronously inside its own `on_end`. If the translator were appended after the exporter (the default of `add_span_processor`), the exporter would ship the pre-translation `langfuse.*` shape. The bridge uses `_prepend_span_processor` to reorder the underlying `_span_processors` tuple so the translator is first. Tests previously masked this because `InMemorySpanExporter` stores span *references* and mutations stick — the SimpleSpanProcessor regression test (`test_translator_mutates_before_synchronous_exporter`) exercises the real timing.
- Public API: `Laminar.connect_to_langfuse()` manually installs the bridge — one of the two opt-in paths, for when initialization happens in code you don't control or you want to install the bridge imperatively after `initialize`. Returns `True` on success, `False` if Laminar isn't initialized, langfuse isn't importable, or langfuse is < 3.0. Gates on `_langfuse_installed()` (version-gates on >= 3.0) rather than `is_package_installed("langfuse")` alone — on 2.x `instrument()` would attach a useless translator and flip `_installed=True`, blocking any later valid install. Returns `LangfuseInstrumentor._installed` (not a hard-coded `True`) so early-return paths inside `instrument()` surface as False. Idempotent (the class-level `_installed` flag collapses repeat calls to no-ops).

The translator applies them only where they already exist (root span). Tests in `test_langfuse.py` exercise each translation branch against a real `Langfuse()` client + `InMemorySpanExporter`.
- Langfuse emits usage/cost as JSON-encoded strings over OTel (`langfuse.observation.usage_details = '{"input":10,...}'`) because OTel attribute values can't be dicts. The translator `_parse_json`s them; it also falls back gracefully if the value is already a dict (shouldn't happen at on_end, but cheap to handle).
- `LangfuseInstrumentor.uninstrument()` is the inverse of `instrument()` — it must remove the translator (and the Laminar `SpanProcessor`) from every provider it was attached to AND clear every class-level bookkeeping field (`_installed`, `_handled_providers`, `_attached_providers`, `_translator`, `_lmnr_span_processor`, `_lmnr_tracer_provider`). Clearing only `_installed` is a bug: a subsequent `instrument()` call would prepend a second translator onto Laminar's provider (the first was never removed) and `_handled_providers` would still carry stale `id()` values so `_attach_to_existing_langfuse_providers` would short-circuit on Langfuse providers it already saw. The bridge tracks every provider it touches in `_attached_providers` (keyed by `id()`, value = the provider) for this reason; `_remove_span_processor` mirrors `_prepend_span_processor` and walks the `_active_span_processor._span_processors` tuple under its lock to drop the processor.
- The "skip Laminar's own provider" guard in `_attach_to_provider` cannot rely on `TracerWrapper.verify_initialized()` alone: during the auto-install path, `init_instrumentations` is called by `TracerWrapper.__new__` BEFORE `cls.instance = obj` is assigned (see `tracing/__init__.py`), so the guard's `TracerWrapper.verify_initialized()` branch returns False and a Langfuse client that shares the newly-created Laminar provider would double-attach the translator + Laminar span processor. `instrument()` pre-registers `id(lmnr_tracer_provider)` into `_handled_providers` up-front so the short-circuit is id-based and independent of TracerWrapper lifecycle.
- `instrument()` prepends the translator to Laminar's provider *before* running the attach-to-existing + resource-manager-patch phases. If either of those later phases raises (e.g. a `RuntimeError` walking `LangfuseResourceManager._instances` under concurrent modification), the translator would be orphaned on the provider while `_installed` stayed False — a subsequent `instrument()` call (e.g. via `Laminar.connect_to_langfuse()`) would pass the guard and prepend a SECOND translator, double-translating every Langfuse span. The attach + patch phases are therefore wrapped in a `try/except` that calls `uninstrument()` before re-raising. `_installed=True` is set *before* the fallible block so `uninstrument()` (which short-circuits when `_installed=False`) actually runs the cleanup path.
- **Opting into the bridge does NOT auto-disable Laminar's other instrumentors.** Since the only opt-in paths are an explicit `instruments` set (honored verbatim) or `connect_to_langfuse()`, the caller is in full control of what else runs. If they enable LANGFUSE via `connect_to_langfuse()` while the default set is active, the raw-provider/framework instrumentors are still on and the same call gets traced twice; to get Langfuse as the single source they should pass an `instruments` set containing only LANGFUSE (plus anything else they explicitly want). The bridge's whole job is to route Langfuse-emitted spans into Laminar — it's up to the caller to avoid double-covering.
- **Python 3.14 compatibility gotcha**: `langfuse` (as of 3.14.x) ships pydantic-v1-generated API models (`langfuse.api.resources.*`) that fail to import on Python 3.14 with `pydantic.v1.errors.ConfigError: unable to infer type for attribute "description"`. Translator/attach-path unit tests stay green because they don't touch the real SDK.
- **LLM-observation input/output is translated to the GenAI *message* conventions, NOT dumped raw into `lmnr.span.input/output`.** This is the critical bug the bridge originally had: `langfuse.openai` ships a chat-completion call's input as EITHER a bare OpenAI message array (`[{role, content}, ...]`, the no-tools case) OR a dict `{"messages": [...], "tools": [...], "functions": [...], "function_call": ...}` (when tools/functions are present — see `_extract_chat_prompt` in `langfuse/openai.py`). The frontend can't render that dict blob. For `is_llm` observations (`generation|completion|embedding`) the translator now splits it via `_genai_input_from_langfuse` → `gen_ai.input.messages` (the message array) + `gen_ai.tool.definitions` (the `tools`, else `functions`, array), and normalizes the single-message output dict (`{role, content, tool_calls, function_call, ...}` from `_extract_chat_response`) into a one-element `gen_ai.output.messages` array via `_genai_output_from_langfuse`. App-server PREFERS `gen_ai.input.messages` / `gen_ai.output.messages` and they OVERWRITE the legacy `gen_ai.prompt.{N}.*` path (see `app-server/src/traces/spans.rs::parse_and_enrich_attributes`), so this is the shape that actually renders. **Non-LLM observations** (and any LLM input whose shape isn't a recognized message/dict) fall back to the original raw `lmnr.span.input/output` blob. Langchain spans share the OpenAI message shape, so the same split covers them. Target shapes mirror Laminar's own `litellm/wrappers/completions/__init__.py`.
- **`langfuse.langchain` inlines tool DEFINITIONS into the input message array as `role:"tool"` messages, and the content shape is PROVIDER-SPECIFIC** — `_split_messages_and_tool_defs_langchain` must handle both. OpenAI: `content = {"type":"function","function":{...}}` (definition under `"function"`). Anthropic: `content = {"name","input_schema","description"}` — the Anthropic-native shape (NO `type`/`function` wrapper), which IS already what Laminar's own Anthropic instrumentor dumps into `gen_ai.tool.definitions` (`anthropic/span_utils.py` stamps raw `kwargs["tools"]`). The splitter detects the Anthropic shape via `"input_schema" in content and "name" in content`. **This was the langchain-anthropic bug**: the splitter did `content["type"]` (direct key access), which `KeyError`-ed on the Anthropic shape; `on_end`'s blanket `try/except` swallowed it, so the ENTIRE span was left untranslated (all `langfuse.*` attrs stayed raw — not just tools). Use `.get()` for all content probing so an unrecognized content dict falls through to being a normal message instead of aborting translation. Pinned by `test_translator_splits_langchain_{openai,anthropic}_inlined_tool_defs`.
- **Anthropic-langchain assistant OUTPUT carries tool calls TWICE — in the `content` list as `{"type":"tool_use",...}` blocks AND a redundant top-level `tool_calls` mirror.** `_convert_openai_tool_calls_to_content_parts` drops the top-level `tool_calls` when the content list already embeds `tool_use`/`tool_call` blocks (otherwise the same call renders twice). For the OpenAI shape (string `content` + separate `tool_calls`) it still folds the calls into content parts. Detection keys on `part.get("type") in ("tool_use","tool_call")` within a list content.
- **openinference-instrumented spans (groq, google_genai) are a SEPARATE detection + translation path.** Langfuse's docs route groq / google_genai through openinference instrumentations (`openinference-instrumentation-google-genai`, `...-groq`), whose spans carry NEITHER the `langfuse-sdk` scope NOR any `langfuse.*` attribute — so `_is_langfuse_span` skips them entirely. `_is_openinference_span` detects them via `openinference.span.kind` OR the flat indexed keys (`llm.input_messages.*` / `llm.output_messages.*` / `llm.token_count.*`), and `on_end` routes them to `_translate_openinference`. Tokens → `gen_ai.usage.{input,output}_tokens` / `llm.usage.total_tokens`; `llm.model_name` → `gen_ai.request/response.model`. - **LiteLLM's `langfuse_otel` callback IS bridged — but provider attachment to `logger._tracer_provider` is NOT enough; see the two-layer fix below.** LiteLLM's `langfuse_otel` success callback (`litellm/integrations/langfuse/langfuse_otel.py`, class `LangfuseOtelLogger`) subclasses LiteLLM's base `OpenTelemetry` integration with `skip_set_global=True`, so it builds PRIVATE stock `opentelemetry.sdk.trace.TracerProvider`s that export OTLP straight to Langfuse Cloud (`{host}/api/public/otel`) — it never registers with `LangfuseResourceManager._instances`, so the resource-manager dual-attach loop can't reach it. - **LAM-1784 (the `instruments=[Instruments.LANGFUSE]` case): bridging the logger needs TWO per-logger wraps, applied in `_patch_litellm_logger` (called from both the existing-logger scan and the factory patch; idempotent via `_wrapped_litellm_loggers` keyed by `id()`).** With `instruments=[Instruments.LANGFUSE]`, Laminar's OWN `LitellmInstrumentor` does NOT run (explicit `instruments` are honored verbatim), so there is no `litellm.completion` span to catch litellm's callback — the symptoms were: NO `litellm_request`/`raw_gen_ai_request` spans reach Laminar AND the user's `@observe` root gets mis-marked LLM. Two independent root causes, each needing its own wrap:
  1. **Wrong provider (spans never arrive).** When the request carries credentials (the common `langfuse_otel` case — env-var or dynamic headers), litellm does NOT emit through `logger._tracer_provider`. `get_tracer_to_use_for_request` calls `_get_tracer_with_dynamic_headers`, which lazily builds a SEPARATE `TracerProvider` PER credential set and caches it in `logger._tracer_provider_cache`. So attaching Laminar's translator + span processor only to `logger._tracer_provider` misses every span. Fix: wrap `_get_tracer_with_dynamic_headers` to `_attach_to_provider` each cache-provider value as it appears (still attach to `_tracer_provider` for the no-credentials path).
  2. **Attribute folding (root mis-marked LLM).** In `_handle_success`, `should_create_primary_span = parent_span is None or get_secret_bool("USE_OTEL_LITELLM_REQUEST_SPAN")`. With a parent active (the `@observe` root resolved via `_get_span_context` Priority 3 = `trace.get_current_span()`) and the env var unset, litellm takes the ELSE branch: creates NO `litellm_request` span and folds `gen_ai.*`/openinference attrs onto the root, which app-server's `gen_ai.*`-keyed `span_type()` then marks LLM. Fix: wrap `_get_span_context` to return `(ctx, None)` — keeps the parent CONTEXT (so `litellm_request` still nests under the root) but reports `parent_span=None`, flipping `should_create_primary_span` to True WITHOUT the global env var (which would change behavior process-wide). **Gated by `_is_llm_span(parent_span)`**: when `Instruments.LITELLM` ALSO runs (combined mode), the active parent is Laminar's own `litellm.completion` LLM span and folding onto it is the correct deduplicated shape — nulling it would create a duplicate nested LLM span, so we leave LLM parents untouched. This is why the LAM-1784 `use_span` fix in `litellm/wrappers/__init__.py` (bullet below) STAYS: it's what makes `litellm.completion` the current span in combined mode, which this gate then preserves. Net shapes: LANGFUSE-only → clean root + `litellm_request`(LLM) + `raw_gen_ai_request`; combined → `litellm.completion`(LLM) + clean root + `raw_gen_ai_request`; both have exactly ONE LLM span and an un-mis-marked root. `_unwrap_litellm_loggers` restores both bound methods on `uninstrument`. Pinned by `test_litellm_bridge_wraps_and_unwraps_logger_methods` + `test_is_llm_span_detects_llm_parents`.
- **Routing precedence in `on_end` is openinference FIRST, then langfuse.** LiteLLM `langfuse_otel` spans are a hybrid but carry NO `langfuse.observation.type`, so the langfuse path (`_translate`) can't tell they're LLM calls and would miss model/tokens/messages — all of which live in the openinference `llm.*` attrs. `_is_openinference_span` (keys on `openinference.span.kind` or `llm.token_count.*` / `llm.{input,output}_messages.*`) is therefore checked before `_is_langfuse_span`. - **`_translate_openinference` must NOT trust `openinference.span.kind=TOOL` on a span that carries LLM signals (LAM-1784 follow-up).** litellm's `langfuse_otel` callback runs through arize's `_utils.set_attributes`, which forces `openinference.span.kind=TOOL` on ANY completion that merely passes `tools=[...]` (see `litellm/integrations/arize/_utils.py`: `if (optional_tools or metadata_tools) and span_kind != TOOL: span_kind = TOOL`). Pinned by `test_translator_does_not_mistype_tool_forced_llm_call_as_tool` + `test_translator_keeps_genuine_tool_span_as_tool`.
- **Laminar's own litellm wrapper MUST activate its `litellm.completion` / `litellm.responses` span as the current OTel span around `wrapped()` (`with Laminar.use_span(span):`) — not just create it.** LAM-1784: litellm's `langfuse_otel` (and any base-`OpenTelemetry`-derived) success callback runs synchronously inside `wrapped()` and resolves its parent via `OpenTelemetry._get_span_context`, whose Priority 3 is `trace.get_current_span()`. Activating our span makes the callback parent onto IT, so litellm's attrs land on the LLM span where they belong and the root stays clean. The wrapper was already doing this on the rollout-mode and async-coroutine paths; the plain sync path was the gap. Regression-pinned by `tests/test_litellm.py::test_litellm_completion_activates_span_for_otel_callbacks` (a bare litellm `CustomLogger` captures `trace.get_current_span()` at success time and asserts it equals our span id; `mock_response`, no network/VCR). app-server does NOT parse openinference/`langfuse.*` attrs, so without the bridge connected the polluted root is not server-classified LLM — but the pollution is still wrong and the fix cleans it at the source.

- `_instrument` performs no version/installation guards of its own: `BaseInstrumentor.instrument()` already enforces the `instrumentation_dependencies()` constraint (`pydantic-ai-slim >= 1.0.0`), and `PydanticAIInstrumentorInitializer` in `_instrument_initializers.py` only returns this instrumentor when `pydantic-ai-slim` or `pydantic-ai` is installed.
- The test suite runs with `disabled_instruments={Instruments.PYDANTIC_AI}` in `tests/conftest.py` so the raw-provider instrumentor tests still operate on the SDK-level spans they assert on.
- `_instrument` also wraps `pydantic_ai.agent.Agent._run_span_end_attributes` to strip the `pydantic_ai.all_messages` attribute (and the v1-equivalent `all_messages_events`) from the parent agent run span. pydantic_ai dumps the full message history of a run on that span as a JSON blob, but the same content is already on the per-step `chat {model}` child spans via `gen_ai.input.messages` / `gen_ai.output.messages`, so keeping it on the parent doubles ingestion + storage cost. The accompanying `logfire.json_schema` entry is updated in lockstep so backends that read it stay consistent. Tests live in `tests/test_pydantic_ai_settings_patch.py` (`test_run_span_end_attributes_strips_duplicate_messages` / `..._preserves_other_attrs`).

## Temporal instrumentor

The Python Temporal integration (`opentelemetry/instrumentation/temporal/`) is the port of the TS `lmnr-ts` Temporal integration. The shapes are similar, but the wiring is fundamentally different because Python has no ESM module-isolation problem — there is **no `instrumentModules` / `workflowBundle` user wiring**. It auto-registers like every other instrumentor (`Instruments.TEMPORAL`, gated by `is_package_installed("temporalio")`).

- **ONE interceptor covers all three paths.** `LaminarTracingInterceptor` implements both `temporalio.client.Interceptor` AND `temporalio.worker.Interceptor` (`intercept_client` / `intercept_activity` / `workflow_interceptor_class`). The Temporal worker auto-inherits client interceptors (`temporalio.worker._worker` prepends client interceptors to worker ones), so injecting it once at the client level covers client + activity + workflow. This is why TS's three-way split (client patch, worker patch, bundled workflow module) collapses into one object here.
- **Auto-injection patches `Client.__init__`, not `Client.connect`.** `Client.connect` builds config then calls `cls(...)`, so patching `__init__` (`_wrap_client_init` in `temporal/__init__.py`, via `wrap_function_wrapper`) covers BOTH the high-level `connect` path and direct `Client(service_client, ...)` construction. The wrap appends a `LaminarTracingInterceptor` to `kwargs["interceptors"]` only if one isn't already present (idempotent — guards user-supplied interceptor + re-entrant construction). Injection must happen before `_init_from_config` builds `self._impl` (which iterates interceptors in reverse).
- **`workflow_interceptor.py` is sandbox code — it must NEVER import `lmnr`.** The workflow interceptor CLASS (not instance) is returned from `workflow_interceptor_class` and instantiated INSIDE the Temporal deterministic sandbox (`_workflow_instance.py`). `temporalio` is a sandbox passthrough module; `lmnr` is NOT (it pulls in httpx → urllib, which the sandbox blocks with `RestrictedWorkflowAccessError`). So this file imports only `contextvars`, `temporalio.*`, and the pure-constant `.consts`; it creates NO spans, uses NO real uuid/time, and ONLY forwards already-serialized trace headers. `temporalio.workflow` appears solely in string annotations (deferred via `from __future__ import annotations`).
- **Handler header scoping uses a `ContextVar`, not instance state.** Signal/update handlers run as separate asyncio tasks (which COPY the context), so `_handler_headers` (a `ContextVar`) keeps each handler's trace headers isolated from the main workflow path and from concurrent handlers — replay-safe and deterministic. `_active_headers()` returns the handler scope if set, else the workflow-start headers. A signal/update arriving with NO injected trace context must NOT enter the scope (`_has_trace_headers` guard), or `_active_headers` would resolve to an empty map and drop the workflow-start trace from activities scheduled inside the handler. Outbound `_merge` is caller-wins: `{**active_headers, **caller_headers}`.
- **Two headers propagate: `x-lmnr-span-context` (preferred) + `traceparent` (W3C interop)**, both `json/plain` Temporal Payloads via `PayloadConverter.default`. `restore_context_from_headers` prefers the full Laminar header, falls back to traceparent.
- **Debug-context propagation is FREE — there is no `pushLaminarContext` (unlike TS).** On the Python span path, `Laminar.start_span(parent_span_context=restored)` already (a) parses the nested `debug` block and arms the downstream debug runtime, and (b) stamps the `lmnr.span.path` / ids-path parent attributes. So the activity interceptor just hands the restored `LaminarSpanContext` to `parent_span_context=` and both trace nesting and debug propagation happen automatically.
- **`create_activity_span=False` still activates the propagated context — it does NOT make in-activity spans detached roots.** When the wrapper span is disabled, `execute_activity` runs the activity inside `with Laminar.use_span_context(restored):` so manual `observe` calls and auto-instrumented LLM spans created inside the activity still nest under the workflow / client trace (and a propagated `debug` block still arms the runtime). The flag only suppresses the *wrapper* span named after the activity, never the parent-context activation. `Laminar.use_span_context` (`sdk/laminar.py`) is the no-wrapper analogue of `use_span`: it parses the `LaminarSpanContext`, arms debug, pushes a `NonRecordingSpan` parent onto both the OTel context and Laminar's isolated context stack, and calls `processor.set_parent_path_info` so child dotted paths are correct — but creates no span of its own. This was a shared bug with TS (`createActivitySpan: false` was treating in-activity spans as roots); both SDKs now nest. Covered by `test_activity_disabled_still_nests_inner_spans` (inner span shares the propagated trace_id and parents to the remote span id).
- **The workflow-lifecycle span ends on the FIRST terminal handle call.** `_wrap_workflow_handle` shadows the handle's `result` / `cancel` / `terminate` bound methods on the instance (`WorkflowHandle` has `__dict__`) and closes the span once on whichever resolves/raises first. `cancel`/`terminate` also open their own short child spans.
- **OTel span ids are 64-bit but `LaminarSpanContext` stores them padded into a UUID.** A full `uuid.uuid4()` span_id (128-bit) is out of OTel's 64-bit range → INVALID SpanContext that `start_span` silently DROPS (no parent inheritance, fresh trace). Tests that assert parent-trace inheritance must mint a valid id: `uuid.UUID(int=uuid.uuid4().int & ((1 << 64) - 1))` — see the `_span_context()` helper in `tests/test_temporal_instrumentation.py`. (`DebugContext.session_id` / `replay_trace_id` are `str | None`, not UUID — wrap test uuids in `str(...)`.)
- **Tests are pure interceptor unit tests, no Temporal server.** `tests/test_temporal_instrumentation.py` drives the interceptors directly with `SimpleNamespace` fake inputs + fake `next` interceptors, so no server/sandbox is needed (the sandbox-import constraint can't be exercised by unit tests — validate that with a `WorkflowEnvironment.start_local()` scratch script where the workflow + activity live in their OWN lmnr-free module, since the sandbox re-imports the defining module). `temporalio` is pinned in `[dependency-groups].dev`.
