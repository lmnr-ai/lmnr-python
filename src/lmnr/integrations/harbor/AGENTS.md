# Harbor plugin (`src/lmnr/integrations/harbor/`)

- `LaminarPlugin` implements Harbor's duck-typed `JobPlugin` protocol (`on_job_start` / `on_job_end`) and is registered via the `harbor.plugins` entry point in `pyproject.toml` (`laminar = "lmnr.integrations.harbor:LaminarPlugin"`), so `harbor run ... --plugin laminar` works with only `pip install lmnr` next to harbor. `--pk key=value` values arrive as **strings** — coerce ints/bools in `__init__` (`_parse_bool`).
- **Never import `harbor` at runtime** (only under `TYPE_CHECKING`): harbor needs Python ≥ 3.12 and this SDK supports 3.11. `tests/test_harbor_plugin.py` drives the plugin with `FakeJob` / `SimpleNamespace` fakes of `Job` and `TrialHookEvent`. **The one exception is `runner.py`** (below): it subclasses Harbor's classes, and only Harbor loads it (`lmnr/__init__`, this package's `__init__` and `lmnr.evals` never import it). Its Harbor imports carry `# pyright: ignore[reportMissingImports]` (Harbor isn't a dev dependency, so basedpyright can't resolve them) and its classes `# pyright: ignore[reportUntypedBaseClass]`.
- **`runner.py`: `LaminarAgent` (`BaseInstalledAgent`) and `LaminarVerifier` (`BaseVerifier`) run an `EvalRunner`** (`lmnr.evals`, `src/lmnr/evals/AGENTS.md`). lmnr-cli writes them into the job config for `agent/eval.py` datasets with `kwargs: {runner: "agent/eval.py:<Class>"}`, relative to Harbor's cwd (the dataset dir); import paths are `spans.py`'s `LAMINAR_AGENT_IMPORT_PATH` / `LAMINAR_VERIFIER_IMPORT_PATH`. The module is loaded by path once per process and the runner instantiated per trial.
  - `LaminarAgent.run` keeps the trial's steps in ONE function, in order: services (`start_services`, their env added to `ctx`) → (phase 3: mock server) → `setup` → `run` → `collect` → services' snapshots, and `collect` (plus snapshots) also runs when `run` raised (its own error is only logged, so the run's wins; after a cancellation, e.g. an agent timeout, it gets `COLLECT_AFTER_CANCEL_TIMEOUT_SEC`). The agent isn't told its task: it reads the trial's `config.json` (`logs_dir.parent`) into Harbor's `TrialConfig`. `install()` does nothing (lmnr-cli built the image).
  - `LaminarVerifier.verify` runs `verify(ctx)` in the Harbor process against the environment Harbor passes (agent container in `shared` mode, the fresh one in `separate`; `ctx.verifier_mode` says which, derived from `task.config.verifier` like Harbor does, and only `shared` gets the services' env), normalizes the result (number → `{"reward": x}`, bools → 0/1), writes `reward.json` on the host and, when `/logs/verifier` isn't mounted, into the container, and writes a readable log (its `ctx.logger` lines, the rewards or the traceback) to the trial's `verifier/test-stdout.txt`, which becomes the verifier span's `test_output`. A custom verifier gets no download of `/logs/verifier` from Harbor, so the host files are written directly. Exceptions propagate (Harbor records them on the trial).
  - Tests: `tests/test_harbor_runner.py` uses real Harbor classes with a fake environment and `pytest.importorskip("harbor")`, so it is skipped by `uv run pytest`. CI runs it in its own env on the 3.13 leg (`run-tests.yml`, "Run Harbor adapter tests"): `uv run --isolated --no-project --python 3.13 --with-editable . --with harbor==0.25.0 --with pytest==9.0.3 --with pytest-asyncio==1.3.0 pytest tests/test_harbor_runner.py`. Bump that pin together with lmnr-cli's `HARBOR_VERSION`.
- **`verify()` is traced under the trial's verifier span.** `_on_verification_started` (Harbor awaits it before running the verifier) STARTS the `verifier` span (open, `start_time` = the hook's timestamp: Harbor sets `result.verifier.started_at` right after the hook), keeps it on `_TrialState.verifier_span`, and registers its `LaminarSpanContext` in `spans.verifier_spans[trial_name]`. `LaminarVerifier` looks up `trial_paths.trial_dir.name` (= the trial name) and runs `verify()` in `Laminar.start_as_current_span("verify", parent_span_context=...)`; without the plugin there's no entry and it runs untraced. At trial end the plugin sets the open span's output / exception and ends it at `result.verifier.finished_at`; trials that never fired the hook keep the after-the-fact `_emit_phase` path, and an open span whose verifier never got timing is ended as unfinished (the exception then goes on the root). Retries and `on_job_end` end a leftover open span (`_end_open_verifier_span`) and drop its registry entry.
- An open span is never exported, so a trial whose root is still open has no spans and the UI shows "Error Loading Trace". Finished child spans are therefore emitted as soon as Harbor's hooks allow, and the frontend draws the still-open root as a pending parent. A zero-length `trial_started` child is emitted at trial START so the trace exists during env setup (which can take minutes). On the first `on_agent_started`, env and agent setup are already done. On `on_verification_started`, the agent span plus trajectory are emitted: logs and the trajectory are synced by then, and agent timeout/exit errors are already in `exception_info`. The verifier and root spans only exist at `on_trial_ended`, which emits whatever wasn't emitted yet. Some trials skip the earlier hooks: early failures, multi-step trials where `agent_execution` is None, and regrades. Per-attempt flags (`setup_emitted`, `agent_span`, `agent_exception`) on `_TrialState` reset on retry. An exception different from the one on the agent span goes on the verifier span, or on the root if there is none.
- Phase span contents come from files, not `TrialResult`.
  - `environment_setup` input: env type plus the task.toml `[environment]` image and resources, with `override_*` winning.
  - `agent_setup`: output is the agent version (`agent_info` is refreshed after setup) plus any `agent/setup/*` install logs.
  - `verifier`: input is the task's `tests/test.*` script; output is `{rewards, test_output}` from `verifier/test-stdout.txt` (stdout and stderr combined).
  - Empty values are dropped.
- Spans are built after the fact from `TrialResult` timings and the ATIF `agent/trajectory.json`, using `Laminar.start_span(..., start_time=ns)` + `span.end(end_time=ns)` (the `start_time` kwarg was added for this). The root span uses `context=Context()` so each trial is its own trace, and `metadata={"evaluation_id": ...}` + `span_type="EVALUATION"` so children inherit the eval trace type / id.
- ATIF timing semantics: an LLM span runs from the previous step's timestamp to its step's timestamp; tool spans are instants at the step timestamp (ATIF records no tool durations) unless they spawned subagents, in which case they stretch to cover the subagent steps. Steps with `is_copied_context` or `llm_call_count == 0` are not LLM calls. Because that makes a step's tools and the next LLM call share a start time, and the trace view sorts siblings by start time at millisecond precision (JS `Date`), `TrajectoryConverter` nudges sibling starts by `ORDER_GAP_NS` (1ms) so they follow trajectory order: each LLM span starts after the previous step's tool spans end, each tool after the previous sibling. The order state is per nesting level (saved/restored around subagent recursion).
- **lmnr-atif trajectories** (written by a Laminar SDK, spec in `spec/lmnr-atif/`) are read only through `lmnr.sdk.trajectory.reader`. `TrajectoryConverter.emit` builds a `TrajectoryExtension` per trajectory, passing the parent's to subagents so they inherit `spec_version` and `$ref` defs. Every reader helper takes `ext=None` for plain ATIF, so there is one code path. LLM span inputs come from `reader.input_messages` for both kinds of file, and its plain-ATIF result matches the old history exactly, which `test_trajectory_becomes_llm_and_tool_spans` pins. Spans with exact `start_time`/`end_time` use them as-is with no `ORDER_GAP_NS` nudging, and they still update the order state so later synthetic-timed siblings follow. Errors become hand-built `exception` events (`_record_error`), because there is no exception object. The root trajectory's summary (`spec_version`, `trace_ids`, `exported`, `complete`, final totals) lands on the agent span as `lmnr.trajectory.*` via `converter.parent_attributes`, and each replayed span links to its original as `lmnr.trajectory.source_span_id`. Tests drive the spec fixtures directly.
- **A root trajectory with `extra.lmnr.exported: true` is not replayed.** The SDK wrote it in dual mode (`LMNR_TRAJECTORY_PATH` plus `LMNR_TRAJECTORY_FORCE_EXPORT`) and already exported its spans, so rebuilding them would record every call twice. The agent span still gets the `lmnr.trajectory.*` summary, whose `trace_ids` link to the agent's own traces. `lmnr_atif_fixture()` in the tests sets `exported: false` unless asked, because two spec fixtures are exported examples.
- Tool errors in plain ATIF come from Harbor's own flags: `observation_result.extra.tool_result_is_error` (claude-code) and `extra.is_error` (kimi).
- Observation results without `source_call_id` (terminus-2 records one combined terminal output per step) are attached to the step's last tool call; earlier calls in that step get no output.
- A step `model_name` without a provider prefix (terminus-2 records the API's `claude-sonnet-4-5-20250929`) takes the provider from the trajectory's `agent.model_name` (`anthropic/claude-sonnet-4-5`), so LLM spans still get `gen_ai.system`.
- The plugin initializes Laminar with `set_global_tracer_provider=False` and `instruments=set()`, except when EVERY `job.config.agents[*].import_path` is `LaminarAgent` (`_all_agents_are_eval_runners`): then `disabled_instruments={Instruments.DAYTONA_SDK}`, so LLM calls in `verify()` (a user's judge through a provider SDK from the evals root's `pyproject.toml` or eval.py's PEP 723 block) are traced under the verifier span. The Daytona leak (an orphan trace per sandbox API call) came from our own `DAYTONA_SDK` instrumentor; other jobs keep the empty set because Harbor-process agents (terminus-2 calls LiteLLM in-process) would produce orphan traces. A local E2E with all instruments on produced only the trial roots.
- Each datapoint's `task_id` is Harbor's `task_name`, so a task's attempts (`-k N`, distinct trial names) are Trials of one Laminar Task and compare across jobs by name. Datapoints are keyed by `trial_name`: Harbor retries reuse the trial name, so a retry upserts the same datapoint id / index with a new trace. Upload order matters (`save_datapoints` upserts by id): every upload of a trial chains after its previous one (`_TrialState.last_upload`), across retries too, so an earlier attempt can never overwrite a retry. A trial without rewards scores 0 for every reward key seen so far (Harbor's metrics count it as 0, so averages match). Laminar averages a score only over datapoints that have it, so such trials keep their datapoint in `_TrialState.unscored_datapoint` and are re-saved (whole-row replace, chained like any upload) whenever a later trial reveals a new reward key; the `reward` fallback used before any key is known gets dropped then. Cancelled trials get no scores, even if a verifier result arrived. END always fires after CANCEL.
- If `Laminar` is already initialized (e.g. an app runs Harbor in-process), spans go through its existing tracer, so the plugin adopts its key and HTTP endpoint (`get_project_api_key()` / `get_base_http_url()`) for the evaluation client and rejects a different `project_api_key`. Otherwise datapoints would link to traces exported to another project. Tests: conftest initializes Laminar with `test_key`, so patch `Laminar.is_initialized` to exercise the fresh-init path.
- Local E2E: harbor's docker environment is unavailable in the sandbox, so use a scratch `BaseEnvironment` subclass that runs commands on the host with `-n 1`, and a tiny agent that writes an ATIF trajectory. `Laminar.initialize` ignores ports in `base_url`, so pass `--pk http_port=8000 --pk grpc_port=8001` for a local stack (default gRPC port is 8443). The sandbox shell exports `PORT=3005`, which overrides `.env` — start the app-server/frontend with an explicit `PORT=`.
- Real-dataset E2E: `pip install daytona` in the harbor venv and run with `-e daytona` (needs `DAYTONA_API_KEY`). Unset `LMNR_BASE_URL` and pass `--pk base_url=https://api.lmnr.ai` when targeting cloud, because a `.env` in the cwd pointing at localhost wins otherwise. Agents installed inside the sandbox (codex, claude-code) can't reach a localhost LLM proxy, so they need a real provider key; harbor-process agents (terminus-2) can use it. Harbor's default `RetryConfig.exclude_exceptions` (AgentTimeoutError, VerifierTimeoutError, ...) beats `--retry-include`, so to exercise retries, use an error such as a nonexistent model (`NotFoundError`) with `-r 2`.
- Lint: `uv run ruff check` / `uv run ruff format` (same config as CI; BLE001 is ignored repo-wide in `pyproject.toml`).
- **The plugin asks agents to write an lmnr-atif trajectory**: in `on_job_start` it does `setdefault("LMNR_TRAJECTORY_PATH", AGENT_TRAJECTORY_PATH)` on every `job.config.agents[*].env`, where `AGENT_TRAJECTORY_PATH` is `/logs/agent/trajectory.json` (`EnvironmentPaths.agent_dir`, i.e. the trial's `agent/` dir that `_trajectory_path` reads). An agent using Laminar's SDK then runs local-only (no API key in the sandbox) and the plugin replays its file under the trial. Three things make this work, and `test_agent_trajectory_reaches_harbor_agents` pins them against real harbor:
  - It has to happen in `on_job_start`. Harbor copies `AgentConfig.env` into the agent object when it creates a trial, before any trial hook fires.
  - The trial configs `Job.create` already built share the `AgentConfig` objects (pydantic doesn't copy model instances passed as fields).
  - `trajectory_spans=false` skips it, and so does a failed evaluation start: a local-only agent whose file nobody reads would lose its spans.
  A user's own `--ae LMNR_TRAJECTORY_PATH=...` wins. Harbor's own agents (claude-code, codex, terminus-2) write their own `trajectory.json` there but don't run our SDK, so the variable does nothing for them.
- The plugin calls `Laminar.initialize(write_trajectory=False)`. `LMNR_TRAJECTORY_PATH` is meant for the agent, and in the Harbor process it would make the plugin local-only, so no trial spans would reach Laminar. Don't go back to popping the variable from `os.environ`: `from_env` also reads a `.env` in the cwd, which popping misses.
- **`runner_modules`** (`--pk runner_modules=<JSON list>`, from describe's `modules`, `agent/eval.py` datasets only): a remote run's `hosted_metadata` gets `runnerModules`, the ones NOT under `<suitePath>/agent/` (the Files view shows that folder already), so the Files view's `runner/` folder shows shared runner code (`evals/_shared/`). Absolute paths and `..` segments are dropped; the list is small, so a `--pk` value, not a file like `task_hashes_file`.
- **Remote runs link the evaluation to the uploaded evals folder.** When both `LMNR_EVAL_UPLOAD_ID` and `LMNR_EVALS_ROOT` are set (only the remote-run orchestrator sets them; read from `os.environ`, not `from_env`, so a `.env` can't fake one), `evals.init` gets `hosted_metadata={"uploadId", "suitePath"}` (`suitePath` = Harbor's cwd, the suite dir, relative to the root) and each datapoint's metadata gets `task_path` (the task dir relative to the root). Tasks outside the root (git/registry datasets, `../` tasks) get no `task_path`: they aren't in the archive. The server stores it in `evaluations.hosted_metadata` (lmnr `docs/internal/hosted-evals.md`).
- **Eval datasets (`lmnr-cli eval run`, LAM-2562):** the CLI passes `--pk dataset=<[dataset] name>` (Harbor's `org/name`, from `tasks/dataset.toml`) and `--pk task_hashes_file=<json>` (`{task dir name: {"name": <[task] name>, "hash": <Harbor content hash>}}`), only when the dataset folder has a `dataset.toml`. `evals.init` gets `dataset_v2_id` (→ `evaluations.dataset_v2_id`). A trial whose task dir name (`event.config.task.get_local_path()`'s basename) is in the file gets `task_version_hash` on every datapoint save (→ ClickHouse `evaluation_datapoints.task_version_hash`) plus `metadata.dataset_task = <[task] name>`; the frontend finds the version in Laminar from (evaluation dataset, `dataset_task`, hash). Keyed by dir because that is Harbor's task id for local tasks; the name comes from the file so the plugin never parses `task.toml`. The hashes come from a file, not a `--pk` value: a single argv string is capped at 128 KiB on Linux, which a dataset of ~1500 tasks would exceed. An unreadable file or a malformed entry only warns / is skipped.
