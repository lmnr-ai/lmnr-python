# One-file eval runner (`src/lmnr/evals/`)

Design: LAM-2588 (Linear doc "LAM-2588 design: one-file eval runner, services, mocks" and its phase plans). A dataset is `evals/<dataset>/agent/eval.py` with one `EvalRunner` subclass; `lmnr-cli eval run` runs it through Harbor with the adapters in `lmnr.integrations.harbor.runner` (`integrations/harbor/AGENTS.md`).

- **Never import `harbor` here**, not even under `TYPE_CHECKING` in a way that runs: the mock server imports `eval.py` inside the container, where only `lmnr` is installed (mock server). The Harbor environment is duck-typed (`context.Environment`: `exec`, `upload_file`, `upload_dir`, `download_file`). `tests/test_evals.py::test_lmnr_evals_never_imports_harbor` pins it, and the tests drive `ctx` with a `FakeEnvironment` that records calls.
- Modules: `runner.py` (`EvalRunner`, `secret`, validation incl. services, `self.service(...)` / `self.mirror(...)`, loading `eval.py` by path), `context.py` (`Case`, `Container`, `Context` / `AgentContext` / `VerifyContext`, `ArtifactSaver`, `normalize_rewards`), `image.py` (the `Image` builder, `compile_image`, the `ImageContributor` protocol), `services/` (`Service` + lifecycle helpers in `base.py`, `bundle.py` shell for bundle stages, `postgres.py`, `clickhouse.py`, `valkey.py`), `mirrors/` (`Mirror`, `rystic.py`), `fixtures.py` (`case_fixture`, seed resolution), `readiness.py` (`port` / `http` / `file` / `cmd`), `mocks/` (`mock.py`: the user-facing API, re-exported as `lmnr.evals.mock`; `host.py`: declaration → `MockSpec`, handler refs, server start / collect; `server.py`: the in-container server; `calls.py`: `ctx.mocks`; its `__init__.py` stays empty, so import the modules by path like `bundle`), `layer.py` (the Laminar layer), `relay.py` (in-container helpers, stdlib only), `describe.py` (`python -m lmnr.evals.describe agent/eval.py` for lmnr-cli), `paths.py` (where relative paths resolve, `caller_site` provenance, the evals root on `sys.path`, the runner's module files), `artifacts.py` (`Artifact`, validation, `ctx.artifacts`), `errors.py` (`EvalConfigError`, `CommandError`, `CommandTimeout`, `ExecResult`; `ExecResult` lives there so `errors` ↔ `context` isn't an import cycle). Import `bundle` helpers by module path (`from lmnr.evals.services.bundle import ...`): `from lmnr.evals.services import bundle` makes pyright report a cycle through `services/__init__`.
- **`describe` JSON is versioned** (`DESCRIBE_VERSION = 1`, top-level `"version"`); lmnr-cli (`commands/eval/eval-py.ts`, `DESCRIBE_VERSION`) rejects other versions. Add fields as optional; bump only for incompatible changes, in both repos. stdout is the JSON only: the user module's prints are redirected to stderr while it is imported. Exit 2 = `EvalConfigError`, 1 = import error (traceback on stderr). A single `image` is named `<dataset folder>-evals`; describe always adds the Laminar layer, so its images are always `generated` (the `registry` / `dockerfile` kinds below only come out of `compile_image` without contributors, i.e. in tests).
- **Shared runners** (main doc 2.1.2): any folder in the evals root that isn't a dataset (convention `evals/_shared/`) holds shared Python, and `eval.py` subclasses a runner from it (`class RefundsEval(SupportRunner): pass`). `load_module` appends the evals root (`<root>/<dataset>/agent/eval.py` → `<root>`) to `sys.path` before importing `eval.py`, for describe and the Harbor adapters alike (appended, so a folder there never shadows an installed package). `find_runner` counts only classes whose `__module__` is the `eval.py` module, so an imported base class never makes two. Shared modules must not import Harbor either (the mock server imports them in the container).
- **Relative paths resolve against the file that declares them** (`paths.caller_dir`: the first stack frame outside `lmnr/evals/`), so a shared runner's paths work from every dataset. `Image.from_dockerfile` captures it at call time (`FromDockerfile.base_dir`, from the class body's frame); `ctx.container.run_file` / `.copy` look it up in `_host_path`, which must run before the coroutine's first `await`: a coroutine's frame links to its caller only until it first suspends. A coroutine started as its own task (`asyncio.gather(ctx.container.run_file(...))`) has the event loop as caller (`asyncio/` frames), so it falls back to `eval.py`'s dir (`Container._runner_dir`). So a shared runner that wants its own scripts calls `run_file` from one of its methods (a `submit_ticket()` helper on the runner); a dataset's `eval.py` calling `run_file("x.py")` looks next to itself. Tests therefore pass absolute paths when they call `ctx` from the test file itself (it would resolve against `tests/`); `test_shared_runner_*` cover the relative case from a subclass in another folder.
- describe's `modules` (`paths.loaded_modules`): every module in `sys.modules` whose file is under the evals root, relative to it, `eval.py` included, skipping `site-packages` / dot dirs (an in-root venv). lmnr-cli passes it to the plugin (`runner_modules`) for the Files view; `start_mock_server` uploads these files into the container.
- **Names say where things run and what they do** (renamed in review of lmnr-python#453, before release; keep it that way): container calls are all under `ctx.container` (`sh`, `run_file`, `service`, `wait_for`, `copy`, `write_file`, `read_text`, `read_json`), and everything else on `ctx` is read on the host (`case`, `model`, `env`, `logger`, `secrets`, `mocks`, `state()`, `verifier_mode`, `result()`, `artifacts`). Agent phase: `ctx.set_result(**fields)` writes, `ctx.result()` reads (verify has no `set_result`), `ctx.artifacts.save(path, name)` (`ArtifactSaver`); verify: `ctx.artifacts` reads (`Artifacts`). Runner attributes: `run_command` (not "entrypoint", which reads as Docker's), `new_task_toml` (written only into tasks without a `task.toml`), `grade_with_test_sh: bool` (Harbor's default verifier runs each task's `tests/test.sh` in the container instead of `verify()`; replaces the old `verify = "task"` string overriding the method; defining both is an error). describe reports `new_task_toml` and `grade_with_test_sh` under those names.
- `EvalRunner` attributes are class-level (`ClassVar`).
- **Env and secrets.** `secrets` are names; lmnr-cli resolves them like required `${VAR}`s and puts the values in the Harbor process env, so `VerifyContext.secrets` reads `os.environ`. `env` values are strings or `secret(name)` (must be in `secrets`); describe renders a secret as `${NAME}` and lmnr-cli writes `env` into `agents[].env`. In the agent phase Harbor already applies `agents[].env` to every command through `scoped_exec_env`, which **wins over per-exec env** (`BaseEnvironment._merge_env`: persistent < per-exec < scoped), so `LaminarAgent` only adds runner env keys Harbor doesn't set (a hand-written harbor.yaml), and a `ctx.container.sh(env=...)` can't override an `agents[].env` key. The verifier container gets the runner env (secrets read from `os.environ`) plus Harbor's verifier env (`[verifier.env]`, `verifier.env`), which is what `test.sh` would get.
- **`ctx.set_result(**fields)` is sync** and writes `result.json` in the trial's host `agent/` dir (`AgentContext.host_logs_dir` = the agent's `logs_dir`). Harbor syncs that dir with `/logs/agent` (bind mount locally, `_upload_agent_logs` after the run for remote envs), and `VerifyContext.result()` reads it from `trial_paths.agent_dir` in both verifier modes. `LaminarAgent.populate_context_post_run` copies it into `AgentContext.metadata`, which the plugin uses as executor output when there's no trajectory message.
- Commands: `user="agent"` maps to `None` (Harbor's default user for the phase: the task's agent user, or the verifier user), `"root"` passes through. **`sh` and `run_file` run through `relay.py exec`** (`Container._run`), because Harbor's environments differ underneath: local Docker (`bash -c`) merges stderr into stdout and raises `RuntimeError` on `timeout_sec`; lmnr-cli's hosted env (`timeout N bash -c`) keeps them apart and exits 124. The relay runs the command with `bash -c` (bash from the command's `PATH`, else `relay.BASH_PATHS`, so a runner `PATH` without `/usr/bin` doesn't silently switch to `sh`; `sh -c` only without bash) as a child in its own process group (env, cwd and user are the ones Harbor gave the relay), captures stdout and stderr apart as bytes (UTF-8, `errors="replace"`), and on timeout kills the group and reports `timed_out` with the output so far. It prints ONE line, `@@lmnr-relay-result@@ <json>` (`relay.format_result` / `parse_result`; the last marker wins, so a shell warning merged in before it doesn't matter, and the rest of its line must parse as JSON) and nothing else. The JSON escapes every `@` (`\u0040`), so the marker occurs only once: `json.dumps` leaves `@` alone, and a command (the agent, which can read `/opt/lmnr`) printing the marker otherwise put a forged frame inside `stdout` that `rfind` picked over the real one. Harbor's `timeout_sec` is the command's + `EXEC_TIMEOUT_MARGIN_SEC` (30), so the relay's fires first; a timeout raises `CommandTimeout(TimeoutError)` with the partial `ExecResult` (exit 124) whatever `check` is; no frame raises with the raw output's tail. One `exec` per command plus the payload upload; the payload is removed by a second root `exec` only when the relay reports `stdin_unlinked: false` (its `fstat(0).st_nlink`: a non-root user can't delete root's file in sticky /tmp). The raw path (`Container._exec`) is for the runner's plumbing only: the relay launches, mkdir / chmod / rm around uploads, and `service`'s start, which returns at once (only its pid is read; its log tail is read with `2>/dev/null`). Everything else, services', mirrors' and the mock server's helpers included, goes through `sh`. `wait_for` / `service` readiness checks run in ONE exec as `relay.py wait` (Python in the Laminar layer, no bash, curl or `/dev/tcp` needed). `run_file` uploads to `/tmp/lmnr-<hex>/`, `chmod -R a+rX` as root, runs (shebang → direct, `.py` → `python3`, else `bash`) and `rm -rf`s it in a `finally`. `service` starts `mkdir -p <logs_dir> || exit 1; nohup sh -c '<cmd>' > <logs_dir>/<name>.log 2>&1 &` (`/logs/agent` in the agent phase, `/logs/verifier` in verify); only `nohup` may be backgrounded (`mkdir ... && nohup ... &` backgrounds a subshell that keeps the exec's stdout open, which hangs any environment that reads to EOF). The readiness check runs with the same `env` as `cmd` (a `Service.custom` bundle's `LD_LIBRARY_PATH` must reach a `ready` that calls the bundled binary). `relay.py wait` exits 2 as soon as the pid dies, so a crashing service fails fast with its log tail; "dies" includes a zombie (`/proc/<pid>/status` `State: Z`), because Harbor's containers run `sleep infinity` as PID 1, which never reaps, and `kill -0` succeeds on a zombie.
- **Naming: "host" and "container", never "local" / "remote" / "upload"** in the `ctx` API (`ctx.container.copy(host, path)`): "remote" already means `lmnr-cli eval run --remote`, where the host is Laminar's orchestrator sandbox, not the user's machine.
- **Artifacts** (main doc 2.5.1, Harbor 0.25.0 `trial/artifact_handler.py`): `EvalRunner.artifacts` (container paths or `Artifact(source, destination, exclude)`, Harbor's `ArtifactConfig` without `service`) goes to describe's `artifacts` and lmnr-cli writes it into the job config's `artifacts`; `validate_artifacts` repeats Harbor's rules (no `..`, relative `destination`, not `manifest.json`) so a bad entry fails in describe. Harbor collects them (plus `/logs/artifacts/`, always) after the agent phase in BOTH verifier modes, before the verifier runs. Host layout under `<trial>/artifacts/`: an entry with a `destination` lands there, any other at its container path without the leading `/` (`/logs/artifacts/x` → `artifacts/logs/artifacts/x`). In `separate` mode each one is uploaded back into the grading container **at its original source path** (not under `/logs/artifacts/`, whatever the destination); only the convention folder maps to the verifier's `/logs/artifacts/`. `ctx.artifacts` (`Artifacts`, verify) reads the host dir: absolute paths are container paths, mapped through the most specific (deepest) declared source that holds them, since Harbor collects nested sources separately (`/srv` → `all/` with `exclude`, `/srv/db` → `db/`): its `destination` if it has one, else the mirrored path, relative ones are under `artifacts/` (`list()` returns those, without `manifest.json`). `ctx.artifacts.save(path, name)` (agent phase, `collect`) is `rm -rf` + `cp -a` + `chmod -R a+rX` as root into `/logs/artifacts/<name or basename>`, so the runner's copy replaces anything the agent planted.
- **Host vs container:** `eval.py` is imported on the host (describe, then the Harbor adapters), and every phase's Python runs there; only `ctx.container` commands and `run_file` scripts run in the container. So what `eval.py` or a shared runner imports must be installed next to Harbor (evals root `pyproject.toml`, or a PEP 723 block), and what the app or a container script needs belongs in the image.
- Default `setup` runs the case's `environment/seed.py` / `seed.sh` / `seed.bash` (or another `seed.*` with a shebang); `seed.json` and other data files are not scripts.
- **No vendored LLM judge** (decided in review of lmnr-python#453: nothing we ship is powered by LiteLLM, and the alternative isn't chosen yet). A judge is the user's own function called from `verify()`: it runs in the Harbor process, so it can use any SDK installed next to Harbor: the evals root's `pyproject.toml` `[project] dependencies` (recommended) or `eval.py`'s PEP 723 block (optional), which lmnr-cli passes to uvx (`pythonRequirements` in its `harbor.ts`), `ctx.secrets` for keys, `ctx.result()` / `ctx.case.expected()` / `ctx.artifacts` / `ctx.container.read_text` for inputs, and `@observe` for its own span; the plugin instruments provider SDKs under the verifier span. `examples/agent-evals` shows one (anthropic `messages.parse`). Keep the `ctx` primitives sufficient for that rather than adding a judge helper.
- `Secrets.__repr__` prints names only (`set=[...]`, `unset=[...]`), never values: `ctx` objects end up in logs and tracebacks.
- Test with `uv run pytest tests/test_evals.py` (no Harbor) and the adapter tests in `tests/test_harbor_runner.py` (Harbor, see `integrations/harbor/AGENTS.md`).

## Images and services (LAM-2588 phase 2)

- **`Image` is an immutable builder** (Modal-style): a base (`from_dockerfile`, `from_registry`, `debian_slim`, `python` = `python:<v>-slim-trixie`, `uv_python` = astral's `ghcr.io/astral-sh/uv:python<v>-trixie-slim`, `node` = `node:<v>-trixie-slim`) plus `Step`s; every method returns a new `Image`, so variants (`base.apt_install(...)`) share the base's steps and Docker layers. Host paths are resolved to absolute ones when the step is declared (`caller_site()`, the first frame outside `lmnr/evals/`), so a shared runner builds the same from every dataset; container paths must be absolute. Missing files fail in `compile_image` (describe exit 2), not at import.
- **`compile_image(image, contributors, root=, fallback_dir=)`** → `CompiledImage`: a bare registry ref stays `{"kind": "registry"}`, a bare Dockerfile stays `{"kind": "dockerfile"}` (phase 1 shapes), anything with steps or services becomes `{"kind": "generated", "dockerfile_text", "context", "ignore_file"?}`. Every kind carries `steps` (`[{origin, step}]`) for `lmnr-cli eval describe`. Order: service bundle stages, the base, service installs, user steps, `WORKDIR /case` (builder images only, unless `.workdir()`). Steps use BuildKit features: `RUN --mount=type=bind` for requirements / `uv sync` inputs (nothing left in the image, cache keyed on file content), heredoc `RUN <<'EOF'` for bundle scripts, `COPY --from=<image>` for uv (`UV_IMAGE`, pinned). `uv_sync` installs into the image's Python (`UV_PROJECT_ENVIRONMENT=$(python3 -c 'import sys; print(sys.prefix)')`, `--no-install-workspace`, `UV_PYTHON_DOWNLOADS=never`).
- **`pnpm_install(dir, dst, version=None)`** is three lines: `npm install -g pnpm@<v>` (its own layer, kept across lockfile changes; the version is the argument, else package.json's `packageManager` minus its `+sha512...` suffix, else `PNPM_VERSION`), `COPY` of `package.json` + `pnpm-lock.yaml` (+ `pnpm-workspace.yaml`, which holds settings such as `allowBuilds` / `onlyBuiltDependencies`), then `pnpm install --frozen-lockfile --store-dir /tmp/pnpm-store && rm -rf /tmp/pnpm-store*`: the store is on the layer's filesystem, so node_modules hard-links it and deleting it in the same `RUN` keeps one copy. `.npmrc` is bind-mounted, never copied (it can hold a registry token; BuildKit removes the mount stub). A `pnpm-workspace.yaml` with `packages:` is refused with a hint (a frozen install needs every member's package.json; use `from_dockerfile` + `pnpm fetch`). pnpm >= 11 FAILS an install whose dependencies have unapproved build scripts (`ERR_PNPM_IGNORED_BUILDS`): the project's `pnpm-workspace.yaml` must decide them (`allowBuilds: {esbuild: false}`), as `examples/agent-evals` does. pnpm 12 reads lockfile v9 written by pnpm 10.
- **Build context** of a builder image: the deepest folder holding every added host path (a file counts as its folder); without any, the folder of the file that declared the base. NOT the declaring files' folders too, as the plan said: a subclass declared far away (tests, another drive) pushed the context to `/`. A `from_dockerfile` image keeps the user's context (their `COPY` lines are relative to it) and every added path must be inside it.
- **Composition with `from_dockerfile`** (`_compose`, the single place where contributors meet a Dockerfile, so the Laminar layer works on both kinds): parser directives (`# syntax=`, `# escape=`, `# check=`) stay first, then `# from <Dockerfile> (<class>)`; the last `FROM` gets `AS lmnr-app` unless it has a name; then our stages, `FROM <that stage>`, `USER root` if the last stage ends as a non-root `USER`: its own last `USER` line, else the one of the earlier stage it builds on (`FROM base`, aliases case-insensitive; `_stage_user`), restored at the end. An external base's default user isn't visible in the text, so it isn't handled, services, steps. The user's `<Dockerfile>.dockerignore` is passed as `ignore_file`.
- **Generated text must be deterministic**: it is Docker's cache key and lmnr-cli dedups images by its content (minus comment lines). Anything random (temp names) belongs in runtime commands, never in build lines; heredoc delimiters come from the text's hash (`services.base.heredoc`). `test_compiling_is_deterministic` pins it.
- **Provenance**: one comment above each step: `# _shared/support.py:12 (SupportRunner)` (each call in a chained expression reports its own line; the owner is the class body's `__qualname__`, absent at module level), `# service: Postgres 16 (_shared/support.py:15)`. Paths are relative to the evals root (`os.path.relpath`, so `../app` when outside it).
- **Golden tests**: `tests/test_evals_images.py` compiles images declared in `tests/data/evals_project/evals/_shared/images.py` (a file of its own so line numbers in comments stay put) against `tests/data/evals_images/*.Dockerfile`; after an intended change `LMNR_UPDATE_GOLDEN=1 uv run pytest tests/test_evals_images.py` and review the diff.
- **How a service gets into the image** (decided for phase 2, reviewed against the vendor-download alternative): a bundle stage `FROM <official image>:<pinned tag>` copies the binaries plus every shared library `ldd` reports (except glibc's own, `bundle._GLIBC`) into `/bundle/`, laid out as in the final image; the final image does `COPY --from=svc-<name> /bundle/ /`, then one `RUN` (`bundle.install_check`) that checks glibc (bundle records the source's glibc at `/usr/local/share/.glibc-required-<name>`, NOT under `/tmp`: COPY would reset the image's `/tmp` to 0755 and break later `apt_install`), that `runuser` exists, and creates the service's OS user. Binaries run through `/usr/local/bin` wrappers that prepend the bundled libs to `LD_LIBRARY_PATH`, so the app's own libraries are never shadowed. Why not vendor downloads: Postgres has no official Linux tarballs (PGDG is apt-only, and apt in the final image re-runs on every app change in a composed Dockerfile); Valkey's tarballs exist only per full version and per Ubuntu release and still link libssl / libsystemd, so they need the same library bundling; ClickHouse's tgz needs the exact full version. Docker tags give a pinned version (`16`, `16.4`), the right architecture (`--platform`), digest-keyed caching and the `source=` override (`pgvector/pgvector:pg16-bookworm`) for free. Sources are pinned to `-bookworm` (glibc 2.36): that runs on `python:*-slim-bookworm`, trixie and Ubuntu 24.04; Ubuntu 22.04 (2.35) needs `source=` from an older distro. Alpine fails the build with a hint. ClickHouse's binary is static apart from glibc, so its stage copies one file and records 2.17. `install_check` checks `runuser` only when it creates users (`Service.custom` and the migrations tool don't use it); `alternative=` replaces the "pass source=" hint.
- **ClickHouse migrations**: `migrator="clickhouse-migrations"` (default) runs the npm CLI of that name (`MIGRATIONS_TOOL_VERSION`, pinned) from a second stage `FROM node:24-trixie-slim AS svc-<name>-migrations`: `npm install --prefix /usr/lib/clickhouse-migrations`, plus that image's `node` and its libs (libstdc++, libgcc_s), behind a wrapper at `/usr/lib/clickhouse-migrations/bin/clickhouse-migrations`, outside PATH so it never shadows the app's Node. Its glibc is checked separately, with `migrator="clickhouse-client"` as the hint, because ClickHouse itself only needs 2.17. The stage records what the bundle needs, not trixie's 2.41 (`record_glibc_needed`: the newest `GLIBC_2.x` string in the bundled node + libs; glibc's own libs aren't bundled): 2.38, from trixie's libstdc++ (node itself needs 2.28). So the default migrator runs on trixie and Ubuntu 24.04 (2.39) but not on bookworm (2.36) apps, which need `migrator="clickhouse-client"` (`test_services_on_base` switches on bookworm; `test_clickhouse_migrations_on_bookworm_fails_the_build_with_a_hint`). Moved from `node:24-bookworm-slim` on request in LAM-2602's review. It runs `migrate --host=http://127.0.0.1:<http_port> --user=default --password= --db=<database> --migrations-home=<tmp>` (commander accepts the empty password), records versions in `_migrations` in the database, and only takes `<positive int>_*.sql` names: `validate` lists misnamed files with the switch as the fix. `"clickhouse-client"` is the old `find | sort -V | clickhouse client --multiquery` loop. `config=` / `users=` (`.xml` / `.yaml`) are COPYed into `/etc/clickhouse-server/config.d/` / `users.d/` after the install check, so ClickHouse merges them over the generated files (theirs win); they are `host_paths`, so they widen the build context.
- **Service runtime**: every built-in binds 127.0.0.1, runs as its own OS user through `runuser -u <user> --` (started as root, so the shell redirect can write `/logs/agent/<name>.log`), and uses the distro-standard paths (`/var/lib/postgresql/data`, `/etc/clickhouse-server`, `/var/lib/valkey`), nothing named lmnr. Postgres: initdb at start (`--no-locale -E UTF8 -A trust`), `fsync` / `synchronous_commit` / `full_page_writes` / `jit` off, `/var/run/postgresql` created at start (Debian's compiled-in socket dir), bundled `zoneinfo` copied in only when the image has no tzdata (`debian:trixie-slim`), `chmod 700` on the data dir (a `migrate_at="build"` dir comes out of `COPY --chown` as 0755). Database / role / extensions / `init_sql` are one idempotent psql script; migrations are `find -maxdepth 1 -name '*.sql' | sort -V`. `migrate_at="build"` runs them in a second stage `FROM svc-postgres` with the source image's own server and copies only the data dir (`COPY --chown=postgres:postgres`, never parents: `--chown` would chown them too).
- **Commands from services** go through `services.base.run_script` (a temp script uploaded with `write_file`, run with `bash`, removed in the same exec) so SQL size isn't limited by argv; helpers run as root. ClickHouse snapshots run each `SELECT ... FORMAT JSONEachRow` through `relay.py rows`, which writes the JSON array, validates every line and fails on a non-zero exit (the phase 2 `{ echo '['; clickhouse ... | sed ...; }` script saved `[]` for a failed query unless it set `pipefail`; a separate verifier grades that as an empty table). Built-in URLs percent-encode user, password and database (`{user}` / `{password}` placeholders stay raw). Live helpers call `require_live`, which raises in a `separate` verifier (`ctx.verifier_mode`); `ctx.state(service, table)` reads `/logs/artifacts/state/<service>/<table>.json` through `ctx.artifacts` and works in both modes.
- **Lifecycle** (`services.base.start_services` / `snapshot_services`, called by `LaminarAgent`): all services in parallel, each start → ready → migrate → seed; their `env()` goes to `ctx.env` and every later command (minus keys Harbor's `agents[].env` sets, which wins anyway); snapshots run after `collect`, also when `collect` or `run` raised. `LaminarVerifier` derives the mode like Harbor (`environment_mode`, else `separate` iff the verifier has an `environment`) and adds services' env only in `shared` mode. `validate` rejects duplicate names, shared ports and env keys set by two services or by a service and `EvalRunner.env`; `"latest"` warns.
- **Mirrors**: `Mirror(Service)` adds `seed` (uploaded to a random `/tmp/.<hex>/`, loaded by the provider's `load_seed` after start, deleted, all before `setup`), `url`, `state(ctx)` (live, or `state/<name>/state.json` with `snapshot=True` in separate mode, `Mirror.saved`) and `get` / `request` (HTTP from inside the container through `context.relay_http` → `relay.py http`; `request` raises on status >= 400). There is no shell fallback for any relay command: phases 1-4 release together and every eval.py image has the layer. Default ports come from a CRC of the name (18000-19999). **Rystic** (`mirrors/rystic.py`) follows the real CLI (0.0.93: `rystic pull --help`, `run --help`, `rystic help control-plane`, all readable without a key) and lmnr-private's hosted-evals proxy (`docs/internal/hosted-evals.md`, "Rystic service simulators"), not the plan's guessed surface. **Access**: every trial sandbox Laminar creates (`sandboxes::create_trial`) gets `RYSTIC_TOKEN` (`rys_` + 43 chars, per trial), `RYSTIC_RELEASE_ENDPOINT` and `RYSTIC_LEASE_URL` (the app-server's proxy) as Daytona sandbox env, so every command inherits them; lmnr-cli's `lmnr_hosted_env.py` runs `user="root"` commands as `su root -s /bin/bash -c` (no login), which keeps that env. Users must never set `RYSTIC_TOKEN` in `env` (it would override the trial's). Local runs use the user's own key, passed with `lmnr-cli eval run --env RYSTIC_TOKEN` (no `RYSTIC_RELEASE_ENDPOINT`, so the CLI talks to rystic.ai); `examples/agent-evals` `billing` was run that way against the real CLI and twin (LAM-2606). `start` checks the env first (`ACCESS_CHECK`): no token raises `NO_ACCESS` (how to pass a key) before the pull, instead of the CLI's exit 3. **CA certificates**: the CLI is a Go binary that reads the system's CA bundle, and slim images (`node:*-trixie-slim`, `debian:*-slim`) have none, so `rystic pull` failed TLS verification (`x509: certificate signed by unknown authority`, found running the example on `node:24`; remote runs would fail the same way). The bundle stage installs the real binary in `/usr/local/lib/rystic/` next to the stage's `ca-certificates.crt`, and `/usr/local/bin/rystic` is a `sh` wrapper (`WRAPPER`) that sets `SSL_CERT_FILE` to it only when `SSL_CERT_FILE` is unset and the image has neither `/etc/ssl/certs/ca-certificates.crt` nor `/etc/pki/tls/certs/ca-bundle.crt`. The image gets only the CLI (static binary, vendor `install.sh` with a pinned `RYSTIC_VERSION` in a `curlimages/curl` stage, no key needed, built on the user's machine and pushed); each trial runs `rystic pull <product>-twin --version <v>` (installs to `$RYSTIC_HOME/twins/<product>/<v>` and marks it current), then `rystic run <product> --name --port [--clock]` in the foreground, booting an EMPTY workspace (no `--scenario`). Control plane: readiness `GET /_rystic/routes` (every plan); `POST /_rystic/seed` MERGES a register map (or lands a scenario document) and answers 204 with no body; `GET /_rystic/inspect` is the whole state; `calls()` is `GET /_rystic/calls?summary=1&writes=1` unwrapped to its `calls` list (the response is `{calls, dropped, epoch, total}`), also what the snapshot saves (`calls.json`, through `Mirror.snapshot_extras`: `Mirror.snapshot` writes every file, then runs one `chmod -R a+rX`, since an uploaded file's mode depends on the environment; a provider writing its own files after `super().snapshot()` skipped it); `settle()` long-polls `/_rystic/settle?quiet_ms=` and returns `{settled, idle_ms, last_call_seq, pending?}` (unsettled after its 30 s default `timeout_ms`). `state_view` / `state_set`, which those need, are on every plan, Free included; Free keys only run the Slack, Linear and GitHub twins. Every such assumption is a constant there. `tests/test_evals_services.py` runs the adapter against a fake `rystic` executable (Python HTTP server) with no curl or python on PATH; an autouse fixture points `RELAY_COMMAND` at the checkout's `relay.py`.
- **Docker tests** (`tests/test_evals_docker.py`, opt-in: `LMNR_EVALS_DOCKER=1 uv run pytest tests/test_evals_docker.py`, ~3 min cold): builds generated images for linux/amd64 on the acceptance bases (`python:3.13-slim-bookworm`, `debian:trixie-slim`, `ubuntu:24.04`) and drives the services through `ctx` over `docker exec` / `docker cp`; also `migrate_at="build"`, composition with a non-root `USER`, the Alpine hint, and `/tmp` keeping 1777. ## Mocks and the Laminar layer (LAM-2588 phase 3)

- **Protocol**: `spec/lmnr-mock/lmnr-mock.md` (version 1) + `cases/*.json` conformance cases, run by `tests/test_evals_mocks.py` against the reference server; lmnr-ts has a byte-identical copy (like `spec/lmnr-atif`), so change both together. The SDK side of function mocks (phase 4) is `src/lmnr/sdk/mock/AGENTS.md`. Function mocks: `POST {LMNR_MOCK_URL}/fn/<key>` → `respond` / `raise` / `passthrough` (404 unknown key, 500 `handler_error`, 400 bad request; SDKs must never fall back to the real call on failure). Arguments are positional in every language: the body's `args` is an array, `kwargs` an optional object (Python's keyword-only params and `**kwargs`; TS sends none), anything else is a 400; the handler gets `Call(key, args, kwargs, index)` and the call log `request` is `{"args", "kwargs", "lang"}` (`kwargs` defaulted to `{}`). HTTP mocks: the key is a base URL (host plus optional path), the runner sets `base_url_env` to `http://127.0.0.1:<port>/h/<host><path>`; those routes carry no token. Wrong token / unknown route = plain `404 Not Found`, so the server looks like any web server.
- **Isolation rules** (the agent must not be able to tell it's being evaluated or read the handlers): the server runs as root from a `chmod -R go=` temp dir `/tmp/.<hex>/` (handlers = the runner's `modules` copied as files, `fixtures/` = the case's `tests/fixtures/`, `c.json` config), which is `rm -rf`ed as soon as the ready file appears: handlers and fixtures stay in memory only. Process name `relay` (`prctl(PR_SET_NAME)`), command line `/opt/lmnr/venv/bin/python -I /opt/lmnr/relay.py serve /tmp/.<hex>/c.json`: **no `mock|eval|test|fixture` in any command line or path we create in the container**; the docker test greps `/proc/*/cmdline`. stdout/stderr go to `/dev/null` once bound (startup errors go to `T/e`, read back when the start fails). The call log and server log are fetched over HTTP in `collect` and written by the runner: `/logs/artifacts/mocks.jsonl` (`rm -rf` first, so a planted file is replaced) and the host `agent/mocks.log` (never written in the container during the run).
- **Relay input never goes through argv**: `context.relay` (and `Container._run` for `exec`) uploads the JSON payload to a temp file `/tmp/.<hex>` (no `mkdir`) and runs `{ rm -f F; RELAY cmd; } < F`, so URLs, tokens and SQL aren't visible in `ps`. `relay.py` is stdlib-only and launched by path (`/opt/lmnr/relay.py` is a 3-line `runpy.run_path` launcher into the installed `lmnr/evals/relay.py`): `import lmnr` takes ~3 s, so nothing on the relay path imports the package; `serve` imports `mocks.server` lazily. `-I` so the app's `PYTHONPATH` can't shadow stdlib modules. `relay.py http` (and so `wait`'s HTTP readiness) ignores proxy variables (`ProxyHandler({})`): every target is in the container, and urllib on Linux sends even 127.0.0.1 to `http_proxy` unless `no_proxy` lists it, so a trial env with a proxy broke health checks, collect and mirror requests (`test_http_ignores_proxy_variables`). Exit 127 from the launcher (also for `exec`: the command's own 127 is inside the frame) → the error says `/opt/lmnr` is missing (an image built without the layer).
- **Handlers** run in the server: one lock serializes every call (deterministic `index` / `calls` / `state`), async handlers run on one event-loop thread. `mocks.host.handler_ref` accepts only module-level functions defined in a module under the evals root (no lambdas, closures, methods): `eval.py` itself is loaded as `__runner__` by path, others by dotted module name with the evals root on `sys.path`. Whatever `eval.py` imports at top level must be importable in the layer's venv, hence `mock_dependencies` (pip specs, validated in describe); the example lists `anthropic` because its judge imports it. Handler kinds are a registry (`HANDLER_KINDS`, `python` only) so a TS handler kind can be added later. **Fixtures are read through `ctx.case` in both places** (`mocks.mock.FixtureReader`): `fixture_bytes` / `fixture_text` / `fixture_json` on the host `Case` (files) and the handler's `CaseInfo` (the in-memory copy), a missing one is `FileNotFoundError("The case ... has no tests/fixtures/<path>.")` in both; only the host has `fixture_path` (a `Path`, what services and `load_sql` take). Keep the two in step rather than adding a reader to one side.
- **Lifecycle** (`integrations/harbor/runner.py`): services → mock server (`start_mock_server`, after services so handlers can reach them, before `setup`) → `LMNR_MOCK_URL` + every `base_url_env` added to the env (minus keys Harbor's `agents[].env` sets) → setup / run / collect → service snapshots → `collect_mocks` (also after a failed or cancelled setup or run, `collect()` itself only after setup finished; always kills the server). A server that started but then failed its wait, port read or health check is killed by `start_mock_server` itself: the runner never got a `RunningMocks` to collect. `validate` rejects a `base_url_env` that `env` or a service also sets. Verify reads the log with `ctx.mocks.calls(key)` / `all()` / `unmatched()` (`MockCalls`; `KeyError` for an undeclared key).
- **The Laminar layer** (`layer.LaminarLayer`, an `ImageContributor` added to EVERY eval.py image; it is its own stage, so an app change only reruns the final `COPY`): stage `FROM debian:trixie-slim`, pinned uv, `uv python install 3.13` into `/opt/lmnr/python`, venv `/opt/lmnr/venv` with `lmnr==<describe's own version>` + `mock_dependencies` installed with `--python-platform "$(uname -m)-manylinux_2_36"` (`WHEEL_GLIBC`: the stage's glibc is 2.41, but the layer goes into every image, bookworm and Ubuntu 24.04 apps included, so uv must not pick a wheel built for a newer glibc; python-build-standalone itself needs 2.17), the launcher, then a trim (libpython.so, tcl/tk, idle, pip, ensurepip, test, tkinter...: 184 MB → 114 MB uncompressed; `examples/agent-evals` with `anthropic` as a mock dependency: 160 MB, 42 MB gzipped; strip saves only ~3 MB, not done) and a smoke test. Final image: `COPY --from=lmnr-layer /opt/lmnr /opt/lmnr` + a glibc-check `RUN`. Everything is under `/opt/lmnr`, nothing on PATH, so the app's own Python is untouched.
- **Which `lmnr` the layer installs**: describe's `--layer-lmnr=<spec>`; lmnr-cli passes `wheel` when `LMNR_EVAL_LMNR_SPEC` is a local checkout (it builds the wheel and passes `--build-context lmnr-dev=<dir>`, describe lists the context in `laminar_layer.build_contexts`), a git spec (`lmnr @ git+https://...`) as is. The stage apt-installs git when any requirement (`lmnr` or a `mock_dependencies` entry) contains `git+`. A git spec is cached by Docker by its text, so a moved branch needs `--no-cache` (known gap). Without the flag: the released `lmnr` version describe runs as.
