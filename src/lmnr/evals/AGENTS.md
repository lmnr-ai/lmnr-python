# One-file eval runner (`src/lmnr/evals/`)

Design: LAM-2588 (Linear doc "LAM-2588 design: one-file eval runner, services, mocks" and its phase plans). A dataset is `evals/<dataset>/agent/eval.py` with one `EvalRunner` subclass; `lmnr-cli eval run` runs it through Harbor with the adapters in `lmnr.integrations.harbor.runner` (`integrations/harbor/AGENTS.md`).

- **Never import `harbor` here**, not even under `TYPE_CHECKING` in a way that runs: later phases import `eval.py` inside containers where only `lmnr` is installed (mock server). The Harbor environment is duck-typed (`context.Environment`: `exec`, `upload_file`, `upload_dir`, `download_file`). `tests/test_evals.py::test_lmnr_evals_never_imports_harbor` pins it, and the tests drive `ctx` with a `FakeEnvironment` that records calls.
- Modules: `runner.py` (`EvalRunner`, `secret`, validation incl. services, `self.service(...)` / `self.mirror(...)`, loading `eval.py` by path), `context.py` (`Case`, `Container`, `Context` / `AgentContext` / `VerifyContext`, `ArtifactSaver`, `normalize_rewards`), `image.py` (the `Image` builder, `compile_image`, the `ImageContributor` protocol), `services/` (`Service` + lifecycle helpers in `base.py`, `bundle.py` shell for bundle stages, `postgres.py`, `clickhouse.py`, `valkey.py`), `mirrors/` (`Mirror`, `rystic.py`), `fixtures.py` (`case_fixture`, seed resolution), `readiness.py` (`port` / `http` / `cmd`), `describe.py` (`python -m lmnr.evals.describe agent/eval.py` for lmnr-cli), `paths.py` (where relative paths resolve, `caller_site` provenance, the evals root on `sys.path`, the runner's module files), `artifacts.py` (`Artifact`, validation, `ctx.artifacts`), `errors.py` (`EvalConfigError`, `CommandError`, `ExecResult`; `ExecResult` lives there so `errors` ↔ `context` isn't an import cycle). Import `bundle` helpers by module path (`from lmnr.evals.services.bundle import ...`): `from lmnr.evals.services import bundle` makes pyright report a cycle through `services/__init__`.
- **`describe` JSON is versioned** (`DESCRIBE_VERSION = 1`, top-level `"version"`); lmnr-cli (`commands/eval/eval-py.ts`, `DESCRIBE_VERSION`) rejects other versions. Add fields as optional; bump only for incompatible changes, in both repos. stdout is the JSON only: the user module's prints are redirected to stderr while it is imported. Exit 2 = `EvalConfigError`, 1 = import error (traceback on stderr). A single `image` is named `<dataset folder>-evals`; a registry image's task `docker_image` is its ref (lmnr-cli pulls it).
- **Shared runners** (main doc 2.1.2): any folder in the evals root that isn't a dataset (convention `evals/_shared/`) holds shared Python, and `eval.py` subclasses a runner from it (`class RefundsEval(SupportRunner): pass`). `load_module` appends the evals root (`<root>/<dataset>/agent/eval.py` → `<root>`) to `sys.path` before importing `eval.py`, for describe and the Harbor adapters alike (appended, so a folder there never shadows an installed package). `find_runner` counts only classes whose `__module__` is the `eval.py` module, so an imported base class never makes two. Shared modules must not import Harbor either (phase 3 imports them in the container).
- **Relative paths resolve against the file that declares them** (`paths.caller_dir`: the first stack frame outside `lmnr/evals/`), so a shared runner's paths work from every dataset. `Image.from_dockerfile` captures it at call time (`FromDockerfile.base_dir`, from the class body's frame); `ctx.container.run_file` / `.copy` look it up in `_host_path`, which must run before the coroutine's first `await`: a coroutine's frame links to its caller only until it first suspends. A coroutine started as its own task (`asyncio.gather(ctx.container.run_file(...))`) has the event loop as caller (`asyncio/` frames), so it falls back to `eval.py`'s dir (`Container._runner_dir`). So a shared runner that wants its own scripts calls `run_file` from one of its methods (`examples/agent-evals` `BillingRunner.submit_ticket`); a dataset's `eval.py` calling `run_file("x.py")` looks next to itself. Tests therefore pass absolute paths when they call `ctx` from the test file itself (it would resolve against `tests/`); `test_shared_runner_*` cover the relative case from a subclass in another folder.
- describe's `modules` (`paths.loaded_modules`): every module in `sys.modules` whose file is under the evals root, relative to it, `eval.py` included, skipping `site-packages` / dot dirs (an in-root venv). lmnr-cli passes it to the plugin (`runner_modules`) for the Files view; phase 3 uploads these files into the container.
- **Names say where things run and what they do** (renamed in review of lmnr-python#453, before release; keep it that way): container calls are all under `ctx.container` (`sh`, `run_file`, `service`, `wait_for`, `copy`, `write_file`, `read_text`, `read_json`), and everything else on `ctx` is read on the host (`case`, `model`, `env`, `logger`, `secrets`, `result()`, `artifacts`). Agent phase: `ctx.set_result(**fields)` writes, `ctx.result()` reads (verify has no `set_result`), `ctx.artifacts.save(path, name)` (`ArtifactSaver`); verify: `ctx.artifacts` reads (`Artifacts`). Runner attributes: `run_command` (not "entrypoint", which reads as Docker's), `new_task_toml` (written only into tasks without a `task.toml`), `grade_with_test_sh: bool` (Harbor's default verifier runs each task's `tests/test.sh` in the container instead of `verify()`; replaces the old `verify = "task"` string overriding the method; defining both is an error). describe reports `new_task_toml` and `grade_with_test_sh` under those names.
- `EvalRunner` attributes are class-level (`ClassVar`). `mocks` exists (empty) and raises "not supported yet" until phase 3.
- **Env and secrets.** `secrets` are names; lmnr-cli resolves them like required `${VAR}`s and puts the values in the Harbor process env, so `VerifyContext.secrets` reads `os.environ`. `env` values are strings or `secret(name)` (must be in `secrets`); describe renders a secret as `${NAME}` and lmnr-cli writes `env` into `agents[].env`. In the agent phase Harbor already applies `agents[].env` to every command through `scoped_exec_env`, which **wins over per-exec env** (`BaseEnvironment._merge_env`: persistent < per-exec < scoped), so `LaminarAgent` only adds runner env keys Harbor doesn't set (a hand-written harbor.yaml), and a `ctx.container.sh(env=...)` can't override an `agents[].env` key. The verifier container gets the runner env (secrets read from `os.environ`) plus Harbor's verifier env (`[verifier.env]`, `verifier.env`), which is what `test.sh` would get.
- **`ctx.set_result(**fields)` is sync** and writes `result.json` in the trial's host `agent/` dir (`AgentContext.host_logs_dir` = the agent's `logs_dir`). Harbor syncs that dir with `/logs/agent` (bind mount locally, `_upload_agent_logs` after the run for remote envs), and `VerifyContext.result()` reads it from `trial_paths.agent_dir` in both verifier modes. `LaminarAgent.populate_context_post_run` copies it into `AgentContext.metadata`, which the plugin uses as executor output when there's no trajectory message.
- Commands: `user="agent"` maps to `None` (Harbor's default user for the phase: the task's agent user, or the verifier user), `"root"` passes through. Docker execs run `sh -c`; `wait_for` / `service` readiness loops run in ONE exec wrapped in `bash -c` (they use `$SECONDS` and `/dev/tcp`), so the image needs bash. `run_file` uploads to `/tmp/lmnr-<hex>/`, `chmod -R a+rX` as root, runs (shebang → direct, `.py` → `python3`, else `bash`) and `rm -rf`s it in a `finally`. `service` starts `mkdir -p <logs_dir> || exit 1; nohup sh -c '<cmd>' > <logs_dir>/<name>.log 2>&1 &` (`/logs/agent` in the agent phase, `/logs/verifier` in verify); only `nohup` may be backgrounded (`mkdir ... && nohup ... &` backgrounds a subshell that keeps the exec's stdout open, which hangs any environment that reads to EOF). Its wait loop exits 2 as soon as the pid dies, so a crashing service fails fast with its log tail; "dies" includes a zombie (`/proc/<pid>/status` `State: Z`), because Harbor's containers run `sleep infinity` as PID 1, which never reaps, and `kill -0` succeeds on a zombie.
- **Naming: "host" and "container", never "local" / "remote" / "upload"** in the `ctx` API (`ctx.container.copy(host, path)`): "remote" already means `lmnr-cli eval run --remote`, where the host is Laminar's orchestrator sandbox, not the user's machine.
- **Artifacts** (main doc 2.5.1, Harbor 0.25.0 `trial/artifact_handler.py`): `EvalRunner.artifacts` (container paths or `Artifact(source, destination, exclude)`, Harbor's `ArtifactConfig` without `service`) goes to describe's `artifacts` and lmnr-cli writes it into the job config's `artifacts`; `validate_artifacts` repeats Harbor's rules (no `..`, relative `destination`, not `manifest.json`) so a bad entry fails in describe. Harbor collects them (plus `/logs/artifacts/`, always) after the agent phase in BOTH verifier modes, before the verifier runs. Host layout under `<trial>/artifacts/`: an entry with a `destination` lands there, any other at its container path without the leading `/` (`/logs/artifacts/x` → `artifacts/logs/artifacts/x`). In `separate` mode each one is uploaded back into the grading container **at its original source path** (not under `/logs/artifacts/`, whatever the destination); only the convention folder maps to the verifier's `/logs/artifacts/`. `ctx.artifacts` (`Artifacts`, verify) reads the host dir: absolute paths are container paths, mapped through the most specific (deepest) declared source that holds them, since Harbor collects nested sources separately (`/srv` → `all/` with `exclude`, `/srv/db` → `db/`): its `destination` if it has one, else the mirrored path, relative ones are under `artifacts/` (`list()` returns those, without `manifest.json`). `ctx.artifacts.save(path, name)` (agent phase, `collect`) is `rm -rf` + `cp -a` + `chmod -R a+rX` as root into `/logs/artifacts/<name or basename>`, so the runner's copy replaces anything the agent planted.
- **Host vs container:** `eval.py` is imported on the host (describe, then the Harbor adapters), and every phase's Python runs there; only `ctx.container` commands and `run_file` scripts run in the container. So what `eval.py` or a shared runner imports must be installed next to Harbor (evals root `pyproject.toml`, or a PEP 723 block), and what the app or a container script needs belongs in the image.
- Default `setup` runs the case's `environment/seed.py` / `seed.sh` / `seed.bash` (or another `seed.*` with a shebang); `seed.json` and other data files are not scripts.
- **No vendored LLM judge** (decided in review of lmnr-python#453: nothing we ship is powered by LiteLLM, and the alternative isn't chosen yet). A judge is the user's own function called from `verify()`: it runs in the Harbor process, so it can use any SDK installed next to Harbor: the evals root's `pyproject.toml` `[project] dependencies` (recommended) or `eval.py`'s PEP 723 block (optional), which lmnr-cli passes to uvx (`pythonRequirements` in its `harbor.ts`), `ctx.secrets` for keys, `ctx.result()` / `ctx.case.expected()` / `ctx.artifacts` / `ctx.container.read_text` for inputs, and `@observe` for its own span; the plugin instruments provider SDKs under the verifier span. `examples/agent-evals` shows one (anthropic `messages.parse`). Keep the `ctx` primitives sufficient for that rather than adding a judge helper.
- `Secrets.__repr__` prints names only (`set=[...]`, `unset=[...]`), never values: `ctx` objects end up in logs and tracebacks.
- Test with `uv run pytest tests/test_evals.py` (no Harbor) and the adapter tests in `tests/test_harbor_runner.py` (Harbor, see `integrations/harbor/AGENTS.md`).

## Images and services (LAM-2588 phase 2)

- **`Image` is an immutable builder** (Modal-style): a base (`from_dockerfile`, `from_registry`, `debian_slim`, `python` = `python:<v>-slim-trixie`, `uv_python` = astral's `ghcr.io/astral-sh/uv:python<v>-trixie-slim`, `node` = `node:<v>-trixie-slim`) plus `Step`s; every method returns a new `Image`, so variants (`base.apt_install(...)`) share the base's steps and Docker layers. Host paths are resolved to absolute ones when the step is declared (`caller_site()`, the first frame outside `lmnr/evals/`), so a shared runner builds the same from every dataset; container paths must be absolute. Missing files fail in `compile_image` (describe exit 2), not at import.
- **`compile_image(image, contributors, root=, fallback_dir=)`** → `CompiledImage`: a bare registry ref stays `{"kind": "registry"}`, a bare Dockerfile stays `{"kind": "dockerfile"}` (phase 1 shapes), anything with steps or services becomes `{"kind": "generated", "dockerfile_text", "context", "ignore_file"?}`. Every kind carries `steps` (`[{origin, step}]`) for `lmnr-cli eval describe`. Order: service bundle stages, the base, service installs, user steps, `WORKDIR /case` (builder images only, unless `.workdir()`). Steps use BuildKit features: `RUN --mount=type=bind` for requirements / `uv sync` inputs (nothing left in the image, cache keyed on file content), heredoc `RUN <<'EOF'` for bundle scripts, `COPY --from=<image>` for uv (`UV_IMAGE`, pinned). `uv_sync` installs into the image's Python (`UV_PROJECT_ENVIRONMENT=$(python3 -c 'import sys; print(sys.prefix)')`, `--no-install-workspace`, `UV_PYTHON_DOWNLOADS=never`).
- **Build context** of a builder image: the deepest folder holding every added host path (a file counts as its folder); without any, the folder of the file that declared the base. NOT the declaring files' folders too, as the plan said: a subclass declared far away (tests, another drive) pushed the context to `/`. A `from_dockerfile` image keeps the user's context (their `COPY` lines are relative to it) and every added path must be inside it.
- **Composition with `from_dockerfile`** (`_compose`, the single place where contributors meet a Dockerfile, so phase 3's Laminar layer works on both kinds): parser directives (`# syntax=`, `# escape=`, `# check=`) stay first, then `# from <Dockerfile> (<class>)`; the last `FROM` gets `AS lmnr-app` unless it has a name; then our stages, `FROM <that stage>`, `USER root` if the last stage set a `USER` (restored at the end), services, steps. The user's `<Dockerfile>.dockerignore` is passed as `ignore_file`.
- **Generated text must be deterministic**: it is Docker's cache key and lmnr-cli dedups images by its content (minus comment lines). Anything random (temp names) belongs in runtime commands, never in build lines; heredoc delimiters come from the text's hash (`services.base.heredoc`). `test_compiling_is_deterministic` pins it.
- **Provenance**: one comment above each step: `# _shared/support.py:12 (SupportRunner)` (each call in a chained expression reports its own line; the owner is the class body's `__qualname__`, absent at module level), `# service: Postgres 16 (_shared/support.py:15)`. Paths are relative to the evals root (`os.path.relpath`, so `../app` when outside it).
- **Golden tests**: `tests/test_evals_images.py` compiles images declared in `tests/data/evals_project/evals/_shared/images.py` (a file of its own so line numbers in comments stay put) against `tests/data/evals_images/*.Dockerfile`; after an intended change `LMNR_UPDATE_GOLDEN=1 uv run pytest tests/test_evals_images.py` and review the diff.
- **How a service gets into the image** (decided for phase 2, reviewed against the vendor-download alternative): a bundle stage `FROM <official image>:<pinned tag>` copies the binaries plus every shared library `ldd` reports (except glibc's own, `bundle._GLIBC`) into `/bundle/`, laid out as in the final image; the final image does `COPY --from=svc-<name> /bundle/ /`, then one `RUN` (`bundle.install_check`) that checks glibc (bundle records the source's glibc at `/usr/local/share/.glibc-required-<name>`, NOT under `/tmp`: COPY would reset the image's `/tmp` to 0755 and break later `apt_install`), that `runuser` exists, and creates the service's OS user. Binaries run through `/usr/local/bin` wrappers that prepend the bundled libs to `LD_LIBRARY_PATH`, so the app's own libraries are never shadowed. Why not vendor downloads: Postgres has no official Linux tarballs (PGDG is apt-only, and apt in the final image re-runs on every app change in a composed Dockerfile); Valkey's tarballs exist only per full version and per Ubuntu release and still link libssl / libsystemd, so they need the same library bundling; ClickHouse's tgz needs the exact full version. Docker tags give a pinned version (`16`, `16.4`), the right architecture (`--platform`), digest-keyed caching and the `source=` override (`pgvector/pgvector:pg16-bookworm`) for free. Sources are pinned to `-bookworm` (glibc 2.36): that runs on `python:*-slim-bookworm`, trixie and Ubuntu 24.04; Ubuntu 22.04 (2.35) needs `source=` from an older distro. Alpine fails the build with a hint. ClickHouse's binary is static apart from glibc, so its stage copies one file and records 2.17.
- **Service runtime**: every built-in binds 127.0.0.1, runs as its own OS user through `runuser -u <user> --` (started as root, so the shell redirect can write `/logs/agent/<name>.log`), and uses the distro-standard paths (`/var/lib/postgresql/data`, `/etc/clickhouse-server`, `/var/lib/valkey`), nothing named lmnr. Postgres: initdb at start (`--no-locale -E UTF8 -A trust`), `fsync` / `synchronous_commit` / `full_page_writes` / `jit` off, `/var/run/postgresql` created at start (Debian's compiled-in socket dir), bundled `zoneinfo` copied in only when the image has no tzdata (`debian:trixie-slim`), `chmod 700` on the data dir (a `migrate_at="build"` dir comes out of `COPY --chown` as 0755). Database / role / extensions / `init_sql` are one idempotent psql script; migrations are `find -maxdepth 1 -name '*.sql' | sort -V`. `migrate_at="build"` runs them in a second stage `FROM svc-postgres` with the source image's own server and copies only the data dir (`COPY --chown=postgres:postgres`, never parents: `--chown` would chown them too).
- **Commands from services** go through `services.base.run_script` (a temp script uploaded with `write_file`, run with `bash`, removed in the same exec) so SQL size isn't limited by argv; helpers run as root. Live helpers call `require_live`, which raises in a `separate` verifier (`ctx.verifier_mode`); `ctx.state(service, table)` reads `/logs/artifacts/state/<service>/<table>.json` through `ctx.artifacts` and works in both modes.
- **Lifecycle** (`services.base.start_services` / `snapshot_services`, called by `LaminarAgent`): all services in parallel, each start → ready → migrate → seed; their `env()` goes to `ctx.env` and every later command (minus keys Harbor's `agents[].env` sets, which wins anyway); snapshots run after `collect`, also when `collect` or `run` raised. `LaminarVerifier` derives the mode like Harbor (`environment_mode`, else `separate` iff the verifier has an `environment`) and adds services' env only in `shared` mode. `validate` rejects duplicate names, shared ports and env keys set by two services or by a service and `EvalRunner.env`; `"latest"` warns.
- **Mirrors**: `Mirror(Service)` adds `seed` (uploaded to a random `/tmp/.<hex>/`, loaded by the provider's `load_seed` after start, deleted, all before `setup`), `url`, `state(ctx)` (live, or `state/<name>/state.json` with `snapshot=True` in separate mode, `Mirror.saved`) and `get` / `request` (HTTP from inside the container: curl if present, else a bash `/dev/tcp` HTTP/1.0 client, `mirrors.base.HTTP_FUNCTION`). Default ports come from a CRC of the name (18000-19999). **Rystic** (`mirrors/rystic.py`) follows the real CLI (0.0.93) and lmnr's hosted-evals proxy (lmnr `docs/internal/hosted-evals.md`, "Rystic service simulators"; lmnr-skills `references/simulated-services.md`), not the plan's guessed surface: the image gets only the CLI (static binary, vendor `install.sh` with a pinned `RYSTIC_VERSION` in a `curlimages/curl` stage, no key needed); each trial runs `rystic pull <product>-twin --version <v>` (needs `RYSTIC_TOKEN` in the container env: per-trial in Laminar sandboxes, `--env RYSTIC_TOKEN` locally), then `rystic run <product> --name --port [--clock]` in the foreground; readiness `GET /_rystic/routes`, seed `POST /_rystic/seed`, state `GET /_rystic/inspect`, plus `calls()` (`/_rystic/calls`) and `settle()` (`/_rystic/settle?quiet_ms=`). Every such assumption is a constant there. `tests/test_evals_services.py` runs the adapter against a fake `rystic` executable (Python HTTP server), with and without curl.
- **Docker tests** (`tests/test_evals_docker.py`, opt-in: `LMNR_EVALS_DOCKER=1 uv run pytest tests/test_evals_docker.py`, ~3 min cold): builds generated images for linux/amd64 on the acceptance bases (`python:3.13-slim-bookworm`, `debian:trixie-slim`, `ubuntu:24.04`) and drives the services through `ctx` over `docker exec` / `docker cp`; also `migrate_at="build"`, composition with a non-root `USER`, the Alpine hint, and `/tmp` keeping 1777.
