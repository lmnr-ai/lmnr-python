# One-file eval runner (`src/lmnr/evals/`)

Design: LAM-2588 (Linear doc "LAM-2588 design: one-file eval runner, services, mocks" and its phase plans). A dataset is `evals/<dataset>/agent/eval.py` with one `EvalRunner` subclass; `lmnr-cli eval run` runs it through Harbor with the adapters in `lmnr.integrations.harbor.runner` (`integrations/harbor/AGENTS.md`).

- **Never import `harbor` here**, not even under `TYPE_CHECKING` in a way that runs: later phases import `eval.py` inside containers where only `lmnr` is installed (mock server). The Harbor environment is duck-typed (`context.Environment`: `exec`, `upload_file`, `upload_dir`, `download_file`). `tests/test_evals.py::test_lmnr_evals_never_imports_harbor` pins it, and the tests drive `ctx` with a `FakeEnvironment` that records calls.
- Modules: `runner.py` (`EvalRunner`, `secret`, validation, loading `eval.py` by path), `context.py` (`Case`, `AgentContext` / `VerifyContext`, `normalize_rewards`), `image.py` (`Image.from_dockerfile` / `from_registry` only; a list of steps so the phase 2 builder can extend it), `readiness.py` (`port` / `http` / `cmd`), `describe.py` (`python -m lmnr.evals.describe agent/eval.py` for lmnr-cli), `paths.py` (where relative paths resolve, the evals root on `sys.path`, the runner's module files), `errors.py` (`EvalConfigError`, `CommandError`, `ExecResult`; `ExecResult` lives there so `errors` ↔ `context` isn't an import cycle).
- **`describe` JSON is versioned** (`DESCRIBE_VERSION = 1`, top-level `"version"`); lmnr-cli (`commands/eval/eval-py.ts`, `DESCRIBE_VERSION`) rejects other versions. Add fields as optional; bump only for incompatible changes, in both repos. stdout is the JSON only: the user module's prints are redirected to stderr while it is imported. Exit 2 = `EvalConfigError`, 1 = import error (traceback on stderr). A single `image` is named `<dataset folder>-evals`; a registry image's task `docker_image` is its ref (lmnr-cli pulls it).
- **Shared runners** (main doc 2.1.2): any folder in the evals root that isn't a dataset (convention `evals/_shared/`) holds shared Python, and `eval.py` subclasses a runner from it (`class RefundsEval(SupportRunner): pass`). `load_module` appends the evals root (`<root>/<dataset>/agent/eval.py` → `<root>`) to `sys.path` before importing `eval.py`, for describe and the Harbor adapters alike (appended, so a folder there never shadows an installed package). `find_runner` counts only classes whose `__module__` is the `eval.py` module, so an imported base class never makes two. Shared modules must not import Harbor either (phase 3 imports them in the container).
- **Relative paths resolve against the file that declares them** (`paths.caller_dir`: the first stack frame outside `lmnr/evals/`), so a shared runner's paths work from every dataset. `Image.from_dockerfile` captures it at call time (`FromDockerfile.base_dir`, from the class body's frame); `ctx.run_file` / `ctx.copy` look it up in `_host_path`, which must run before the coroutine's first `await`: a coroutine's frame links to its caller only until it first suspends. A coroutine started as its own task (`asyncio.gather(ctx.run_file(...))`) has the event loop as caller (`asyncio/` frames), so it falls back to `eval.py`'s dir (`ctx.runner_dir`). Tests therefore pass absolute paths when they call `ctx` from the test file itself (it would resolve against `tests/`); `test_shared_runner_*` cover the relative case from a subclass in another folder.
- describe's `modules` (`paths.loaded_modules`): every module in `sys.modules` whose file is under the evals root, relative to it, `eval.py` included, skipping `site-packages` / dot dirs (an in-root venv). lmnr-cli passes it to the plugin (`runner_modules`) for the Files view; phase 3 uploads these files into the container.
- `EvalRunner` attributes are class-level (`ClassVar`); `verify = "task"` overrides the method with a string, so `verify_mode()` checks `getattr(cls, "verify") == "task"`. `services` / `mocks` exist (empty) and raise "not supported yet" until phases 2-3.
- **Env and secrets.** `secrets` are names; lmnr-cli resolves them like required `${VAR}`s and puts the values in the Harbor process env, so `VerifyContext.secrets` reads `os.environ`. `env` values are strings or `secret(name)` (must be in `secrets`); describe renders a secret as `${NAME}` and lmnr-cli writes `env` into `agents[].env`. In the agent phase Harbor already applies `agents[].env` to every command through `scoped_exec_env`, which **wins over per-exec env** (`BaseEnvironment._merge_env`: persistent < per-exec < scoped), so `LaminarAgent` only adds runner env keys Harbor doesn't set (a hand-written harbor.yaml), and a `ctx.sh(env=...)` can't override an `agents[].env` key. The verifier container gets the runner env (secrets read from `os.environ`) plus Harbor's verifier env (`[verifier.env]`, `verifier.env`), which is what `test.sh` would get.
- **`ctx.result(**fields)` is sync** and writes `result.json` in the trial's host `agent/` dir (`AgentContext.host_logs_dir` = the agent's `logs_dir`). Harbor syncs that dir with `/logs/agent` (bind mount locally, `_upload_agent_logs` after the run for remote envs), and `VerifyContext.result()` reads it from `trial_paths.agent_dir` in both verifier modes. `LaminarAgent.populate_context_post_run` copies it into `AgentContext.metadata`, which the plugin uses as executor output when there's no trajectory message.
- Commands: `user="agent"` maps to `None` (Harbor's default user for the phase: the task's agent user, or the verifier user), `"root"` passes through. Docker execs run `sh -c`; `wait_for` / `service` readiness loops run in ONE exec wrapped in `bash -c` (they use `$SECONDS` and `/dev/tcp`), so the image needs bash. `run_file` uploads to `/tmp/lmnr-<hex>/`, `chmod -R a+rX` as root, runs (shebang → direct, `.py` → `python3`, else `bash`) and `rm -rf`s it in a `finally`. `service` starts `nohup sh -c '<cmd>' > <logs_dir>/<name>.log 2>&1 &` (`/logs/agent` in the agent phase, `/logs/verifier` in verify), and its wait loop exits 2 as soon as the pid dies, so a crashing service fails fast with its log tail.
- **Naming: "host" and "container", never "local" / "remote" / "upload"** in the `ctx` API (`ctx.copy(host, container)`): "remote" already means `lmnr-cli eval run --remote`, where the host is Laminar's orchestrator sandbox, not the user's machine.
- Default `setup` runs the case's `environment/seed.py` / `seed.sh` / `seed.bash` (or another `seed.*` with a shebang); `seed.json` and other data files are not scripts.
- **No vendored LLM judge** (decided in review of lmnr-python#453: nothing we ship is powered by LiteLLM, and the alternative isn't chosen yet). A judge is the user's own function called from `verify()`: it runs in the Harbor process, so it can use any SDK from `eval.py`'s PEP 723 dependencies (lmnr-cli passes them as `--with`), `ctx.secrets` for keys, `ctx.result()` / `ctx.case.expected()` / `ctx.read_text` for inputs, and `@observe` for its own span; the plugin instruments provider SDKs under the verifier span. `examples/agent-evals` shows one (anthropic `messages.parse`). Keep the `ctx` primitives sufficient for that rather than adding a judge helper.
- `Secrets.__repr__` prints names only (`set=[...]`, `unset=[...]`), never values: `ctx` objects end up in logs and tracebacks.
- Test with `uv run pytest tests/test_evals.py` (no Harbor) and the adapter tests in `tests/test_harbor_runner.py` (Harbor, see `integrations/harbor/AGENTS.md`).
