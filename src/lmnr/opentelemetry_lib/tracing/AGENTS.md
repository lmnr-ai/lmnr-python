# src/lmnr/opentelemetry_lib/tracing/

## Import cycles

- **The `Instruments` -> initializer registry is injected, not imported.** `tracing/instruments.py` holds an empty `INSTRUMENTATION_INITIALIZERS` and `register_initializers()`; it must NOT import `_instrument_initializers` (which imports every instrumentor, which import `Laminar`, which imports `instruments`). The built-ins are registered by `tracing/default_initializers.py::register_default_initializers()`, called once from `lmnr/__init__.py`. Any import of `lmnr.*` runs the package `__init__` first, so the registry is always populated; code that imports `instruments` in isolation sees it only after `lmnr` has been imported. The `InstrumentorInitializer` ABC lives in the leaf `tracing/instrumentor_initializer.py` so `instruments.py` can type the registry.
- **The tracing singleton lives in the leaf `tracing/wrapper.py`** (`TracerWrapper`, `get_tracer_wrapper`, ...); `tracing/__init__.py` only re-exports it and holds `init_tracing`. Library code should import from `tracing.wrapper`, not the package. Tests that monkeypatch `_tracer_wrapper` / `_session_recording_options` patch `tracing.wrapper`.

## Tracing singleton and provider lifecycle

- **Singleton**: `Laminar` is a singleton initialized once at startup. Tracing's singleton is NOT the class — `TracerWrapper` is a plain all-`self` object, and the process-wide instance lives in module globals in `tracing/__init__.py`, built by `init_tracing()` and read via `get_tracer_wrapper()`. `init_tracing` publishes the global only AFTER `init_instrumentations` returns, so a half-built wrapper is unrepresentable and `is_tracing_initialized()` is False for the whole of instrumentor setup (the Langfuse bridge depends on this). `is_tracing_initialized()` / `get_tracer_wrapper()` must stay lock-free: an instrumentor importing an `@observe`-decorated module at import time runs inside the init lock and would deadlock.
- **The `TracerProvider` / `LoggerProvider` are built ONCE per process and REUSED across `initialize()`/`shutdown()` cycles; `shutdown_tracing()` shuts down and detaches the run's *processors*, never the providers.** Two OTel facts force this: `trace.set_tracer_provider()` refuses to override an already-set global provider, and `BaseInstrumentor.instrument()` no-ops when already instrumented, so a later `init_tracing` can neither publish a replacement provider nor re-instrument anything. Instrumentors that bind a tracer at `_instrument()` time — MCP, `pydantic_ai`, and the traceloop-derived ones (chromadb, crewai, haystack, llamaindex, langchain, langgraph, milvus, marqo, ...) — would therefore be stranded on a dead provider for the rest of the process, and their spans would silently vanish. Laminar's OWN instrumentors are unaffected either way: they resolve the tracer per call via `safe_start_span` → `get_tracer_with_context()` → `get_tracer_wrapper()`. `_detach_span_processor` / `_detach_log_processor` walk the private `_span_processors` / `_log_record_processors` tuples under their lock (same approach as the Langfuse bridge's `_remove_span_processor`) so the reused providers don't accumulate one retired processor per cycle. **Cost: the provider's `Resource` is fixed at first init**, so a re-init with a different `app_name` / `resource_attributes` keeps the original service name and logs a warning. Pinned by `tests/test_tracer_module.py::test_instrument_time_bound_tracer_survives_a_reinit` and `..._shutdown_detaches_the_retired_processors`.

## Default instrument set

- `init_instrumentations` builds the default set from `Instruments` (`instruments.py`). An explicit `instruments` set is honored verbatim.
- `LANGFUSE` is never in the default set: see `opentelemetry/instrumentation/langfuse/AGENTS.md`.
- `PYDANTIC_AI` is auto-enabled and strips the raw provider instrumentors (`_PYDANTIC_AI_PROVIDER_CONFLICTS`): see `opentelemetry/instrumentation/pydantic_ai/AGENTS.md`.
- `DEEPAGENTS` is auto-enabled, strips `LANGCHAIN`/`LANGGRAPH` (`_DEEPAGENTS_NOISE_CONFLICTS`), and wins over pydantic_ai's conflict removal: see `opentelemetry/instrumentation/deepagents/AGENTS.md`.

## Span batching / export

- **`LaminarSpanProcessor` is a `SpanProcessor` wrapper, not a batcher.** It owns the path bookkeeping + attribute stamping and delegates the actual buffering to `self.instance`: `SimpleSpanProcessor` when `disable_batch=True`, `SizeLimitedBatchSpanProcessor` when `flush_by_size=True`, and the plain upstream `BatchSpanProcessor` otherwise. `disable_batch` wins over `flush_by_size`. Both construction sites (`__init__` and `force_reinit`) go through `_new_batch_processor()` so the two must never drift — `force_reinit` silently dropping a limit *or switching transports* is the failure mode this centralization prevents.
- **`SizeLimitedBatchSpanProcessor` adds a THIRD flush trigger to OTel's two, and it is OPT-IN** via `Laminar.initialize(flush_by_size=True)`. Upstream `BatchSpanProcessor` flushes on `max_export_batch_size` items OR `schedule_delay_millis` elapsed; neither bounds the payload, so a few large GenAI spans (whole prompts + completions as string attributes) can build an export the backend rejects. `max_export_batch_size_bytes` (default `DEFAULT_MAX_EXPORT_BATCH_SIZE_BYTES` = 32 MiB) flushes the buffer when the span being ended *would* push it over, then enqueues that span as the start of a fresh batch. **The default is restated in prose in three places — this file, the `Laminar.initialize` docstring, and the overshoot arithmetic in `on_end`'s comment — so changing the constant means updating all three** (a stale 16 MiB in those spots is what Bugbot flagged on PR #318). `max_export_batch_size_bytes` is **ignored without the flag** — passing it alone must not silently switch transports (pinned by `test_size_limit_is_ignored_without_the_flag`). The full option chain is `Laminar.initialize(...)` → `init_tracing` → `LaminarSpanProcessor` → the batch processor; a new export knob must be threaded through all four or it is silently ignored.
- **The size flush normally runs on this processor's OWN background thread (`LmnrSizeLimitedSpanFlush`), not on the thread that ended the span.** Upstream's worker cannot be reused for it: `BatchProcessor._should_export_batch` returns False for a queue shorter than `max_export_batch_size` under `EXPORT_WHILE_BATCH_EXCEEDS_THRESHOLD`, the strategy an `emit`-interrupted sleep selects, so merely waking it does nothing. An earlier revision called `force_flush()` inline from `on_end` and load testing measured a p99 of ~664ms — every thread tripping the limit serialized on OTel's `BatchProcessor._export_lock`.
- **Two cases still export INLINE, and both are load-bearing** (`on_end`): (a) a previous flush request has not been picked up yet — the producer is outrunning the network and this backpressure is the only thing bounding the buffer, without which the export size is governed by `max_export_batch_size` instead; (b) the span is at least half the limit by itself, since an async flush **cannot exclude the span that triggered it** (`on_end` enqueues before the flush thread wakes), so a large span would ride along and materially overshoot. The half threshold bounds any export at 1.5x the limit.
- **`_at_fork_reinit` must replace EVERY lock and Event, not just some.** `fork` clones only the calling thread, so any lock another thread held at fork time is inherited permanently locked with nobody left to release it. `on_end` acquires `_pending_size_lock` before it could ever notice the pid changed, so a lazy "respawn if pid differs" check in `on_end` **deadlocks instead of recovering** — verified: the child hangs forever on its first span. Registered via `os.register_at_fork(after_in_child=...)` (same mechanism upstream uses) with a `weakref.WeakMethod`, because fork handlers cannot be unregistered and must not keep a dead processor alive. Pinned by `test_forked_child_can_still_flush_with_locks_held_at_fork`, which hangs if the handler is removed.
- **The running byte total is an estimate that resyncs on an observed-empty queue** (`if not self._batch_processor._queue: self._pending_size_bytes = 0`). The worker drains the buffer on its own schedule without notifying us, so any counter we keep drifts: over-counting after a partial drain, under-counting when a concurrent emitter resyncs mid-`on_end`. Both self-correct at the next resync and only shift *when* a flush happens, never *whether* spans are exported — do not try to make this exact by tracking per-span sizes through the deque, which would mean reimplementing `BatchProcessor`.
- **String sizes go through `utf8_size`, NOT `len()` — `len()` counts code points and undercounts CJK ~3x, Cyrillic/Arabic ~2x, emoji ~1.4x.** `utf8_size` takes an O(1) `str.isascii()` fast path (CPython caches the flag on the string object, so it does NOT scale with length — verified flat at 10.4ns from 100 to 1M chars) and returns `len()` there, exact and free for the common case.
- **Above `_UTF8_SAMPLE_BUDGET` (1024 chars) `utf8_size` encodes a STRIDED sample (`value[::step]`), never a prefix.** Prefix sampling is wrong for this data specifically: `gen_ai.input.messages` opens with ASCII JSON scaffolding (`[{"role":"system","content":"`) before reaching non-ASCII content, so a prefix probe reports near-ASCII sizes for a CJK payload (measured −64.5%, i.e. no better than the bug being fixed). Striding lands within ~2% worst case at ~5us on an 80 KB value, versus 40–80us to encode it outright, and never reallocates the whole string. Pinned by `test_utf8_size_is_within_five_percent_of_the_real_encoding` (parametrized across scripts, including both prefix-adversarial layouts).
- **`utf8_size` MUST encode with `errors="replace"`.** Attribute values can contain lone surrogates (upstream JSON decoding produces them) and a strict `.encode("utf-8")` raises `UnicodeEncodeError` on those. This runs inside `on_end`, so raising would break span export for the whole batch. Verified that such a string does reach span attributes intact. Pinned by `test_utf8_size_survives_lone_surrogates`, which fails with `errors="strict"`.
- **`approximate_span_size` is still deliberately an underestimate** in the other dimensions: non-string values counted a flat 8 bytes, no protobuf framing / ids / timestamps. That is safe by design — if most spans are small the item-count or schedule-delay trigger fires first; the size trigger only needs to be accurate for spans dominated by big string attributes, which is what `utf8_size` delivers.
- **When `on_end` latency regresses, the cause is the export, never the size bookkeeping lock.** Measured under an 8-thread stress test with a 20ms export against the old inline implementation: `on_end` p99 ~170ms, of which `force_flush` was 99.9% and the `_pending_size_lock` wait was ~0.2us (0.00%). The contention is OTel's own `BatchProcessor._export_lock` (p50 wait ~148ms), which serializes every concurrent `force_flush`, so N threads queue behind N sequential exports. That is what the background flush thread exists to avoid. Do NOT "optimize" the size-aggregation lock — it has never been the bottleneck.
- **`LaminarSpanProcessor(max_export_batch_size=...)` was previously typed `int = 64`, but the 64 never applied.** Every caller in the chain defaults to `None` and passed it straight through, so `BatchSpanProcessor` fell back to OTel's own env-var default of **512** — i.e. the "we lowered 512 to 64" claim in the `initialize` docstring was not true in practice. The default now lives in `DEFAULT_MAX_EXPORT_BATCH_SIZE` and is applied via `or` inside `LaminarSpanProcessor.__init__`, where a `None` from any upstream layer actually resolves. Pinned by `test_default_is_the_plain_upstream_batch_processor`, which asserts the 64 on the DEFAULT (non-`flush_by_size`) path — that is the path the bug lived on. `sdk/evaluations/models.py` keeps its own `MAX_EXPORT_BATCH_SIZE = 64` as an explicit non-None default for eval runs.
- **`tests/test_batch_processor.py` builds its own `TracerProvider` + recording exporter instead of using the session-scoped `span_exporter` fixture.** Isolating the byte trigger requires setting `max_export_batch_size` high (1000) and `schedule_delay_millis` to 10 minutes so the other two triggers cannot fire; the shared fixture initializes with `disable_batch=True` (`SimpleSpanProcessor`) and has no batching to test. An autouse fixture shuts down every processor the module builds — each starts a daemon worker thread that would otherwise survive the whole session and keep exporting on its own schedule.

## Span payload size limit

- `MAX_MANUAL_SPAN_PAYLOAD_SIZE` (10MB, `opentelemetry_lib/tracing/span.py`) caps manual `set_input` / `set_output`. An oversized payload is **truncated to the limit with a trailing `TRUNCATION_SUFFIX` (`...[Laminar: truncated]`)**, NOT replaced — the old behavior swapped the whole value for `"Laminar: input too large to record"`, which discarded everything (LAM-2050). The recorded value is deliberately no longer valid JSON; the frontend renders it as a string. Keep `_truncate_payload` line-comparable with TS `truncateSpanPayload` in `packages/lmnr/src/utils.ts` (same constant, same suffix).
- The limit only guards the MANUAL API. Auto-instrumentation attributes (`gen_ai.input.messages`, the daytona/langfuse `SPAN_INPUT` writers) are not truncated — they set the attribute directly rather than going through the mixin.
- **The SDK limit (10MB) is larger than app-server's default `HTTP_PAYLOAD_LIMIT` (5MB)**, so a payload can pass truncation and still 413 on export. Truncating is not a guarantee of ingestion; it only stops one span from being unboundedly large.
