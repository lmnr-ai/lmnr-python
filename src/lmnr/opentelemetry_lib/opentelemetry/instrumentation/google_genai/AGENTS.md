# google_genai instrumentation

## Native Gemini shape (no OpenAI conversion)

- Messages are built by `content_union_to_dict` + `part_to_dict` into the native Gemini `{role, parts}` shape, and that is what the frontend parses (`frontend/lib/spans/types/gemini.ts`, wired into `process-messages.ts` — `GeminiContentSchema` requires `parts`). **Don't add an OpenAI-format conversion layer here.** An older pipeline that converted parts to OpenAI's `{type: "image_url", ...}` shape (`get_content` / `process_content_union` / `_process_part*` / `_process_image_item` plus the `ProcessedContentPart` / `ToolCall` / `ImageUrl` / `ImageUrlInner` / `ToolResult` models) was orphaned when the native shape landed in `5b43e75`, and is now DELETED — along with the two `Config` fields that gated it (`convert_image_to_openai_format`, `upload_base64_image`) and their `GoogleGenAiSdkInstrumentor.__init__` kwargs. `Config.exception_logger` is the only remaining field.
- It was deleted rather than re-enabled because it was **lossy**. `ProcessedContentPart` models only text / function_call / image_url / function_response, so `executable_code`, `code_execution_result` and `file_data` each fell through `_process_part`'s final `else` into `json.dumps(part_dict)` — becoming a text part holding a JSON blob of the entire part with every null field spelled out. It also dropped `thought` / `thought_signature` (which would break Gemini 3 thinking-signature round-trips) and `role`, and returned a bare part array with no `{role, parts}` wrapper, so the frontend's Gemini parser would not have matched it and every span would have fallen through to the generic renderer. Since `convert_image_to_openai_format` defaulted to `True`, enabling it would have changed span shape for every Gemini user, not just opt-ins.
- If a consumer ever needs image data URLs, transform the current `{role, parts}` output (map `inline_data` → a data-URL part, leave every other part type structured) rather than reviving that pipeline.

## Bytes serialization (see `src/lmnr/sdk/AGENTS.md` for `json_dumps`)

- **Therefore: never serialize a pydantic model for a span attribute with `model_dump(mode="json")` or `model_dump_json()` when the model can carry bytes.** Dump `mode="python"` and let `json_dumps` do the encoding. `mode="json"` applies the model's own `ser_json_bytes` setting — and **google-genai sets `ser_json_bytes="base64"`, which is pydantic's URL-SAFE alphabet**, so json mode emits `-`/`_` and bypasses our encoder entirely. In `google_genai/utils.py` this is what `model_to_json_safe_dict` exists for; the affected attributes were `gen_ai.input.messages`, `gen_ai.output.messages`, and `lmnr.sdk.raw.response`, and the bytes fields are `Blob.data` and `Part.thought_signature`. openai / anthropic base models set no `ser_json_bytes`, so they were never affected.
- **Keeping `mode="json"` was investigated and is not possible** — don't re-try these: pydantic exposes no standard-base64 setting (`ser_json_bytes` accepts only `"base64"`, which IS the URL-safe one, plus `"hex"` and `"utf8"`, and `utf8` raises `UnicodeDecodeError` on real binary); a per-call `context=` does not reach `ser_json_bytes`; `TypeAdapter(config=...)` is rejected outright for BaseModel types (`PydanticUserError`); `model_dump(fallback=...)` only fires for types pydantic can't serialize, so it never sees `Blob.data`; and repairing the alphabet after the dump would have to guess which strings came from bytes — a blind `-`→`+` / `_`→`/` swap corrupts ordinary text (`"well-known B-tree"` → `"well+known B+tree"`) and even JSON keys.
- **`mode="python"` is also strictly MORE robust than `mode="json"` here, not a tradeoff.** For the `Any`-typed `function_call.args` / `function_response.response` fields, json mode RAISES `PydanticSerializationError` on any value it doesn't recognise (a `Mapping` that isn't a `dict`, a custom object, `range`, a lambda) — and because the callers are `@dont_throw`, that silently dropped the ENTIRE `gen_ai.input.messages` attribute, every message in the conversation, not just the offending value. Python mode passes the value to `json_dumps`, which degrades that one leaf. Pinned by `test_an_unserializable_tool_value_does_not_drop_the_conversation`.
- Pydantic's base64 **validator** (`val_json_bytes="base64"`) accepts BOTH alphabets, so the debug-replay path (`GenerateContentResponse.model_validate_json` on `lmnr.sdk.raw.response`) round-trips old URL-safe spans and new standard ones alike — the fix needed no migration. The frontend's `toStandardBase64` (`frontend/lib/utils.ts`) is a no-op on standard base64, so it stays harmless.
