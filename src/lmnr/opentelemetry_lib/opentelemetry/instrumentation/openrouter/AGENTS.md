# openrouter instrumentation

- Wraps `openrouter.chat.Chat.send/send_async`, `openrouter.responses.Responses.send/send_async` and `openrouter.embeddings.Embeddings.generate/generate_async` (the official Speakeasy-generated `openrouter` SDK, kwargs-only API). Span names are `openrouter.chat` / `openrouter.responses` / `openrouter.embeddings`. Models live under `openrouter.components.*`, not `openrouter.models`; `model_dump()` is snake_case, so usage keys are `prompt_tokens` / `input_tokens`, cost is `usage.cost` + `usage.cost_details.upstream_inference_{prompt,completions,input,output}_cost`.
- Built on `BaseLaminarInstrumentor` + `WrappedFunctionSpec` (like litellm/daytona), so spans carry `lmnr.span.instrumentation_scope.name/version`; the handlers take the spec as their first arg and derive the resource kind from `span_name` (`_kind`). **The wrapped-method table `_WRAPPED_METHODS` is FLAT `(kind, method_name, is_async)` triples, not nested** — a nested comprehension over `(kind, (methods...))` blows the 88-col ruff limit in the `WrappedFunctionSpec` construction, which is why it was flattened.
- **`embeddings` is `generate`/`generate_async`, NOT `send`** — the only resource with a different method name, and the only non-streaming one (`is_streaming=kind != "embeddings"`; that field is metadata-only, read nowhere in the base instrumentor, but keep it accurate). Its `usage` is CHAT-key compatible (`prompt_tokens`, `total_tokens`, `cost`, `cost_details.upstream_inference_prompt_cost`) so it reuses the chat usage reader; `completion_tokens` is simply absent and `set_span_attribute` skips `None`. Its input is stamped as `gen_ai.input.messages = [{"content": <str>}, ...]` (no `role`), and there is deliberately no `gen_ai.output.messages` — nobody wants raw float vectors in a span.
- **`embeddings` `input` has FIVE shapes** (`InputUnion` in `openrouter/operations/createembeddings.py`): `str`, `list[str]`, **`list[float]`**, `list[list[float]]`, `list[Input]`. A flat list of numbers is ONE token-id sequence, not a batch — verified live that `input=[15339, 1917]` returns a single embedding with `prompt_tokens: 2`. So `_embeddings_input_messages` must not iterate a flat number list, or an N-token request is recorded as N one-token documents. Note the SDK types it as `list[float]` even though these are token ids, so the isinstance check has to accept `int` and `float`. Same trap and fix in the TS instrumentor (`embeddingsInputMessages`) — keep the two in sync.
- **Content is gated by `LMNR_TRACE_CONTENT` via a LOCAL `should_send_prompts()` in `span_utils.py`** (default `"true"`), matching openai / anthropic / groq. Do NOT copy google_genai's `LAMINAR_TRACE_CONTENT` — that is a different env var. The gate covers `gen_ai.input.messages`, `gen_ai.output.messages` AND `gen_ai.tool.definitions` (tool definitions carry user schemas / descriptions, so they are content, not metadata — the TS side was moved behind its `traceContent` gate for the same reason).
- **Speakeasy alias trap, Python-only:** the generated TypedDicts spell aliased fields `schema_` / `format_`, but the BaseModels' custom `model_serializer` emits `schema` / `format` from `model_dump()`, and `to_dict` has no `by_alias`. So `response_format` / `text.format` must be read through the 3-line `_aliased(d, key)` helper, which tries `key` then `key_`. TS has NO such trap (`responseFormat.jsonSchema.schema`, `text.format.schema` are literal). Extracting `gen_ai.request.structured_output_schema` needs NO pydantic / `TypeAdapter` machinery here (unlike the openai instrumentor) — the values arrive as plain dicts or as models `to_dict` flattens.
- **Terminal error marking keys off `response["status"]`, not the stream event `type`** (`responses_error_message` + `ERROR_RESPONSE_STATUSES = ("failed", "incomplete")`). `response_from_stream_events` returns the terminal event's `.response`, which carries `status`, so ONE helper covers streaming and non-streaming. Failing statuses set `error.type = <status>` + `Status(ERROR, error.message | incomplete_details.reason | status)`. `cancelled` is deliberately NOT an error (user-initiated). Verified live: OpenRouter really returns `status: "incomplete"` with `incomplete_details.reason == "max_output_tokens"`.
- Streaming returns `EventStream` / `EventStreamAsync` (`openrouter.utils.eventstreaming`) holding a `.generator`; the instrumentor replaces that attribute with a wrapping generator and finalizes the span in `finally`. **`EventStream.close()` (also called by `__exit__`) flips `_closed` and never touches the generator**, so a stream closed before iteration would leak the span — the instrumentor also shadows `stream.close` on the instance to finish the span, and `_finish_stream` is idempotent via `span.is_recording()`. Responses streams are a flat event list — the terminal `response.completed` / `response.incomplete` / `response.failed` event carries the full `.response`.
- The agent loop (`openrouter_agent`) fails to import on `openrouter==1.1.156`, so there is no dedicated agent wrapper; its per-turn calls go through `Responses.send`, which is already covered.
- Tests: `tests/test_openrouter.py` with cassettes in `tests/cassettes/test_openrouter/`; the dev dep is pinned `openrouter==1.1.156`. **Always pass `dimensions=8` when recording an embeddings cassette** — the default 1536-float vector makes a 25 KB cassette for a two-word input (2.4 KB with the cap), and none of the assertions touch the vector.
