# Microsoft Agent Framework instrumentation

`opentelemetry/instrumentation/microsoft_agent_framework/` (gated on `agent-framework-core`). The framework emits its OWN GenAI semconv spans; the instrumentor creates none, it patches module-level helpers in `agent_framework.observability` / `_mcp` that the framework looks up by global name. The module docstring lists every gap it closes. Non-obvious points:

- **Provider dedupe is scoped:** `_SUPPRESS_INSTRUMENTATION_KEY` is set only while a framework `chat`/`embeddings` span is active, so direct provider calls (incl. LLM calls made inside a tool) are still traced. Don't strip provider instrumentors from the defaults like pydantic_ai / google_adk do.
- **`get_tracer()` is called with NO args:** bind the wrapped signature + `apply_defaults()` before delegating, or `set_global_tracer_provider=False` silently yields zero framework spans.
- **Framework spans start in the GLOBAL context**, so `_LaminarActivatingTracer` copies session/user/metadata/trace-type keys from `get_current_context()` and mirrors span activation into Laminar's context.
- **Workflow span names are `OtelAttr` (`str` enum):** a non-exact-`str` name in `lmnr.span.path` makes OTel drop the attribute for the span and all descendants. The tracer wrapper coerces names with `str.__str__`.
- **Gemini thinking tokens:** MAF's Gemini client puts only candidates in `output_tokens` (thinking goes to `gen_ai.usage.reasoning.output_tokens`, which the backend ignores). The `_get_response_attributes` wrapper adds them on `gcp.*` `chat` spans and sets `gen_ai.usage.reasoning_tokens`. Never for OpenAI: its output already includes reasoning.
- **MCP `tools/call` spans carry `gen_ai.operation.name=execute_tool`**, so the backend shows them as a duplicate tool span inside the real `execute_tool`; the `create_mcp_client_span` wrapper strips the operation name. Laminar's own MCP instrumentor (`instrumentation/mcp/`) still adds its `{tool}.tool` / `{method}.mcp` CLIENT span around each MCP request (it honors the suppress key).
- **Version drift:** private helpers get renamed, so tool definitions for `chat` spans come from calling the ORIGINAL `_get_span_attributes(options={"tools": ...})`. Content/reasoning/tool-definition attributes are gated on `use_latest_experimental_gen_ai_semconv`. 1.0.0 had instrumentation off by default and no MCP spans.
- **Built on `BaseLaminarInstrumentor`, but the framework creates the spans**, so there is no span-opening wrapper to stamp `lmnr.span.instrumentation_scope.{name,version}`. `_LaminarActivatingTracer` stamps it instead: every framework span goes through the patched `get_tracer()`, which hands the tracer the scope from its spec.
- **Wrap the `_mcp` binding of `create_mcp_client_span` BEFORE the `observability` one.** `_mcp` does `from .observability import create_mcp_client_span`, so importing it after the observability binding is wrapped copies the wrapper and the second patch wraps it twice (each MCP span bridged twice, and uninstrument leaves one layer). Pinned by `test_uninstrument_restores_every_hook`.
- **Explicit user settings win:** `ENABLE_INSTRUMENTATION` / `ENABLE_SENSITIVE_DATA` in env are left alone, and `LMNR_TRACE_CONTENT=false` means no content.
- **Tests:** `tests/test_microsoft_agent_framework.py` + cassettes (gpt-5-mini, real `OPENAI_API_KEY`); `agent-framework-core` / `-openai` are pinned dev deps.
- **Manual testing gotchas:** pydantic-ai / google-adk in the dev venv drop OPENAI / GOOGLE_GENAI from default instruments, so pass an explicit set to see dedupe. `agent-framework-gemini` (beta) 400s on agents with no tools. Unset the sandbox `ANTHROPIC_BASE_URL`. The full suite has env-caused Azure/Bedrock failures that also fail on `main`.
