# openai_agents instrumentation

- **Failures arrive as a `SpanError` payload, not a raised exception.** `apply_span_error` (`span_data.py`) reports them with `record_exception` — that event, not the OTel status, is what makes the span red in Laminar (see `../AGENTS.md` → "Error status"). `exception.type` is set to the SDK's label so the error card is headlined by it instead of `Exception`, and `exception.stacktrace` is blanked because nothing was actually raised and `record_exception`'s synthetic trace would just repeat the message.
- **`SpanError` is a `TypedDict`, so at runtime it is a plain dict** — `getattr(error, "message")` silently returns `None`. `apply_span_error` handles the dict and object shapes both. Its `message` is a short label ("Error running tool (non-fatal)", "Max turns exceeded"); the specifics live in `data`.
- **Cached input tokens are unavailable on `openai-agents` <= 0.0.x.** `_apply_usage` (`messages.py`) correctly reads `input_tokens_details` / `prompt_tokens_details` → `cached_tokens` and emits `gen_ai.usage.cache_read_input_tokens`, but early SDK versions have a 4-field `Usage` dataclass with no details objects, AND `models/openai_chatcompletions.py` hand-builds the generation span's usage as a 2-key `{"input_tokens", "output_tokens"}` dict. The data is destroyed before any `TracingProcessor` sees it — this is not an instrumentation bug, and the only fix at those versions is to read the raw provider response yourself.
- `OpenAIAgentsInstrumentor` declares `_instruments = ("openai-agents >= 0.7.0",)`, but the `TracingProcessor` ABC and the `set_trace_processors` / `GLOBAL_TRACE_PROVIDER` API are compatible far below that. To instrument a pinned older version, skip the version-gated instrumentor and register the processor directly: `set_trace_processors([LaminarAgentsTraceProcessor()])`. Replace rather than append — the SDK's default processor uploads to OpenAI's own tracing backend.
- **Every `_apply_*_span_data` handler in `span_data.py` must call `set_lmnr_span_io`.** Custom `openai.agents.*` attributes are stored but never rendered as span I/O, so a handler that only sets those produces a span that looks empty in the trace view while the data sits in the payload. `_apply_mcp_span_data` had exactly that bug — 15 `agents.mcp_tools` spans on a chi-bench run, all blank, with the full tool list in `openai.agents.mcp.result`. The handlers for handoff / guardrail / custom still set attributes only; that is the same latent gap if those spans ever need to render.
- **The first turn's `agents.mcp_tools` span parents to the trace root, not to the agent span, and that is upstream behaviour.** `agents/run.py` calls `get_all_tools()` (which opens `mcp_tools_span`) before `agent_span(...)` is created and started, and the agent span is only created `if current_span is None`. Every later turn nests normally. Don't "fix" the parenting in `processor.py`.
- `MCPServerStreamableHttp(cache_tools_list=True)` caches the tool list but the SDK still opens one `mcp_tools` span per turn — the cache check lives inside `list_tools`, which the span already wraps, so the repeats are ~0.3ms cache hits, not MCP round trips. A run with N turns legitimately shows N of these spans.
- **`LitellmModel` used to produce TWO LLM spans per model call, each with the full token usage — so every turn's cost was counted twice.** `LitellmModel.get_response` / `stream_response` (in the installed `agents` package, `extensions/models/litellm_model.py`) open a `generation` span and call `litellm.acompletion` inside it, so this processor emitted `agents.generation` and the litellm instrumentor emitted a nested `litellm.completion` for the same call. It is not visible as an error anywhere — the trace just renders two identical LLM spans and Laminar's `total_cost` comes out ~2x the runner's own measurement (observed on chi-bench Anthropic traces: $0.9123 + $0.9846 = the $1.90 trace total). Fixed by `DISABLE_LITELLM_INSTRUMENTATION_CONTEXT_KEY` (`../shared/context_keys.py`), set by `processor.py::on_span_start` on the context it hands to `Laminar.start_active_span` and honored by an early return in both litellm wrappers. This mirrors the pre-existing `DISABLE_OPENAI_RESPONSES_INSTRUMENTATION_CONTEXT_KEY`; the litellm wrappers were simply never wired into that pattern. Note this is a DIFFERENT duplicate from litellm's own `completion`↔`responses` bridge re-entrancy (`../litellm/AGENTS.md`): that one is guarded by `is_in_litellm_context()`, which the agents processor never sets, so neither guard subsumes the other. Pinned by `tests/test_instrumentations/test_openai_agents/test_litellm_model.py`.
- **The suppression is scoped to `generation` spans only** (`if span_kind(span_data) == "generation"`), not to the whole agent run. Tools, handoffs and MCP calls inside a run may legitimately call litellm themselves, and those calls have no enclosing span that already describes them — suppressing the key at the run level silently drops them from the trace.
- **The key lives in `../shared/context_keys.py`, not in `helpers.py`.** That leaf module exists so an instrumentation which only needs the key doesn't pull optional packages through a parent package — importing it from `openai_agents/helpers.py` would make the litellm wrapper drag in `agents` (openai-agents).
- **Which span survives is not a free choice: `agents.generation` has to be the one kept.** The processor also produces the entire trace structure (root, agent, turn, tool and MCP spans) and cannot be disabled for generation spans only. The cost of keeping it is that `cache_creation_input_tokens` is lost — the agents SDK's `Usage` carries only `prompt_tokens_details.cached_tokens`, with no cache-creation field anywhere in `litellm_model.py`, so it is unrecoverable without patching the agents SDK. Measured impact on an Anthropic span: $0.0369 vs $0.0375, ~1.5%. `cache_read_input_tokens` IS preserved.
- **`gen_ai.system` on generation spans is derived from the model string (`provider_from_model` in `messages.py`), not hardcoded `"openai"`.** litellm model names are `<provider>/<model>`, so every `LitellmModel` call used to be labelled `openai` regardless of who served it. Bare names (the Responses path) still resolve to `openai`. The two remaining hardcoded `"openai"` providers in `span_data.py` (`_apply_speech_span_data`, `_apply_transcription_span_data`) are genuinely OpenAI-only APIs and are deliberately left alone.
- **`extra_args={"mock_response": ...}` on `ModelSettings` reaches `litellm.acompletion` untouched** (`litellm_model.py` merges `extra_args` into the call kwargs), which is what lets the agents+litellm tests run a full `Runner.run` with no network and no cassette.
