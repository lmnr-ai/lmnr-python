# openai_agents instrumentation

- **Failures arrive as a `SpanError` payload, not a raised exception.** `apply_span_error` (`span_data.py`) reports them with `record_exception` — that event, not the OTel status, is what makes the span red in Laminar (see `../AGENTS.md` → "Error status"). `exception.type` is set to the SDK's label so the error card is headlined by it instead of `Exception`, and `exception.stacktrace` is blanked because nothing was actually raised and `record_exception`'s synthetic trace would just repeat the message.
- **`SpanError` is a `TypedDict`, so at runtime it is a plain dict** — `getattr(error, "message")` silently returns `None`. `apply_span_error` handles the dict and object shapes both. Its `message` is a short label ("Error running tool (non-fatal)", "Max turns exceeded"); the specifics live in `data`.
- **Cached input tokens are unavailable on `openai-agents` <= 0.0.x.** `_apply_usage` (`messages.py`) correctly reads `input_tokens_details` / `prompt_tokens_details` → `cached_tokens` and emits `gen_ai.usage.cache_read_input_tokens`, but early SDK versions have a 4-field `Usage` dataclass with no details objects, AND `models/openai_chatcompletions.py` hand-builds the generation span's usage as a 2-key `{"input_tokens", "output_tokens"}` dict. The data is destroyed before any `TracingProcessor` sees it — this is not an instrumentation bug, and the only fix at those versions is to read the raw provider response yourself.
- `OpenAIAgentsInstrumentor` declares `_instruments = ("openai-agents >= 0.7.0",)`, but the `TracingProcessor` ABC and the `set_trace_processors` / `GLOBAL_TRACE_PROVIDER` API are compatible far below that. To instrument a pinned older version, skip the version-gated instrumentor and register the processor directly: `set_trace_processors([LaminarAgentsTraceProcessor()])`. Replace rather than append — the SDK's default processor uploads to OpenAI's own tracing backend.
- **Every `_apply_*_span_data` handler in `span_data.py` must call `set_lmnr_span_io`.** Custom `openai.agents.*` attributes are stored but never rendered as span I/O, so a handler that only sets those produces a span that looks empty in the trace view while the data sits in the payload. `_apply_mcp_span_data` had exactly that bug — 15 `agents.mcp_tools` spans on a chi-bench run, all blank, with the full tool list in `openai.agents.mcp.result`. The handlers for handoff / guardrail / custom still set attributes only; that is the same latent gap if those spans ever need to render. The task / turn handlers set I/O too (input = name / turn + agent, output = aggregate usage).
- **The first turn's `agents.mcp_tools` span parents to the trace root, not to the agent span, and that is upstream behaviour.** `agents/run.py` calls `get_all_tools()` (which opens `mcp_tools_span`) before `agent_span(...)` is created and started, and the agent span is only created `if current_span is None`. Every later turn nests normally. Don't "fix" the parenting in `processor.py`.
- `MCPServerStreamableHttp(cache_tools_list=True)` caches the tool list but the SDK still opens one `mcp_tools` span per turn — the cache check lives inside `list_tools`, which the span already wraps, so the repeats are ~0.3ms cache hits, not MCP round trips. A run with N turns legitimately shows N of these spans.

## Span tree and naming (`processor.py`)

- **The SDK's own nesting is authoritative; don't reparent across handoffs.** An earlier version stashed each handoff's parent context (`pending_handoff_ctxs`) and started the destination agent under it. But the SDK ends the source agent's span *before* starting the destination's, so the destination became a child that starts after its parent ended. The destination agent is now a sibling of the source, under the trace root. Pinned by `test_agents_span_tree.py`.
- **The root span is named from the trace up front (`_root_span_name`), because `lmnr.span.path` / `lmnr.span.ids_path` are captured at span start.** A placeholder name leaks into the path of every descendant. When a span arrives before `on_trace_start`, the root is started as `agents.trace` and later renamed. `_rename_root_span` then rewrites the path attribute *and* the `LaminarSpanProcessor` path cache (`set_parent_path_info`). Children started afterwards read their parent's path from that cache, so a stale cache entry leaks the old prefix. The rewrite covers the root and every still-open span in `state.spans`, since the spans that arrived first carry the placeholder in their own paths. Descendants are matched by `lmnr.span.ids_path` prefix, not by name. Spans that already ended can't be repaired, because they accept no attributes and have left the cache. The rename is skipped unless the root's last path element equals the old name. With tracing disabled, the path is masked as `_` and must stay that way.

## Attribute shapes

- **`gen_ai.output.messages` is a flat list of output blocks**, the same as every other producer, not the old `{id, object, output}` envelope (that rendered as one opaque blob). A non-list `response.output` sets nothing. Responses-API blocks (`function_call`, `reasoning`, ...) have no `role`, so `_with_roles` (`messages.py`) stamps `tool` on the tool-output block types and `assistant` on the rest, copying instead of mutating. Keep `_TOOL_OUTPUT_BLOCK_TYPES` in sync with `responsesItemRole` in the frontend's `lib/spans/process-messages.ts`.
- **The system prompt is prepended only if `span_data.input` lacks it.** The ChatCompletions model path already inserts it into the input; the Responses path sends it as a separate `instructions` field. `_message_text` compares across str and content-block shapes.
- **Function spans record raw `span_data.input` / `.output`, not `export()`**, because `FunctionSpanData.export()` does `str(self.output)`. A structured tool result would arrive as a Python repr and `0` would arrive as `"0"`.
- **Task / turn usage goes in `openai.agents.{task,turn}.usage` (JSON), never `gen_ai.usage.*`.** It aggregates the LLM spans beneath it, which already report their own usage, and the backend would read it as one more LLM call's tokens (double cost). `TaskSpanData` / `TurnSpanData` (openai-agents >= 0.20) export as `{"type": "custom", "name": "task"|"turn", "data": {...}}`, so `_exported_payload` unwraps `data`.
- **A failed response span still records the model.** `ResponseSpanData` has no model field, and a failed call leaves `response=None`. `_wrap_get_response` / `_wrap_stream_response` (`instrumentor.py`) stash `instance.model` in the `_current_model_name` ContextVar (`helpers.py`) and the response handler falls back to it. For streams the var is set inside the generator, since that is where the call runs.

## Duplicate LLM spans

- **The OpenAI chat-completions wrappers skip tracing while an Agents span is active.** An agent on `OpenAIChatCompletionsModel` otherwise produces the SDK's `generation` span *and* our `openai.chat` span for the same call. `chat_wrapper` / `achat_wrapper` (`openai/shared/chat_wrappers.py`) check `DISABLE_OPENAI_RESPONSES_INSTRUMENTATION_CONTEXT_KEY` (`shared/context_keys.py`), the same key the processor already sets for the Responses path. Despite its name, it suppresses both paths. The name is kept for lmnr-ts parity.
