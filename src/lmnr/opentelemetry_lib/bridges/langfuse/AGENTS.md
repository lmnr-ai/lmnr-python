# Langfuse bridge

`Laminar.initialize(bridges=[Bridge.LANGFUSE])` (or `bridges=["langfuse"]`) sends everything the Langfuse SDK exports to Laminar too. Supported: langfuse 3.x, 4.x, 5.x (all OpenTelemetry-based; 2.x is not). The contract shared with future bridges is in `../base.py` and `../AGENTS.md`.

## The one rule: Langfuse's export must not change

- **Laminar never writes to a span Langfuse owns.** `LangfuseBridgeSpanProcessor` (`processor.py`) sits on Langfuse's provider. In `on_start` it runs Laminar's `LaminarSpanProcessor.on_start` against a `_ShadowSpan`, which records Laminar's stamps (`lmnr.span.path`, `ids_path`, sdk version, association properties from Laminar's context) in a side table. In `on_end` it builds a new `ReadableSpan` (original attributes + stamps + `translate_span`) and passes only that copy to Laminar's `on_end`. Both directions used to leak before this: the old translator wrote `gen_ai.*` / `lmnr.*` into `span._attributes`, and `LaminarSpanProcessor.on_start` stamped `lmnr.span.*` on the live span, all of which Langfuse then exported. The old processor-ordering and `_immutable`-toggle hacks are gone with it.
- **Laminar keeps its provider off the global slot while the bridge is on** (`requires_private_tracer_provider`; `Laminar.initialize` overrides `set_global_tracer_provider`, warning if it was explicitly True). Langfuse reuses the global provider if one is set, in all three majors. Sharing it meant Langfuse's processor saw Laminar's spans (3.x exports every span; 4.x/5.x export any span with `gen_ai.*` attributes), stamped `langfuse.internal.is_app_root` / propagated attributes on them, and inherited Laminar's resource and sampler.
- **`OTEL_ATTRIBUTE_COUNT_LIMIT` is not set process-wide while a bridge is on.** Laminar's provider gets `SpanLimits(max_span_attributes=10000)` directly (`tracing/__init__.py::_span_limits`); setting the env var raised Langfuse's provider limit too. Copies are plain `ReadableSpan`s with a dict, so they are not capped.
- `tests/test_langfuse/test_bridge.py::test_langfuse_export_is_unchanged_by_the_bridge` compares Langfuse's export with and without the bridge. Keep it passing on every change here.

## Which spans reach Laminar

- Only the ones Langfuse exports. `langfuse_would_export` finds every `LangfuseSpanProcessor` on the provider and replays its `on_end` decision: `_is_langfuse_project_span` (langfuse-sdk scope only), `_is_blocked_instrumentation_scope` (3.x, 4.x), `_should_export_span` (4.x, 5.x; the default is the scope allowlist in `langfuse/_client/span_filter.py`). All private, so each is probed with `getattr` and skipped when absent; an exception means "not exported", like Langfuse.
- A span that isn't forwarded still goes to Laminar's `on_end`, marked `lmnr.internal.disabled`, so Laminar releases its per-span path bookkeeping and trajectory entry.
- LiteLLM's `langfuse_otel` providers export everything to Langfuse, so they are attached with `langfuse_owned=False` (no filter).

## Attaching

- `provider_attachment.py`: `attach_to_existing_langfuse_providers` walks `LangfuseResourceManager._instances`, and `patch_resource_manager` wraps `_initialize_instance` so clients created later are covered. Both are private but identical in 3.x-5.x. `Langfuse(tracer_provider=...)` providers are covered the same way.
- Attachment uses public `add_span_processor`; detach walks the private `_span_processors` tuple (`remove_span_processor`). Every branch of it logs at debug level, so a detach that silently stops working after an OTel SDK upgrade shows where.
- The bridge is installed on every `Laminar.initialize` and uninstalled on every `Laminar.shutdown` (`bridges/__init__.py`), so an initialize/shutdown/initialize cycle re-attaches with the new processor. No rebind logic.
- **LiteLLM** (`litellm_bridge.py`): attaches to `logger._tracer_provider`, and wraps `_get_tracer_with_dynamic_headers` to attach to each per-credential provider in `_tracer_provider_cache`. Newer LiteLLM stores `_CachedTracerProvider(provider=...)` wrappers there; unwrap with `getattr(entry, "provider", entry)` or the attach silently no-ops. The old second wrap (forcing a `litellm_request` span by nulling `_get_span_context`'s parent) is gone: it changed what LiteLLM sends to Langfuse.

## Translation (`processor.py::translate_span`, `translate.py`)

- Attribute names (`attributes.py`) are public constants: `LF_*` for Langfuse's keys, `OI_*` for openinference's, and the `gen_ai.*` keys Laminar writes come from OTel's `gen_ai_attributes` where it defines them (only Laminar-only keys like `gen_ai.usage.cost` and `cache_write` are defined here).
- openinference first (groq / google_genai instrumentations and LiteLLM's hybrid spans, which have no `langfuse.observation.type`), then `langfuse.*`. openinference forces `span.kind=TOOL` on any LiteLLM call that passes `tools`, so TOOL is trusted only without LLM signals.
- `generation|completion|embedding` -> LLM, `tool` -> TOOL, everything else DEFAULT.
- **Usage details are additive in Langfuse**: `input` excludes cached tokens, which arrive as `input_*` keys (`input_cached_tokens` from the OpenAI wrapper, `input_cache_read` / `input_cache_creation` from LangChain), and likewise `output_*` (reasoning). `gen_ai.usage.input_tokens` must include them (app-server subtracts cache tokens to get regular input), so `usage_attributes` sums. Cache / reasoning go to the semconv `gen_ai.usage.cache_read.input_tokens`, `cache_write.input_tokens`, `reasoning.output_tokens`. Cost details are additive the same way.
- LLM input/output -> `gen_ai.input.messages` / `gen_ai.output.messages` / `gen_ai.tool.definitions`; anything else -> raw `lmnr.span.input/output`. Input shapes (`genai_input_from_langfuse`): `langfuse.openai` chat sends a message list or `{messages, tools|functions}`, its **Responses API** path the `input` (string or item list, `instructions` already prepended as a system message) or `{input, tools, tool_choice, ...}` (matched only when every key is a Responses prompt key, so a manual `{"prompt": ...}` stays raw); a bare string is a user message. `langfuse.langchain` 3.x inlines tool definitions as `role: "tool"` messages (OpenAI `{type, function}` or Anthropic `{name, input_schema}` content; probe with `.get()`, a KeyError used to abort the whole span), 4.x/5.x use the OpenAI shape. Outputs: one message (chat), a string (streamed chat text), or the Responses items (a list, or the only item as a dict).
- **Every message goes through `normalize_messages` (LAM-2528), inputs and outputs alike**, into Laminar's `{role, content}` with `text` / `reasoning` / `tool_call` (`{id, name, arguments}`) parts and `{role: "tool", content, tool_call_id}` results. Same rules on both sides is the point: app-server dedups messages by hash (`unique_content`), so the tool-call turn a call outputs must be byte-identical to its copy in the next call's history. Before, chat outputs were wrapped as an OpenAI choice `{message: ...}` while the same turn in the next input became content parts, and Responses items stayed bare `{type: "function_call", ...}` objects. What it maps: chat `tool_calls` / `function_call`; Responses `function_call` (id = `call_id`, what `function_call_output` references), `function_call_output`, `reasoning` (summary text only; `encrypted_content` is dropped) and `message`, with consecutive items of one turn merged into one assistant message; LangChain `args`; Anthropic `tool_use` / `thinking` and `tool_result` (split out of the user turn into `tool` messages); Gemini's `model` role; openinference's `{message_content: ...}` content wrappers. Tool calls repeated in one message (LangChain keeps them in content blocks and `tool_calls`) are deduped by id. Provider extras (`refusal`, `annotations`, `additional_kwargs`, ...) are dropped and a single text part collapses to a string, both so input and output copies hash the same. Same rules as the TS bridge's `normalizeMessages`.
- `tests/test_langfuse/fixtures/python_sdk_payloads.json` holds what langfuse 5.2 really recorded for a two-call tool loop per integration (`langfuse.openai` chat / Responses, streamed and not; LangChain with OpenAI chat / Responses, Anthropic, Gemini). `test_message_shapes.py` asserts the shape and that call 1's output is in call 2's history. Re-record by running the loop against a `Langfuse(tracer_provider=TracerProvider())` client and dumping `langfuse.observation.input/output` from its exporter; shorten `encrypted_content`.
- OpenLLMetry's Anthropic instrumentation (`opentelemetry-instrumentation-anthropic` 0.63, which Langfuse documents) already writes semconv `gen_ai.input.messages` (`{role, parts}`) and passes through untranslated; app-server parses that natively.
- **Provider and request parameters.** Langfuse has no provider field (its cost inference matches the model name only), so `gen_ai.system` comes only from LangChain's `ls_provider` observation metadata (`LS_PROVIDER_ALIASES` renames the three values that differ from Laminar's price providers) or openinference's `llm.provider` (LiteLLM's `custom_llm_provider`; its "Unknown" is skipped). `langfuse.openai` records none, since the client may point at any OpenAI-compatible API. `model_parameters` / `llm.invocation_parameters` go through `model_parameter_attributes` to the `gen_ai.request.*` keys Laminar's instrumentations write (`reasoning_effort` -> `gen_ai.request.reasoning.level`, the three max-token names -> `max_tokens`, `n` -> semconv `choice.count`); other keys stay in the raw attribute. Non-numbers are skipped: Python LangChain records an unset `max_tokens` as `"Infinity"`. Same table as the TS bridge's `translate.ts`.
- **Session / user / tags / metadata (`_promote_trace_attributes`, LAM-2531) mirror what Langfuse's server reads** (`OtelIngestionProcessor.ts` in langfuse/langfuse: `extractSessionId` / `extractUserId` / `extractTags` / `extractMetadata`), so a trace shows the same values in both. Laminar's copy gets association properties (`session_id`, `user_id`, span `tags`, `metadata.*`; app-server merges them over all spans of the trace):
  - session: `langfuse.session.id`, `session.id`, then the `langfuse_session_id` key of observation, then trace metadata (first non-empty wins). User the same with `langfuse.user.id` / `user.id` / `langfuse_user_id`. Tags: `langfuse.trace.tags`, then `langfuse_tags` metadata.
  - The `langfuse_*` metadata keys are how `langfuse.openai` documents setting them (`create(..., metadata={"langfuse_session_id": ...})`): it records them as plain observation metadata in all majors and never calls `propagate_attributes`, so they were lost before LAM-2531. They are not repeated as Laminar metadata. `propagate_attributes`, `update_current_trace` (3.x) and the LangChain handler (which reads the same keys from `config["metadata"]`) already write `session.id` / `user.id` / `langfuse.trace.*`.
  - Tags parse like Langfuse's: a list, a JSON list (LiteLLM's `langfuse_otel` writes `langfuse.trace.tags` as a JSON string; `langfuse_tags` is always JSON), a comma-separated string, or one tag, deduped.
  - Trace metadata: `langfuse.trace.metadata` (one JSON object) and `.*`. **On the root span the observation metadata is trace metadata too**, the observation's value winning, as in Langfuse ("root" = no parent or `langfuse.internal.as_root`; a Langfuse span under a Laminar span is not a root, in either backend). Elsewhere observation metadata stays raw (apart from `ls_provider`): it is mostly LangChain's `ls_*` noise. So a LangChain root also brings `is_langchain_root` / `tags` keys, as it does in Langfuse.
  - Not mapped: `gen_ai.conversation.id`, openinference `tag.tags`, `langfuse.tags` / `langfuse.metadata` (undocumented server fallbacks), `ai.telemetry.metadata.*` (app-server reads it natively), and `langfuse.trace.name` (Laminar's `trace.name` exists; not requested yet).
  - **langfuse 5 JSON-encodes metadata values** (`'"v"'`); `json_encoded_metadata` (major >= 5) decodes them, older majors' raw strings are kept as is. A list in metadata is JSON in every major; a JSON-list *string* in 5.x is encoded twice, so `_tags` parses again when the first parse gives a string starting with `[`.
- **Converted attributes are dropped from Laminar's copy** (never from Langfuse's export), so Laminar doesn't store and bill each payload twice. `translate_span` returns `Translated`, where None removes a key in `on_end`. Dropped: `model.name`; `usage_details` / `cost_details` when they produced attributes; the input / output key the value came from (`observation.*`, else `trace.*`) whether it became GenAI messages or the raw `lmnr.span.input/output`; `model.parameters` / `llm.invocation_parameters` are rewritten to only their unmapped keys and dropped when none are left (`_convert_model_parameters`). On openinference spans also the converted `llm.input_messages.*` / `llm.output_messages.*` / `llm.tools.*` families, `llm.model_name`, token counts, and the `input.value` / `langfuse.observation.input` (and output) copies LiteLLM's hybrid spans carry: once either is converted, both go. Metadata, tags, user / session ids and unconverted values stay. Same rules as the TS bridge.
- `update_current_trace` (3.x only) sets trace attributes on the root span only; `propagate_attributes` (all majors, the only API in 5.x) sets them on every span.
- **Errors**: Langfuse never records an `exception` event; a failure is OTel ERROR status and/or `langfuse.observation.level=ERROR` + `status_message`. Laminar marks a span failed only by an `exception` event, so `error_event` adds one to the copy (hand-built: the span has ended, `record_exception` isn't available). `level=WARNING` is left as the raw attribute.
- Every forwarded copy gets `lmnr.span.bridge.name=langfuse` and `lmnr.span.bridge.version=<installed langfuse version>`.

## Nesting

- Langfuse spans under a Laminar span: Laminar's `observe` attaches its context to the global OTel context, so Langfuse picks the parent up, and the shared `LaminarSpanProcessor` path map gives the full path.
- Laminar spans under a Langfuse span: `inherits_global_context` turns on `tracing/context.py::set_inherit_global_context`. `get_current_context()` then merges the global context in when its current span is not Laminar's (`instrumentation_scope.name != TRACER_NAME`). Merging the whole context (not just the span) keeps Langfuse's propagated attributes for Langfuse spans created under a Laminar span.
- Langfuse sees a parent id it never receives for Langfuse spans under a Laminar span. Accepted: langfuse 4.x/5.x mark such a span `langfuse.internal.is_app_root` (`_mark_app_root_candidate` checks whether *it* exports the parent), so Langfuse's trace stays coherent. Laminar's own spans (including instrumentations Langfuse has no counterpart for, like browsers or Kernel) never reach Langfuse: they are created on Laminar's private provider, and no Laminar instrumentation uses the global `trace.get_tracer`.

## Tests

- `tests/test_langfuse/`: `test_translator.py` (pure translation, no SDK), `test_bridge.py` (real `Langfuse(tracer_provider=TracerProvider())` client, recording exporter swapped into `LangfuseSpanProcessor`, separate `LaminarSpanProcessor` with an in-memory exporter), `test_litellm_bridge.py`, and `test_initialize.py` (what `Laminar.initialize(bridges=...)` passes to a mocked `init_tracing`: blocked instruments, private provider, context inheritance, unavailable / unknown bridges).
- **No subprocess tests.** The global tracer provider can be set once per process, and importing `langfuse.openai` patches the openai SDK for the whole process. Earlier versions ran end-to-end `initialize` and `langfuse.openai` scenarios in subprocesses for that reason; they were dropped as too hacky (PR #422 review). Don't import `langfuse.openai` in the test session: with langfuse 5 its wrapper records `OpenAI-generation` spans into every later openai test. The OpenAI wrapper's payload shapes are covered by `test_translator.py`.
- The dev pin is langfuse 5.2.0. `run-tests.yml` runs `tests/test_langfuse` against 4.15.0 and 3.15.0 overlays. Locally: `uv run --with langfuse==4.15.0 pytest tests/test_langfuse`.
- langfuse 3.15, 4.15, 4.18 and 5.2 all import on Python 3.14 (the old pydantic-v1 problem is gone).
